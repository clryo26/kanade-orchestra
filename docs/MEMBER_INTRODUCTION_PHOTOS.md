# 団員紹介・写真の軽量化

## 対象と境界

団員紹介・団員管理・本人編集の写真と紹介情報のみを変更する。共通認証の全件取得・権限条件・障害時対応は変更しない。他用途のファイル保存・配信・削除・再送、他画面のCSS・キャッシュTTL、Cloud Run設定は変更しない。

`GET /api/member-introductions` は既存認証を1回行い、紹介用の明示した公開項目だけを返す。エキストラを除外し、DBモードでは列を限定したSELECTでBase64を画像URLへ置換してからアプリへ渡す。既存の団員一覧・個別詳細APIの用途は維持する。

紹介データは `portalAppState.memberIntroRecords` に保持し、編集用の詳細キャッシュへ混ぜない。画面を開くとETagで再検証し、写真を待たず文章を描画する。通信失敗時は再試行を表示し、ログアウト・アカウント変更後の遅延応答を破棄する。プロフィール編集を開いた場合も進行中の紹介応答を破棄する。

## 登録・写真変更

- 長辺800px以内、縦横比維持、拡大・保存時のトリミングなし。
- WebP品質75。200KiBを超える場合だけ品質65、長辺640px、長辺480px/品質60へ段階的に調整する。収まらなければ旧写真を保持してエラーにする。
- 撮影方向を補正、ICC色変換後にsRGBで保存し、EXIF・XMP・不要なICC情報を除去。透明部分は保持。
- JPEG/MPO/PNG/WebP/HEIC・HEIF/GIF/BMP/TIFFをデコードし、静止画として保存する。HEIFはデコーダーのprimary image、他の複数フレーム形式は先頭画像を使用する。
- 入力上限20MiB・6000万画素。変換はDBトランザクション外・ワーカースレッドで実行し、1プロセス1件に制限する。混雑時は同じ操作IDで再試行する。
- `member_service` だけが変換コールバックを指定する。ファイル操作のダイジェスト・リプレイ判定は元ファイルのまま実行し、初回保存時だけ変換する。他kindではコールバックを実行しない。
- 保存するのは縮小画像だけ。アセットのSHA-256は縮小後の内容。団員写真だけの `member_photo/v1/{UUID}.webp` 名前空間とファイル名 `member-photo-v1.webp` を処理版のマーカーとし、移行時には寸法・容量・ハッシュも照合する。利用者が元ファイル名を同じにしただけでは変換済みと判定しない。
- 写真を選び直さない編集では再変換しない。UUID保存、COMMIT後の参照切り替え、失敗時の旧写真保持、操作ID再送の既存ルールを維持する。

## 既存写真の移行

`scripts/normalize_member_photos.py` の既定動作は読み取り・メモリ内試算だけ。画像本体、氏名、紹介文、認証情報を計画やログへ記録しない。計画はテナント・DB/バケットのフィンガープリント・処理版に結び付ける。

実行前に、対象環境のDB/GCS設定を明示的に用意する。TESTと本番の計画を取り違えない。以下のファイルはTEMP等のソース共有対象外へ保存する。

```powershell
$memberPhotoPlan = Join-Path $env:TEMP 'member-photo-test-plan.json'
$memberPhotoReport = Join-Path $env:TEMP 'member-photo-test-report.json'
.venv/Scripts/python.exe scripts/normalize_member_photos.py --organization default --output $memberPhotoPlan
# 計画を確認して適用する場合のみ --apply-plan を指定する。
.venv/Scripts/python.exe scripts/normalize_member_photos.py --organization default --apply-plan $memberPhotoPlan --run-id member-photo-test-1 --output $memberPhotoReport
```

`ready` だけを適用する。原画像のSHA-256と参照が変わっていれば停止する。切り替え時にも写真参照を行ロック下で比較し、写真参照と必要な更新日時・アセット記録だけを更新する。変換中の紹介文・権限などの更新を保持する。変換済みは再圧縮しない。元画像・旧アセットは削除せず、確認期間後に既存のcleanup手順で整理する。

状態は `ready` / `normalized` / `missing_source` / `unresolved_reference` / `source_error` / `conflict` / `converted` / `failed` で別集計する。

旧固定名参照は、ファイルが存在するだけでは採用しない。先に既存 `scripts/migrate_reference_assets.py` の確認済みマニフェストで登録情報を確定する。`missing_source` は勝手に参照削除・置換しない。TESTで調査済みの既存欠損3件の復旧は本変更の対象外。

## 検証・反映

Pythonで画像形式・向き・透明部分・不正画像・保存・デプロイ前後の再送・移行競合・他用途のバイト保持を確認する。フロントでは一括取得、編集用キャッシュとの分離、再試行、ログアウト後の応答破棄を確認する。Chromiumでは59人の紹介が一括通信で描画され、写真が遅延取得されることを確認する。

反映はTESTコード反映→TEST計画・移行→既存欠損の別集計→機能・実機・性能確認→本番コード反映→本番再計画・移行→本番確認の順。移行の更新許容差分以外の団員項目と、他画像・楽譜・録音・通知の既存動作を比較する。

iPhone実機の色・画質・HEIC、48MP HEICの512MiBコンテナでのピークメモリ、実環境の応答時間、実際のTEST/本番移行は別途受入確認する。Cloud Runの共通設定変更はこの実装に含めない。

### 実装時の確認結果（2026-10-20）

- バックエンド全体：573件成功、78件スキップ。外部DB等を要するスキップは成功として数えない。最終追加の画像・本人編集・移行防御テストは関連18件を再実行して成功。
- 専用ローカルPostgreSQL：ファイル操作・写真移行の10件成功。テナント分離、他項目保持、写真変更競合、移行再実行を確認。検証用DBは終了後に停止。
- フロントエンド全体：110ファイル・1189件成功（レビュー後の競合回帰テストを含む）。構文・読み込み順・共有状態参照のチェックも成功。
- Chromium：団員紹介と既存アルバムの関連2件成功。団員紹介はAPIをモックしたブラウザー検証であり、実環境の性能確認ではない。
- リリース安全性チェック、Pythonコンパイル、依存ロック整合、差分空白チェック成功。着手前から存在した別件9ファイルのSHA-256一致を確認。

コードは未デプロイ。本番・TESTの既存画像は、この実装作業では更新していない。既存画像の縮小は、対象環境に反映した後で上記の計画・適用手順を実行して完了させる。

レビュー後、団員紹介の失敗応答にも読み込み世代の確認を追加。キャッシュ無効化後の新しい表示が成功した後で、古い通信の失敗が届いても表示を上書きしない。修正前に再現する回帰テストを追加し、通常の失敗時の再試行表示と併せて確認した。配信用スクリプトのバージョンも更新した。
