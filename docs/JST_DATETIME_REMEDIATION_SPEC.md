## 2. 目的・適用範囲・完了の定義

### R01 基本原則

ポータルの利用者向け日時表示、入力の意味、業務上の日付境界は `Asia/Tokyo`（現在の日本標準時、UTC+09:00）で統一する。日時の特定の瞬間は、サーバー・ブラウザー・DB接続の時間帯設定によって変えない。

同じ記録・同じ更新版は、保存直後、メモリーキャッシュ、IndexedDB、DB再取得、別Cloud Runインスタンスで同じ日時になる。更新による正当な変更と、形式解釈による変化を区別する。

同じ瞬間の表記変更と、誤保存された瞬間の補正は別工程にする。本番はDB Onlyを維持し、旧JSONを本番の代替データソースにしない。

適用範囲は通常業務API、共通日時処理、対象画面、日付検索・期限判定、およびその修正に必要な保存整合性と移行である。既存専用の宣伝・楽譜・音声同期APIは契約を保ち、共通処理へ無理に統合しない。

OSの時計合わせ自体は本仕様の変更対象ではない。DB・アプリの時計差は事前照合し、端末時計に誤りがある場合の表示上の限界を、時間帯の問題と区別する。登録等の確定時刻と権限判断を端末時計に委ねない。

## 3. 日時契約と対象項目

### 3.1 分類と形式

| 分類 | API/保存契約 | 表示・計算 |
|---|---|---|
| 特定の瞬間 | 明示的オフセット付き。通常業務API出力は `YYYY-MM-DDTHH:mm:ss.ffffff+09:00` | 日本時間。画面ごとの既存の秒表示有無は維持 |
| 日付 | `YYYY-MM-DD`、DBは既存DATE等。新規の汎用UTC午前0時変換は禁止 | 時差変換なし、暦日演算 |
| 月 | `YYYY-MM`、既存列を維持 | 月番号等の暦演算。日時変換しない |
| 時刻 | 既存の `HH:mm` 等を維持し、許容精度を項目ごとに定義 | 日本時間の時刻。単独でUTCへ変換しない |
| 経過時間/数値時刻 | 既存の秒、ミリ秒、epoch等の単位・契約を維持 | 経過時間を9時間ずらさない |
| 識別・競合制御 | 瞬間・マイクロ秒精度・署名やハッシュの既存規則を維持 | 表示用文字列を識別子に転用しない |

`TIMESTAMPTZ` の内部UTC保存を維持する。取得時オフセットは入力元の時間帯の証明ではない。汎用的な全列型変更やDB全体のTimeZone変更は行わない。

| チューナー/メトロノームの測定・セッション日時 | 瞬間、epoch/UTC等の既存契約 | tuner/metronomeサービス・ストア・画面 | 同期・ハッシュは維持、表示と検索境界をJST化 |
| 履歴のメモ日付、日別グラフ | 日付 | tuner/view_history、intonation_profile等 | UTCの日付切出しを除去。既存JST実装は維持 |
| ファイル名/日別保存先 | 識別子または運用上の日付 | album、recording_upload、desired_piece_asset | 保存先を一括改名しない。新規の業務日付はJST、識別はUUID等 |

これは調査に基づく初期台帳であり、全項目の旧形式解釈が確定済みという意味ではない。実装担当は検索結果を、修正対象・正しい既存実装・契約上維持する例外へ全件分類する。

項目ごとにテーブル/JSONパス、API、生成元、旧形式、解釈根拠、新形式、精度、null/空欄、異常時、識別依存、移行区分、テストIDを台帳へ記載する。将来日時が正当な予定・期限に、システム更新日時の未来値制限を適用しない。

## 4. 共通処理・保存・API

### R02 共通バックエンド処理

生成、瞬間の厳密解析、JST出力、暦日の検証、UTC変換、旧形式専用解析を責務分離する。業務処理はservices/core/repositoriesに置き、app_coreは互換ファサードのままにする。

- 時間帯なしのnow、fromtimestamp、引数なしastimezone等にシステム日時の意味を依存させない。
- 新規の瞬間はaware datetimeで処理し、naiveへ時間帯を付ける処理は確定した旧形式codecだけに限定する。
- 通常業務APIのシステム日時はJSTの6桁小数秒へ統一する。既存UTC/epoch例外は台帳で明示する。入力のZと任意の許容オフセットは同一瞬間へ解析する。
- システム管理項目はサーバーが設定する。created_atは通常更新で変更しない。既存の権限を弱めず、任意日時の上書き経路を追加しない。
- 永続化されるDB生成日時はDBが基準となる。競合判定とupdated_at生成は同一トランザクションでロック取得後のDB現在時刻を使う。長い待機前のトランザクション開始時刻を実更新時刻として流用しない。
- Pythonが生成するAPI診断日時等はawareな時計を使う。反映前にDBとの時計差を測定する。
- mtimeはepochからaware日時へ変換する。GCSのaware日時と同じ出力契約に合わせる。
- 宣言した項目だけを変換する。自由記述・任意JSON・操作ID・署名対象を推測変換しない。
- 日付、月、時刻を厳密に検証する。存在しない日付、NaN/Infinity、単位不明の数値を自動補正して受理しない。新規入力の小数秒は最大6桁を契約とし、超過時の暗黙切捨てをしない。
- 新規の不正入力は422を原則とする。既存専用APIのエラー契約を変える場合は別途互換対応を記載する。保存側必須値が不正なら通常保存を止め、サービスエラーとして調査可能にする。機密値はログへ出さない。

JST実装は、Python 3.10/Windows/Dockerで同じ結果となることを確認する。ZoneInfoを使うならIANAデータの同梱・依存関係を保証し、環境の偶然の有無に依存させない。固定+09:00を使う場合は現行ポータルの対象期間に限る方針を文書化する。

DB列の実精度を照合し、保存前後で競合トークンが変わらない形式を返す。レスポンスはコミットされた値から生成し、表示用変換によってupdated_atを進めない。

## 5. 画面表示・日付計算・検索

### R03 表示と暦演算

`ja-JP` と `timeZone: Asia/Tokyo` を明示した共通表示処理を使用し、年月日・曜日・時刻を同じ瞬間から生成する。対象値は事前に項目契約で解析し、時間帯なし文字列をブラウザー任せに解釈しない。

| 入力 | 修正後の表示 |
|---|---|
| 2026-10-19T03:00:00Z | 2026/10/19（月）12:00 |
| 2026-10-18T16:00:00Z | 2026/10/19（月）01:00 |
| 2026-10-19T01:00:00+09:00 | 2026/10/19（月）01:00 |
| 日付項目2026-10-19 | 2026/10/19（月） |

日付・月の演算は暦の演算とし、端末の夏時間による23/25時間の日を「日数差」として扱わない。曜日、残日数、翌日、予定区分、会費月、月加算、日別グラフを点検する。月末の繰越/末日丸め等の業務規則は今回推測で変更せず、現行仕様を固定してテストする。日付演算にUTCのDateを内部利用すること自体は許容するが、瞬間との取り違えを禁止する。

日時入力欄の値は日本時間として明示変換し、日付欄はYYYY-MM-DD、時刻欄は既存HH:mm等を維持する。空欄は既存の未記録等を維持。不正な表示値は日時不明とし、元値を書き換えない。

表示のためのDate変換でマイクロ秒を失っても、元の競合トークンは文字列のまま保持してそのまま返送する。精度を落とした値を競合・識別・ハッシュに使わない。

### R04 今日・期限・検索境界

「今日」は日本時間。利用期限の最終日は丸一日有効で、翌日00:00から期限切れ。権限・期限の最終判断はサーバーが行う。端末の現地日付・端末が送るtoday値を認可根拠にしない。

画面は初期表示、再描画、操作、復帰、日付変更で当日判定を再評価する。背景タブでタイマーが遅れることを前提に、復帰時にも再計算する。新たな時刻同期機能は必須にせず、端末時計の誤りと時間帯誤りを区別する。

日付検索は全対象で `開始日00:00+09:00 <= 時刻 < 終了日翌日00:00+09:00`。23:59:59や23:59:59.999への丸めで終端を表現しない。チューナーはUIとローカルストアの両方を排他的終端へ変更し、他の呼出元・同期APIの既存契約を確認する。開始>終了、不正日付は入力エラー。空の片側条件は既存の意味を維持する。

回答期限は入力・保存・再編集で同じ暦日を維持する。既存の回答受付制限の有無を調査し、新たな回答拒否規則は追加しない。判定がある場合の終了境界だけJST翌日00:00へ統一する。

events.deadlineは当面既存DB型を維持し、業務APIは日付として返す専用codecを設ける。旧UTC午前0時と新JST午前0時を区別するため、管理された一括移行か、DB管理の形式バージョンを選定する。入力オフセットをDBが保持すると仮定しない。根拠不明値がある状態で新旧を推測混在させない。

## 6. 更新競合・一覧保存・削除

### R05 永続化の原子性

期待更新日時は、DB現在値とマイクロ秒精度の瞬間として比較する。同じ瞬間のZ/+09:00表記は一致、異なる値は409、不正な要求は422。旧値は確定したcodecでのみ解析する。DB側の必須値不正は更新停止。競合指定の既存省略可否は維持し、省略要求に古い画面検出まで保証しない。

比較、認可に必要な現在値確認、更新版生成、対象保存を同一DBトランザクションで行う。テナントと対象IDを条件に含め、条件付きUPDATEまたは適切なロックを使う。削除済み対象への更新をINSERT/UPSERTで復活させない。対象不存在と版不一致の応答規則を各APIで固定する（既存契約を維持し、通常は不存在404、版不一致409）。

単一項目の更新は対象行と必要な関連行だけを書き換える。古いコレクション一覧を書き戻さない。一覧置換を残す経路では、テナント/コレクション単位のDB側ロック等を読み取り前からコミットまで保持し、対象に書く全経路（登録・更新・削除・子項目変更）が同じ規則に参加する。プロセス内ロックやSELECT FOR UPDATEだけで新規追加を防げるとみなさない。無保護な一覧保存と行単位更新の混在は禁止する。

混在対象はrecording_metadataだけでなくconnection_settingsも含む。connection_settingsの起動時シードは、通常の行単位登録・更新・削除と同じ `collection:connection_settings` のDBロック（テナントをキーへ含める）を取得した後、同一接続で再読込し、未設定分だけを補う。一覧保存ガードを迂回するallow_bulk等は保護済み経路内に限定し、起動時という理由だけで無保護な置換を許可しない。

親子データ、並び順の再採番、投票等の部分変更は、変更単位とロック対象を明示し、他の項目の内容を古い値で戻さない。複数ロックの順番を固定し、有限の待機/処理時間を設ける。デッドロック等の再試行はDB処理の安全な範囲に限定し、ファイル作成や通知を重複実行しない。

異なる操作が同じ更新版へ要求した場合は一方だけ成功。別項目の同時更新は双方を保持。更新と登録で追加が消えず、更新と削除で削除が復活しない。省略可能な競合トークンを省略しても、無関係な他行の更新を破壊してよいわけではない。

### R05-A 操作の同一性・再送・応答

更新版は「どのデータ状態を編集したか」、操作IDは「どの一回の操作か」、attempt_idは「その操作をどの実行試行が処理中か」を区別する。操作IDを持たない既存APIまで無条件に新しい操作プロトコルへ変更しない。新たに必要な対象APIと、既存契約を維持する対象を台帳へ明記する。ただし次段落の今回アセット化する対象APIは、1.6のE01・E03に基づく明示的な例外であり、この原則の「無条件の変更」には当たらない。例外は次段落の対象に限定し、他の既存APIへ広げない。

今回アセット化する参考楽譜・共通画像の作成/置換/削除と、確定参照を持つ所有行の削除には新しい操作プロトコルを導入する。クライアントが一回の操作ごとにUUIDを生成し、再送では同じIdempotency-Keyを維持する。操作表に指紋・状態・試行・終端結果を保持し、認証付き結果照会を設ける。対象の旧キーなし要求は428と再読込案内にする。POSTも対象とし、PUTの版比較やサーバーが毎回新しいIDを振る方式を再送保証の代わりにしない。既存の無関係なAPIだけ現状契約を維持する。

操作結果と対象行・アセットの確定は同一接続/同一TXとし、行単位リポジトリへ委譲するために独立した内側COMMITを行わない。計画の新規操作表はportal_file_operations、アセット表はportal_file_assetsとする（いずれも実装予定）。

| 要求の関係 | 動作 |
|---|---|
| 異なる操作ID・同じ期待更新版 | 初回のみ成功、他方409。通常の競合制御 |
| 同じ操作ID・同じ内容・処理中 | 既存の処理中応答または認可済み状態照会。並列に再適用しない |
| 同じ操作ID・同じ内容・完了済み | 保存済みの成功/拒否結果を返す。変更・通知・ファイル作成を再実行しない |
| 同じ操作ID・異なる内容 | 既存専用APIの409等の契約に従って拒否。過去結果を書き換えない |
| 操作IDなしの既存要求 | 既存の許容/再読込要求を維持。冪等性を保証したと報告しない |

操作記録の一意範囲はテナント・操作主体のアカウント世代・操作IDとする。要求指紋はHTTPメソッド、対象ID、意味のある変更値、期待版、添付の内容ハッシュ等を含める。multipartの境界文字列や現在の表示形式を指紋に使わない。新規方式の日時は精度を保って正規化する一方、既存方式の署名/指紋を勝手に変更して旧再送を別内容扱いにしない。

完了済みの再送は操作記録から応答し、その後の対象の版変更や削除だけで元操作を競合/不存在へ変えない。ただし現在のセッション有効性、テナント、主体世代、結果の閲覧権限は毎回確認する。成功結果があっても権限失効者や別世代会員へ返さない。結果閲覧の認可と、新規に変更を実行する際の対象版/権限確認を分離する。

業務変更、確定アセット参照、完了結果の保存を同一DBトランザクションで確定する。再送は保存時点の結果であり、現在の一覧データとは区別する。利用者表示は成功確定後に必要に応じて最新状態を取得する。

同じ完了操作の再送を新規通知生成の契機にしない。通知の配信・再試行は既存契約を維持し、外部配送のexactly-onceを本仕様で新たに保証するものではない。

状態照会の応答に内部キー・他人の操作・機密情報を含めず、認証情報を共有HTTPキャッシュへ保存しない。操作ID不明、保持期限外、結果不明を成功/未実行と推測しない。自動再送は同じ操作IDを保ち、結果不明を理由に新しいIDで自動作成し直さない。

操作結果の保持期間と再送保証期間をAPIごとに明記する。既存楽譜の30日等の保持契約を無条件に変更しない。新設方式では、結果本文を消しても失効済みIDを識別する最小記録等を残し、古い操作が新規として黙って再実行されないようにする。未解決・実行中・回収未完了の記録は結果本文の保持期限だけで消さない。既存APIの保持期限外の制約も移行表・試験・利用者案内へ記載する。

### R05-B 再送判定・対象確認の共通順序

R05/R06の保存手順は、以下の分岐順序に従う。完了済み結果の返却に、現在の対象レコードの存在、期待版一致、変更可能状態を前提条件として追加しない。

1. 現在のセッション有効性、テナント、操作主体のアカウント世代を確認する。更新要求は形式と、内容を同定するための構文/精度/必要な添付ハッシュを確認する。状態照会は操作ID等の照会形式だけを確認し、元の添付を要求しない。この段階では対象行の存在・現在版・変更権限を理由に完了済み結果を遮らない。新しい規則で過去の要求が解析不能にならないよう、必要な互換codecを使用する。
2. テナント・主体世代・操作IDで操作記録を照合する。更新要求は指紋も比較する。同じIDの異なる内容は拒否する。同じ内容で終端状態なら、操作記録に対する現在の結果閲覧権限を確認し、保存済み結果を返して終了する。状態照会は元の添付や対象行を要求せず、認可された操作記録を読む。
3. 新規操作、またはprocessingから安全に再開可能な操作だけ、DBの一意制約・比較更新等で一つのattempt_idに実行権を与える。稼働中の他試行がある場合は既存の処理中応答とし、並列実行しない。照合から予約までの競合でも終端結果の上書き・二重実行を防ぐ。
4. 実行権を得た試行だけ、現在の対象存在、変更権限、期待版、動的な業務条件を確認する。対象が削除済みなら新規実行として既存の404等、版不一致なら409とする。ファイルが必要なら、この確認後に準備記録を永続化する。
5. 外部保存後、確定トランザクションでも実行権、現在の認証/権限、対象版、アセット状態を再確認し、業務変更・結果・参照を同時確定する。別試行へ引継ぎ済みなら確定せず、現在の操作状態へ合流する。
6. 確定した結果を返し、回収等はR06に従う。コミット結果が不明なら操作記録を照合してから応答を決め、結果不明のまま新しい操作を起こさない。

操作IDを持たない既存APIには、台帳で定義した既存の認可・対象確認・競合処理を適用し、無条件に操作記録を新設しない。R06で新たに必要な操作プロトコルを導入する対象は、旧要求の拒否/互換方法を反映前に確定する。

結果閲覧の認可に必要な主体・操作種別等の情報は操作記録等へ保持し、削除済み対象の再取得を必須にしない。結果閲覧の可否は現在の認証/権限で判定するが、元対象の現在版との一致を再要求するものではない。

| 分岐 | 現在対象の確認 | 結果・副作用 |
|---|---|---|
| セッション無効・別テナント/別主体世代・結果閲覧不可 | 結果取得のために対象を迂回参照しない | 既存の認可応答。保存済み結果を漏らさない |
| 要求構文不正・互換規則でも解析不可 | 対象変更は行わない | 契約どおり入力エラー。誤った指紋で受け付けない |
| 同じ操作ID・異なる指紋 | 版比較で元結果を覆さない | 既存の409等。元結果と業務データを変更しない |
| 同じ内容・succeeded | 現在の存在/版/変更権限を再実行条件にしない | 結果閲覧を認可し、元の成功結果。削除後も404へ変更しない |
| 同じ内容・rejected | 現在の状態が改善していても元操作を再実行しない | 元の拒否結果。意図して再操作する場合は新しい操作として行う |
| 同じ内容・processingで有効な他試行あり | 新たな変更処理は開始しない | 処理中/認可済み照会。再アップロード・通知再生成なし |
| processingで引継ぎ可能 | 実行権取得後に現在条件を確認 | 新attempt_idでのみ再開。旧試行は確定不可 |
| 新規実行で対象が不存在・版不一致・変更権限なし | 実行権取得後および確定時に確認 | 既存の404/409/403等。確定可能な拒否は当該操作の結果として保存 |
| DB接続不能・照会結果不明・コミット成否不明 | 未確認のまま対象変更/回収へ進まない | 一時障害/保留応答。404・未実行・成功と推測しない |
| 操作記録が正常に照会できたが存在しない | 更新要求か状態照会かを区別 | 新規要求は予約判定へ、状態照会は既存の不明応答。新規要求でも失効済みIDは保持規則に従う |
| 保持期限外・失効済みID | 期限外を理由に対象を黙って再作成しない | R05-Aの保持規則と既存APIの制約に従い、案内/拒否/照会へ |

入力・権限・版等による確定的な拒否と、一時的なDB/GCS障害を区別する。一時障害や未確定コミットをrejectedへ固定して同じキーの安全な再開を永久に阻害しない。拒否結果の確定自体も現在のattempt_idに限定し、そのコミットが不明なら再照合する。DB照会が失敗したため記録の不存在を確認できない状況と、正常照会で記録がない状況は別の応答・状態として扱う。

## 7. ファイルとDBの整合性

### R06 確定参照・置換・回収

DBとGCSは単一トランザクションではないため、下記の順序と状態を明示する。対象は今回修正する参考楽譜、共通画像、関連する添付保存削除経路。既存の宣伝/楽譜専用アセット・操作記録は維持し、同等の機構を重複作成しない。

1. R05-Bのセッション/主体・要求確認、操作記録/指紋照合、結果閲覧の認可を行う。同じ内容の完了済み操作はここで結果を返す。現在対象の存在・版・変更権限を先に確認して、保存済み結果を404/409へ変えない。
2. 新規実行または安全に再開する試行だけ、実行権取得後に対象存在・変更権限・期待版を確認する。外部保存の前に、操作ID、現在のattempt_id、予定アセットキー、内容ハッシュ/サイズ、処理状態、必要なリースをDBへ記録してコミットする。準備記録が確定したと確認できなければアップロードしない。
3. テナント・アセット・実行試行を識別する衝突しないキーで仮保存する。既存ファイルへの固定名上書き、時刻文字列だけの一意性保証は禁止。外部アップロード中にDBロックを保持しない。
4. DBトランザクションで実行権、現在の認証/対象権限、対象版、アセットの状態を再確認する。新参照、更新版、操作結果、旧参照の回収候補を同時に確定する。保存の成否が未確定な候補を配信しない。
5. コミット済み参照だけを配信する。未確定候補の「最新mtime/updated順」で配信対象を選ばない。
6. 旧参照の回収はコミット後、参照/読取り保護/状態の再確認を経て行う。次の成功更新の新参照を消さず、旧アセットの正確なキー/世代に限定する。
7. 競合/ロールバックが確定した場合だけ、その要求・実行試行の未参照仮ファイルを回収する。prefix内の一括trimや他要求のファイルを巻き込む削除は禁止する。

この禁止は反映途中の状態にも適用する。保存の行単位化だけを先に反映し、旧方式のprefix一括trim・DB確定前削除が残る状態を本番・TESTの利用者へ開放しない（1.7 F03）。運用スクリプト（`scripts/migrate_base64_images.py` 等）も同じ規則に従う（F02）。

準備記録はファイルがまだ存在しない状態も表せる。記録直後の停止、アップロード応答喪失、アップロード成功直後・参照確定前の停止から、操作記録と保存実体を照合して再開または回収する。クライアントが接続を切ったことだけで処理を取り消し済みとはしない。

参考楽譜には確定ファイル名/アセット参照をDB側に保持する必要がある。必要な列または専用参照表は既存スキーマとテナント境界を確認して移行で追加する。既存URLは互換ルートを維持できる。旧参考楽譜からの移行は、保留アップロードと確定済みファイルを照合し、選定根拠を残して参照を固定する。判断できないものを最新候補で自動確定しない。

候補がちょうど1件でも、その1件が中断/失敗アップロードである可能性があるため、件数だけで配信・自動移行しない。旧DB参照、テナント/所有者、保存キー/世代、既知の確定操作等の根拠をマニフェストで照合して参照を確定する。確定できない対象は要確認として扱い、必要な旧参照の移行が完了するまで対象機能を一般利用へ開放しない。共通画像の旧固定名も同じ原則で扱う。

コミット成功後の通信切断は「失敗確定」ではない。操作ID/アセット参照をDBで照合できるまで、候補ファイルを削除しない。ロールバック確認とコミット結果不明を区別する。結果不明時は状態照会で収束させ、非冪等な登録やアップロードを盲目的に再試行しない。

GCSでは作成時の未存在条件、削除時の世代条件等を使い、同名別世代を誤削除しない。ローカルでは同等の一意名・排他的作成を使う。回収は永続候補と参照/操作状態に基づき再実行可能にし、進行中の処理を経過時間だけで孤立ファイルと判断しない。保持期間は既存運用に合わせ、無制限の仮ファイル蓄積を防ぐ。

### R06-A 状態・実行試行・回収の境界

新設する対象では下記の論理状態を必ず表現する。名称は既存専用テーブルに合わせてよく、同じテーブルを新設する要求ではない。

| 対象 | 論理状態 | 必須の制約 |
|---|---|---|
| 操作 | processing / succeeded / rejected | 終端状態と結果は原則不変。再送で再適用しない |
| 実行試行 | 有効 / 期限切れ / 別試行へ引継ぎ済み | DB現在時刻とattempt_idで判定。旧試行は確定できない |
| アセット | staged / active / retired / delete_pending / deleted | activeは業務参照と同時確定。回収対象を新参照へ再利用しない |
| 不明な結果 | DB照合待ち | 失敗・未実行へ推測変換せず、回収や新規再実行を抑止 |

リース切れ後に別の試行が引き継ぐ場合、比較更新で実行権を交代させ、別の仮アセットキーを割り当てる。旧試行のアップロードが遅れて完了しても、旧attempt_idによる参照切替・終端結果更新はDB側で拒否する。旧試行の後処理は自分の未確定アセットに限り、引継ぎ先のファイルを消さない。参照を外してから古い処理がactiveへ戻す遷移も禁止する。

回収可能性をDBで再確認し、状態をdelete_pendingへ確定してから外部削除する。確認と削除の間にactiveへ戻せる遷移を残さない。共有された旧実体については、参照照合範囲を現在のテナント内だけに狭めて他の参照を壊さない。必要な横断照合は内部の可否判定だけに用い、他テナントの情報を利用者へ返さない。

一度NotFoundになっても遅延アップロードが実体を後から作る場合を考慮する。旧試行の実行/外部処理が終わったことを確認できるまで回収記録を早期削除せず、削除済み状態の再照合等で遅延孤立実体を回収する。リース期限だけで外部I/Oが停止したとは判断しない。各処理の最大時間、保持・猶予期間、再照合周期は台帳に数値で定義し、有限の外部タイムアウト・再試行予算と整合させる。

旧アセットを参照して開始済みの配信と、置換後の回収も競合し得る。既存の楽譜用猶予/リースを維持し、新設対象には配信中保護または十分な猶予と再読込みを含む方式を定める。版固定ダウンロードは新しい内容へ黙って差し替えず、対象世代を維持する。論理的に「現在のファイル」を返すルートは認可と参照を再取得して回復できるが、最新候補探索へ戻らない。

新設対象では、配信参照を取得する短いTXでアセット行をロックし、DB時刻から15分後までの `read_protected_until` を延長・確定してから実体を読み込む。回収は同じ行をロックし直して保護期限を確認する。候補選択時の判定だけで削除せず、先に `delete_pending` となったアセットの新規配信は開始しない。退役や別読取りの終了・失敗で保護を短縮しない。15分はストレージ読取りの再試行予算120秒と最終要求タイムアウト60秒を上回る保護期間であり、このI/O予算を変更する際は保護期間も再評価する。停止した読取りの保護は期限切れで解消し、DBロックを外部I/O中に保持しない。

旧ファイル削除が失敗しても、コミット済み保存を失敗応答へ戻さず再回収する。コミット後の通知・キャッシュ更新の失敗も、DBロールバック扱いにしない。外部処理は有限のタイムアウト・再試行予算を設定する。

配信キャッシュにはアセット版を反映する。参照が切り替わっても同じURLで旧内容が残る場合はETag/再検証等を設ける。認証・認可は従来どおり維持し、内部キーやGCS保存先を団員画面へ出さない。

## 8. 認証・所有者・履歴・経過時間

### R07 更新版と未来値

DBロック取得後の現在時刻と、DBにある正規化済み前回updated_atを使う。正常値では `max(DB現在時刻, 前回値+1µs)` で単調増加させる。同じマイクロ秒での連続更新を識別するための微小差であり、業務上の予定日時にこの処理を適用しない。

前回値がDB現在時刻より5秒を超えて未来なら異常とし、通常更新を止める。5秒は本仕様の設計値であり、実環境で検証済みの時計差ではない。9時間誤差を吸収するために閾値を広げない。反映前に実精度・正常な連続更新・時計差を検証し、変更が必要なら根拠と試験を仕様へ反映する。created_atの識別用値をこの規則で補正しない。

異常は管理者が対象・理由を調査できる形で記録し、利用者へは保存できない旨を表示する。根拠なく9時間を引く、現在値で置換する、将来値へ加算し続ける処理は禁止する。

### R08 認証・所有者の保護

members.created_at等の識別用日時は通常修正で瞬間を変えない。ownerId、memberBirthToken、履歴、同意、削除世代、宣伝のactor/操作識別が表記変更で変わらないことを確認する。署名・操作ハッシュ対象のUTC表記は既存の正規形を維持する。

認証のDB直接参照方針を維持する。最終確認更新で認証日時や権限を古い値へ巻き戻さない。通常セッション、DB書込み失敗時の既存フォールバック、一覧への統合を同じ日時契約で処理する。naiveとawareの比較による例外を防ぐ。

authenticated_atは表示専用ではない。tuner_service.resolve_ownerとmetronome_service.resolve_ownerはauthenticated_at（既存の代替は端末created_at）をmembers.created_at/member_birthと比較し、旧会員世代のセッションを拒否する。この比較・代替規則を弱めず、値の瞬間・精度を保持する。旧形式、両方の欠落/不正、同じIDでの会員再作成、再ログインと最終確認の並行時をT13/T24で検証する。last_seen_atを認証世代の代替値にしない。

フォールバックの8時間等の既存寿命を9時間変えない。プロセス内TTLは適切な単調時計または統一したaware時計で一貫させ、保存する業務日時と経過時間を分ける。未確定な認証値を推測して認証成功にしない。新たな認証迂回やフォールバックの恒久化は行わない。

識別用日時自体が誤保存されていた場合は専用移行とする。履歴所有者・操作キー・参照・認証状態の対応と切り戻しを定義できるまで補正しない。データ補正を契機に旧履歴を別世代会員へ渡さない。

AudioContext.currentTime、performance.now、epoch、音声スケジューラ、同期エクスポート、保存ハッシュの単位・意味を維持する。UTC文字列やDate.nowを一括置換しない。

## 9. キャッシュ・外部契約・互換性

### R09 表現版とデータ版

メモリーキャッシュ、IndexedDB、インフライト要求、HTTP/ETag、bootstrap、遅延読込みスクリプト、実際に使うPWAキャッシュを棚卸しする。表現変更をETag等へ反映し、旧ペイロードに304を返して再利用させない。元データの更新日時を変えることでETagを無理に更新しない。

新しい日時表現のキャッシュ版/名前空間を設けるか、対象エントリを確実に再検証する。旧版で開始した要求が切替後に到着しても新キャッシュへ混入させない。形式変更のためにチューナー/メトロノームのオフライン履歴や未同期操作を全消去しない。DBスキーマ変更は既存IndexedDB移行と複数タブのblocked/versionchangeを考慮する。

共有オブジェクトの直接変換は禁止。通常はコピーを正規化して返す。認証・期限・競合の最終判断に古い端末キャッシュを使わない。別インスタンスの更新後に古い一覧を返す問題を、表示の形式統一だけで解決済みとしない。

バックエンドのコレクションデータ、ETag、検索索引、get/set/clear/invalidateはすべて検証済みtenant contextを含むキーへ統一する。当該テナントの無効化で別テナントを巻き込まない。全テナント消去が必要な起動/運用経路は明示的に分離する。HTTPのテナント指定は利用者の権限の証明ではなく、認証・認可と整合させる。DBのテナント数が1であることや保存後のclearだけで、読込キャッシュの越境防止を満たしたとしない。

ICSのDTSTAMPは既存UTC、予定はAsia/Tokyo、終日は日付という契約を維持する。GCSメタデータ、署名URL、有効期限、外部API、リリース時刻、履歴export等は契約を個別確認する。表示はJST化しても、外部形式を無条件に+09:00へ変更しない。

現行公開関数・UIイベント・分割ロード順・portalAppStateを維持する。テスト専用コピーだけを修正せず本番読込み経路を修正する。tuner/metronomeを変更する場合は既存リリース生成・整合性チェックを実施する。

## 10. 旧データの解釈・復旧

### R10 旧値の扱い

| 状態 | 処置 |
|---|---|
| 正しいDBの瞬間 | 値を維持し、返却・表示を修正 |
| 時間帯付き文字列 | 同じ瞬間・精度を保持して正規化 |
| 生成元が確定した時間帯なし値 | 項目別codecで解釈 |
| 生成元不明 | 自動補正せず要確認。表示は日時不明、重要更新/認証は安全側で処理 |
| 誤った瞬間が証明された値 | 対象・期間・依存を限定して補正 |
| 日付を日時として保存した値 | 当時の入力規則から元の暦日を復元 |
| 識別用日時 | 通常補正から除外し専用移行 |

読み取り専用の事前照合で、稼働リビジョン、アプリとDBセッションの時間帯、列型/精度、実際のAPI値、操作したJST、DBの瞬間を対応させる。現在の環境設定だけで過去の生成元を断定しない。既知の操作記録等で裏付ける。一律±9時間補正は禁止。

バックアップ、対象のテナント/キー/旧値/新値/根拠/依存/件数、ドライラン差分を用意する。実補正は想定した旧値がまだ一致する場合だけ適用し、不一致は停止・再調査する。移行記録/形式版を保持し、再実行で二重変換しない。競合トークン・ETagへの影響、開いた画面からの要求への応答も定義する。

表示の正規化だけでcreated_at/updated_atを更新しない。真のデータ補正の場合は、通常業務更新時刻と移行監査記録の区別を明示する。切り戻しも変更後の値が一致する場合だけ行い、後続の正常更新を上書きしない。

## 11. 反映・切り戻し

### R11 反映条件

| 区分 | 順序と条件 |
|---|---|
| 補正不要 | 互換性・受入試験後にコード反映 |
| 新コードが旧値を安全に扱える | 互換コード/必要な追加スキーマ→切替→補正→後方互換整理 |
| 先行補正が必要 | 書込み停止または保護手順と旧新コード互換性を確定し、移行計画に従う |
| 重要な解釈/識別依存が未確定 | その影響範囲の反映を開始しない |

全体工程を一律「コード先行」としない。移行中の読み書き、複数Cloud Runリビジョン、旧タブ、オフライン復帰を含む組み合わせ表を作り、対応しない組合せは実際に流入させない。非互換の旧書込み側が新ファイル参照や形式を壊す場合は、トラフィック切替だけで済ませず旧書込み停止等を組み込む。

互換期間と旧画面への再読み込み案内を定義する。非冪等な旧要求の自動再送や、オフライン未同期データの破棄で移行を済ませない。既存の冪等キーは維持し、必要な新規操作状態照会は関連する変更APIに限定して設計する。

DBの追加列・参照表等はexpand→移行→検証の順とし、旧コードが新値/新参照を安全に扱えるかを確認する。戻せない場合は旧コードへの切り戻しを選ばず、安全な修正版への前進復旧を用意する。バックアップがあるだけでオンライン切り戻し可能とみなさない。

TEST、本番は既存運用チェックリストに従う。TESTデプロイに伴う保留マイグレーションの適用範囲も確認する。本書作成自体ではデプロイ、DB補正、実環境ファイル変更を実施しない。

既存manage_production_maintenance.pyは解除に宣伝リセットの完了runを要求し、旧revision復帰も拒否するため、今回の解除・切戻しへそのまま流用しない。無関係なリセットの実施や既存ガードの解除で代用しない。今回用のmanage_datetime_maintenance.pyを実装対象とし、対象service/DB・旧新revision/digest・traffic/tag・状態ファイルを照合する開始/確認/解除/条件付き復旧を定める。

停止後は旧request timeoutに基づくdrainに加え、DBの実行中TXとdeploy/sync/cleanup等のwriter停止を確認する。解除は候補revisionの通常エントリ、DB/スキーマ・移行状態、health等の照合後に行い、解除確認失敗時はmaintenanceへ戻す。TESTで解除と障害復旧を検証するまで本番で使用しない。

非互換な保存方式・アセット移行の途中を一般利用へ開放しない。必要な追加スキーマは先行可能だが、行単位化・操作方式・根拠付き参照移行が揃うまでメンテナンスを維持する。新参照/操作結果を利用した後は旧コードへの復帰を許可せず前進復旧とする。ファイルの新規書込みを止めただけで旧コード互換が回復したと扱わない。

### 公式仕様（2026-10-19参照）

- [Python 3.10 datetime](https://docs.python.org/3.10/library/datetime.html): aware/naiveの区別、明示的な時間帯を伴う生成・変換。
- [PostgreSQL Date/Time Types](https://www.postgresql.org/docs/17/datatype-datetime.html): TIMESTAMPTZは瞬間を保持し、入力の元時間帯は保持しない。実稼働DBのバージョンは別途照合する。
- [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html): ロックの範囲、競合とデッドロック。実装のロック粒度は全書込み経路で検証する。
- [Intl.DateTimeFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat): 表示時間帯の明示指定。
- [Cloud Storage Request Preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions): 作成・削除の世代条件。DB参照の正しさは別途保証する。
