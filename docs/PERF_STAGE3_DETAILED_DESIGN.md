## 3. バージョンと世代のデータモデル

追加名は既存マイグレーションとの衝突検査後に確定する。番号は実装時に次の未使用番号を採番し、ここでは固定しない。

| 表（設計名） | キーと列 | 意味 |
|---|---|---|
| portal_data_generation | singleton SMALLINT PK=1、generation UUID NOT NULL、updated_at TIMESTAMPTZ | 環境固有の世代。復元・同期・異常回復で更新 |
| portal_collection_versions | organization_id TEXT、collection_name TEXTの複合PK、version BIGINT NOT NULL CHECK(version>0)、updated_at TIMESTAMPTZ | 団体×集合の単調増加番号 |

版は時刻・xmin・最大IDから導かない。初回INSERTで1、以後同じトランザクションで`version=version+1`。番号は連続性を要求せず、確定した変更の前後で必ず異なることを要求する。ロールバックした更新は番号も戻る。BIGINT溢れは例外として止め、0や循環値に戻さない。

環境世代は本番からTESTへコピーして流用しない。アプリ起動ごとのランダム値でもない。複数インスタンスが同じDBの同じ値を読む。世代・版は毎要求DBから読む。プロセス内TTLで省略しない。

既存団体×対象集合には移行時に初期値を作る。新規・未知の団体に専用の作成経路があるとは仮定しない。必要版行がなければ、同じRRで対象集合の全依存表が空であることをSELECT EXISTSで確認した場合に限り、ETag上の版0として扱う。READ ONLY要求から版行をINSERTしない。最初の書込のトリガーが同じトランザクションで正の版を作り、版0からの変更を検知する。init-tenantは任意の保守用事前初期化であり通常利用の前提にしない。データがあるのに版行が欠ける場合は異常とし、既知の正の版から0への逆行も既存の検出・完全照合で扱う。削除済み団体の版行を再利用せず、団体再作成・全復元では世代を管理する。

ETagの依存集合には、DB集合以外にAPI_DATETIME_FORMAT_VERSION、エンドポイント、取得条件、Cloud Run revision等の本文に現れる値を含める。版定義自体の変更には固定の`clock_schema_version`を上げる。

## 4. 更新検知とトリガー

### 4.1 依存の生成と対象列

親集合30件と子7表の対応は`JSON_COLLECTION_TABLES`・`DB_CHILD_TABLES`・`DB_CHILD_PARENT_KEYS`から生成する。SQL生成・試験・調査用一覧を同じ生成元に揃え、別の手書き対応表を作らない。移行SQLはレビュー可能な固定成果物として出力し、CIで生成元との一致を検査する。

30＋7は棚卸し母集団で、全表へ最初からトリガーを付ける指示ではない。5.1の初回APIの依存閉包は9親集合（performances、schedules、announcements、events、members、payments、part_settings、org_settings、sns_settings）と子2表（performance_pieces、payment_performance_fees）、メニュー表の計12表。まずこの閉包を生成・検証する。残る表は対応APIを追加するときに対象化し、アクセスログやlast_seen_at等へ不要な版更新を増やさない。対象集合の全更新経路を捕捉する条件は緩めない。

`menu_visibility_settings`→メニュー版は追加定義とする。専用表・汎用JSON・設定値から本文へ入る依存は、実際の読取SQLから追加または対象外を明記する。楽譜・ファイル・プロモーションの専用操作状態を、そのまま汎用版へ置換しない。fullのno-store処理だけが読む表は、それだけを理由に早期304の対象にしない。

全対象表自身にNOT NULLのorganization_idを要求する。子のOLD/NEWから団体を得て、消えた親行へ照会しない。団体移動のUPDATEは旧・新両方を更新する。親子の団体一致と参照制約を検査し、適用時に列欠落・不一致があれば停止する。判定キャッシュは移行後の再起動で破棄する。新経路に列なしの互換分岐を持ち込まない。

### 4.2 発火方式

- INSERT、UPDATE、DELETEごとにAFTER STATEMENTトリガーを作り、遷移テーブルの対象団体をDISTINCTする。UPDATEはOLDとNEWの和集合。子表の変更は親集合の版へ反映する。
- 1 SQL文につき、影響した団体×集合を各1回更新する。対象行0件なら更新しない。値が同じUPDATEは安全側に更新してよい。本文比較をトリガーに追加しない。
- 版行のUPSERT順はorganization_id・collection_nameの固定順にする。複数文・カスケードをまたぐデッドロックを全廃できる保証ではなく、検出・ロールバックも試験する。
- ON CONFLICT、FKカスケード、複数の遷移集合に分かれる場合は実PostgreSQLで確認し、最終的に該当版が増えることを条件とする。発火回数を常にトランザクション1回とは規定しない。
- 一般アプリによるTRUNCATEは拒否する。TRUNCATEは遷移テーブルで捕捉できないので、専用文トリガーと権限の両方で扱う。承認済み保守のみ、対象の旧団体集合を取得し、全関連版と世代を更新してから検証する。

トリガー関数のDDL/DML権限は最小化する。アプリに版表の任意UPDATE/DELETEやトリガー無効化の権限を与えない。SECURITY DEFINERが必要なら固定search_path、完全修飾名、信頼できる所有者、PUBLIC実行権の制限をセットにする。session_replication_role変更、トリガー無効化、DDLでの置換は通常アプリに許可しない。

### 4.3 ロックと一括処理

同じ版行を更新する書込は確定まで直列化する。文レベルでもこの性質は残る。通常書込は既存`db_item_repository.LOCK_TIMEOUT = "5s"`を維持し、読取の1秒制限を一律に適用しない。専用書込・同期の既存制限も本変更で短縮しない。通常保存と一括登録・同期の競合を測り、保存待ち時間と失敗率を確認する。既存save_busyの形式と保存結果不明の扱いを維持し、非冪等保存を勝手に自動再送しない。

`executemany`の呼出しは実SQL文数で計数する。同期では8章の信頼済み同期モードを使える場合だけ版更新を省略する。通常の楽譜・アルバム登録では省略しない。同期スクリプトの集合SQL化は、計測でメンテナンス時間の問題が判明してから別に設計する。

| /api/schedules | 共有 | schedules。現行一覧はBaseRepository経由。private, no-cache |
| /api/announcements | 共有 | announcements。現行一覧はBaseRepository経由。private, no-cache |

| /api/member-introductions | 共有接続を先行 | 既存の専用本文ハッシュ・毎回再検証を維持。新版への早期304は別測定まで保留 |

対象は明示的なパス・メソッドの許可リスト。単に「GETだから」対象にしない。書込を伴う`GET /api/auth/devices/{id}`（最終利用時刻更新・期限切れ削除）はREAD ONLY対象外。auth、保存結果確認、promotions、楽譜専用API、ストリーミング・画像・録音・ZIP等も既存契約のまま。未対応extraを一括で対象にしない。

版に含める実集合は、liteがperformances/schedules/announcements/members/payments/part_settings/org_settings/sns_settingsとメニュー、coreがメニュー。子依存は4章の生成定義に従う。各一覧の画像URL正規化は現行値と表現ロジックに依存し、画像本体を取得しない。団員紹介はmembersの列限定SELECTを維持し、非公開列やbase64を全件取得する経路へ戻さない。

現在、上表の5一覧とcoreは認証必須ではない。これらに認証を新設しない。liteはOPTIONAL_DEVICE、団員紹介はREQUIRED_DEVICEという経路別の前処理を設定する。早期304ではFastAPIの通常ハンドラーを呼ばないため、前処理は既存の認証関数を明示的に呼び、同じ要求スコープに検証済み結果と取得元を記録する。200側の依存・lite処理はその同じ結果を使い、二重認証読取を防ぐ。任意認証の401/403を匿名にする現行分岐を維持する。新しい共通の認可規則を作らない。

代替認証fallback_auth_device、取得元不明、認証DBエラーが起きた要求では版による早期304・本文キャッシュ再利用を行わない。既存の代替認証の公開契約を一律に廃止しないが、DBトランザクションがabortしたまま本文を構築せず、正常なスナップショットを保証できなければ成功応答を返さない。監査の主体再利用は別途保留のままとする。

### 5.2 要求の処理順

1. 既存の入力形式検査、ヘッダー長・必須ヘッダーの有無など、DBを使わない検査を行う。認証必須の経路だけに必須検査を適用し、公開API・liteの任意認証を必須化しない。
2. 待機開始時の単調時計から入場・接続待ち共通の2秒期限と読取全体の5秒期限を作り、プロセスの読取枠を待機取得する。入場期限内に取れなければ接続を借りず503を返す。
3. 入場・接続待ち共通期限の残り時間内で、共通プールから1本取得する。接続待ちに新たな2秒を与えない。autocommit=FalseでBEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY、時間制限をSET LOCALする。
4. 現行の認証依存処理・任意認証を、同じ接続で実行する。端末・団員・現在権限を要求ごとに読む。外部へ公開する認証結果の形式・副作用は変えない。
5. 同じ接続で環境世代・依存版を読む。版ETagが一致するなら、認証・認可を完了した後に304を返す。
6. 200の場合は同じスナップショットで本文を取得・構築・既存モデルでシリアライズする。旧メモリ本文を無条件に読まない。
7. トランザクション終了→接続返却→読取枠解放。例外・取消でも必ず行う。GZip・監査はこの後の既存の層で扱う。

認証も最初のデータSELECTから確定する同じスナップショットに含める。スナップショット前に確定した権限取消は反映し、進行中の要求へ遡及しない。認証結果を要求間でキャッシュしない。認証拒否は枠内で接続を使い得るが、容量拒否は使わない。この2種類の拒否を別に計数する。

### 5.3 接続の受渡し

既存`PortalCacheRoute.get_route_handler()`の外側に、許可リストの読取スコープを組み込む。FastAPIの依存処理より前に開始し、Responseのシリアライズ完了まで保持する。別の全要求ミドルウェアを増やさない。

設計上のReadContextはconnection、tenant、deadline、依存版、operation guardを持つ。要求スコープのContextVarで到達させ、読取用リポジトリに明示的なconnection引数を追加する。現在の公開関数の呼出互換性を維持する。認証端末・団員、JSON親子、RowStore一覧、メニュー、専用団員紹介の読取をこの接続へ渡す。

コンテキスト内でプールのgetconn、pooled_psycopg.connect、実psycopg.connectを追加で呼ぶことは禁止。SELECT用の明示的なヘルパーだけが既存接続を借用し、独自commit/rollback・autocommit切替・書込・FOR UPDATEは拒否する。単に接続アダプター全体を既存接続へ差し替えて書込まで通す実装にしない。

syncの依存処理はFastAPIのスレッドへContextVarが伝わることを試験する。プールの取得・BEGIN・終了等は既存のthreadpool経由でイベントループを塞がずに行う。接続の操作は直列とし、親のasync経路とsync依存が同時に使わないことをguardで検出する。子タスクへの伝播だけを根拠にasyncio.gatherで同時SQLを実行しない。取消時も実行中の同期操作が止まる前に接続を返却しない。

現行asyncサービス内の同期DB処理と監査の同期処理が自動的に非同期化されるわけではない。イベントループ停止を別計測し、必要なら対象サービス単位でワーカーへ移す設計を追加する。別イベントループを作ってFastAPIハンドラー全体を移す方式は採用しない。

## 6. 容量制御と接続予算

| 設計値 | 値・適用 |
|---|---|
| 読取枠 | 4処理/プロセス。認証を含む要求全体 |
| 共通プール | 最大5/プロセスを維持。増設で問題を隠さない |
| 入場・接続待ち | 合計で最大2秒。枠の待機開始から共通の期限を使う |
| getconn待ち | 入場・接続待ち共通期限の残り時間内で最大2秒。呼出元の指定が大きくても超えない |
| 読取lock_timeout | 最大1秒。全体予算の残り時間が短ければその値 |
| 書込lock_timeout | 通常書込の既存5秒を維持。読取の1秒を一律適用しない |
| 読取statement_timeout | 1文あたり最大3秒、要求の残り時間が短ければその値 |
| 読取処理の全体予算 | 入場待ち開始からシリアライズまで5秒。待機も含めSQLごとに残予算を反映し、本文構築の境界でも検査 |
| Retry-After | 容量拒否は2秒 |

全体予算はSQLの3秒を呼出数だけ繰り返してよい意味ではない。入場待ち開始をt0とし、入場・接続待ち期限はt0+2秒、全体期限はt0+5秒とする。例えば入場に1.5秒使ったら、getconnに使えるのは最大0.5秒で、取得後の全体予算も更新しない。接続待ちの期限切れでは取得済み枠を解放する。入場待ちの間は接続を保持せず、イベントループも共有ワーカースレッドも占有しない。1プロセス1イベントループを前提にasyncio.BoundedSemaphoreとasyncio.wait_forで残時間内を待ち、キャンセルは待機を取り消す。41件・80件を同時投入し、既定40ワーカーを枠待ちが使い切らず、入場済み要求のDB処理と他APIの同期処理が進むことを確認する。試験で複数のイベントループを作る場合は、そのループに結び付いた待機枠を使い、終了済みループのSemaphoreを再利用しない。

5秒は処理を継続する上限であり、取消・接続回復を含む厳密な応答時間の保証ではない。タイムアウト後は部分本文を成功として返さない。pool待ち・処理予算の不足は既存形式の503 `{"detail":{"code":"read_capacity_exceeded","message":"現在、処理が混み合っています。時間をおいて再試行してください。"}}`と`Retry-After: 2`、no-storeとする。version_clock_anomalyとメンテナンスとは区別する。プール接続待ちでの拒否は貸出成功0回、入場待ちでの拒否はgetconn呼出自体0回として区別する。接続取得後の全体期限超過は、これらの入場・接続容量拒否とは別に計数し、接続0回とは扱わない。

Webアプリのlifespan開始からclose完了までpoolを必須とし、準備前・取得失敗・DSN不一致・未対応kwargsで直接接続へ切り替えない。読取コンテキストもlifespanの有無にかかわらずpoolを必須とする。cursorのrow_factory等は取得した接続・cursorで適用する。一方、mainのimportだけではWeb稼働とみなさず、単独の保守スクリプトはAPP_ENVがproduction/testかつDB Onlyでも従来の直接接続を使える。Web稼働の明示的スコープで分離し、環境変数やローカルJSONへの切替で代用しない。起動順はpool準備→自己点検のまま。宣伝リセット・楽譜回収のdry-runをDBモード/プールなしで試験する。

設定確認済みのCloud Runは両環境とも同時実行80、最大3インスタンス、workers指定なし。プロセス数WはTESTで実測して確定する。接続予算は`各稼働リビジョンのインスタンス数×W×5`の総和に、移行・同期・運用接続を加える。監査・通常書込はこの5に含め二重計上しない。単一ワーカー・単一リビジョンの設定上の上限は各環境15、本番＋TESTで30だが、ロールアウト並行稼働・DB共有先・外部プーラー・他アプリを含む保証値ではない。

読取4は「監査・保存に常時1本予約」ではない。書込等も同じプールを利用する。DB max_connectionsと他利用・運用余力を確認して接続予算を承認する。Cloud Runの同時実行80の変更は本書で自動実施せず、拒否率・待ち時間の測定から別途判断する。

## 7. ETag・本文キャッシュ・異常検出

### 7.1 新しい版の優先順位

DBモードかつ新経路有効時は、認証→環境世代/DB版→ETag→本文の順。現在のxmin集約、メモリETag優先へのフォールバック、互換check_etagを新経路で使わない。ローカルJSONモードは独立して維持する。

ETagは`clock-v1`名前空間、環境世代、clock_schema_version、団体、endpoint、意味を保った取得条件、表現版、本文が依存する主体情報、依存集合と版のソート済み組からSHA-256で作る弱いETagとする。認証で本文が変わる経路は、端末ID・団員IDだけでなく現在の名前・権限値等も含める。公開経路は新たな認証を行わず、従来の利用者識別ヘッダーと公開表現の区分を維持する。秘匿トークンは入れない。全パラメーターを落として同一キーにしない。

デプロイrevisionは本文にcloudRunRevisionが現れるbootstrap-lite/coreだけに含め、5一覧と団員紹介には含めない。本文・依存版・表現版が同じ一覧はデプロイだけではETagを変えない。本文の変換規則を変更するときは該当する表現版を更新し、revisionをその代用にしない。

liteの本人会計は現在の名前照合を含むため、その主体値とmembers/paymentsの版を対象に含める。匿名/認証済み/権限別の表現を共有しない。coreは不要な全集合を読まず、メニュー版・revision等の実依存だけを使う。UI項目の削減は行わない。

If-None-Matchは既存http_cache.etag_matchesを利用し、弱い比較、複数値、`*`を維持する。認証・認可前に304を返さない。200/304の`private, no-cache`、Vary（Device/Organization/TenantとGZip側のAccept-Encoding）を維持する。圧縮前の同じ表現の版で判定する。旧JSが保持する旧ETagは初回200で更新され、本文形式は変わらない。

### 7.2 本文とメモリ

最初の有効化では早期304を優先し、200は同じスナップショットのDBから構築する。`json_collection_service`の通常メモリ先行読取はReadContext内で迂回する。新しい汎用応答キャッシュは新設しない。

既存メモリキャッシュを再利用する対象は、環境世代・団体・集合版・表現版のタグを付け、その全一致を同一要求のDB読取で確認できた場合だけに限定する。タグなしの旧エントリーは不採用。応答の可変listを他要求が更新できる形で共有しない。依存表や生成設定までタグに表現できない対象はキャッシュ再利用を有効化せず、DBから読む。キャッシュ更新失敗は200を失敗にしないが、未検証の旧値へ戻らない。

版が同じでも別スナップショットで本文を構築する方式は採用しない。RRを採用しているので本文後の版再確認による再試行は基本不要。トランザクション終了後に追加SQLを行ってETagを作り直さない。

### 7.3 異常と完全ダイジェスト

世代行の欠落、非空集合の版欠落、同じ世代で観測した番号の逆行、依存定義不備、ダイジェストの矛盾は、既存`version_clock_anomaly`の503・detail.code/message形式を維持し、安全に停止する。読取経路だけはmessageを「データを確認できませんでした。管理者に連絡してください」とする。保存経路の既存文言「保存できませんでした。管理者に連絡してください」は変更しない。読取例外の変換箇所で文言を選び、既存の全体例外ハンドラーを一律に書き換えない。

この読取用案内はPERF-R29の明示的な許容差分として9.3に列挙する。既存の警告表示を使い、新しいUIを作らない。同じcodeの再試行禁止・残り時間を付けない制御は維持する。DB障害時にメモリETag・本番JSONへ戻らない。

管理者向けの完全ダイジェスト照合をCLI/運用手順として残す。新しい公開診断APIを作らない。導入時、保守・復元・同期後、導入後のTESTでは日次に実施する。同じRRで版と対象親子の全データを読み、版行/実データのどちらかに現れる団体とdefaultについて全依存集合を照合し、空集合の欠落版は0として正規化する。非空の版欠落は停止する。PKで順序を固定し、日時・NULL等を正規化してハッシュ化する。xminではなく内容を照合する。最後の`(世代,団体,集合,版,内容hash)`を制限された運用記録へ残し、同じ版でhashが変わったら異常とする。

初回のhashだけで過去の取りこぼしを証明できるとは扱わない。直接SQL・トリガー無効化の権限点検、日次検査の成否監視を併用する。矛盾発見時は当該新経路を止め、原因修正・世代再発行・全照合後に再開する。ダイジェスト本体や個人データをログへ出さない。

## 8. 同期・復元・保守

通常同期はUPSERTと不要行DELETEであり、pg_restoreとは分ける。同期対象・除外表は既存スクリプトの定数から取得する。新版管理表を本番からTESTへ複製しない。取得元0件の全DELETEも同期モードの対象とする。

信頼済み同期接続に限り、autocommit=Falseのトランザクション内で`SET LOCAL app.portal_sync_mode='on'`を設定できる。トリガーは設定値だけでなく専用の信頼ロールへのsession_userの所属を確認した場合だけ早期returnする。アプリから同じSETを送っても省略できないことを試験する。許可する実ロール名は実接続調査後に運用表へ固定する。ロール新設・Secret移行の全面設計は別変更。

現在の同期ロールを証明できない間は、版更新省略を無効にしたまま通常トリガーで同期する。最終の世代更新は省略しない。これにより同期高速化は保留できるが、誤ったキャッシュのまま公開することは許さない。アプリに保守権限を付けて解決しない。

手順は、TESTへの書込を停止・排出→バックアップ→DB同期→GCS同期→トリガーの存在・有効性/依存/データ整合性を検証→TEST版を更新し新UUID世代を確定→完全ダイジェスト照合→メンテナンス解除とする。DBだけ成功・GCS失敗なら解除せず、gcs_only再開後も最後の検証・世代発行を行う。最終更新失敗も解除しない。旧プロセスのキャッシュは次のDB世代照合で不採用となる。

同期のアルバム削除では通常の7日物理回収候補を作らない。この条件は将来のPERF-R15ガードとの接続契約。物理回収は別段階であり、アプリ・同期のロール分離を保証できなければ有効化しない。

pg_restoreや手動復元、トリガーを扱う保守は、復元された版・世代をそのまま公開せず、トリガー検査と新世代発行を必須にする。SET LOCALはトランザクション外で使わず、プール返却後に他要求へ同期・保守設定が漏れないことを試験する。

TEST架空データは同期で消え得る。測定fixtureは同期対象外のソース管理された定義を保持する。隔離DBを第一選択とし、TESTを使う場合は同期後に再投入し世代・計測の基準を再作成する。実データを試験成果物へコピーしない。

## 9. 計測・試験・受入条件

### 9.1 修正前の固定

標準架空データは団員100、予定200、出欠5,000、イベント20と回答1,000、アルバム20と写真500。2倍量も用意する。演奏会等は第2段階CDEのfixture値を引き継ぎ、異なる値へ変更する場合は比較を取り直す。最初の変更より前に3Aで採取する。

操作は初回lite/core、各一覧、同じETagでの再取得、別インスタンスで保存後の再取得、権限取消、直接SQL、旧版と新版並行保存、一括登録と読取の競合、同期・復元後の再取得。HAR/Playwrightで200/304・転送量、サーバーでSQL実行数・時間、getconn待ち・保持時間、版行lock待ち、容量拒否、認証拒否、実プロセス数を記録する。対象処理のDB checkout数は認証を含めて測る。

監査は主体取得とINSERTのcheckout回数・pool待ち・SQL時間・イベントループ停止時間を分離する。同じ最大5接続内の利用として集計する。書込トリガー実行時間、版行競合、日次ダイジェスト負荷も測定する。4.2の保守的な版更新は、トリガー内に本文比較を持ち込まないための選択であり、合意した不要な更新の削減を達成済みとは扱わない。値が同じUPDATE・表現に影響しない変更の文数、版更新数、結果として304を失う追加200件数・転送量を測る。追加200が問題となる対象は有効化を保留し、対象列の比較方式を別途確定する。モックのSQL計数を実DB性能として報告しない。

### 9.3 各段階の合格判定

正しさの必須条件は全件合格。3Dの304は認証と版照会を除く本文用SELECT・xmin全件集約・本文シリアライズを0とする。200は修正前と同じ正規化本文で、版と同一スナップショット。3Bは同時書込のlock待ち・保存失敗、3Cは接続保持・拒否率・監査待ち、3DはSQL数・転送量・p50/p95を比較する。

性能の許容差は3Aの修正前分布から、対象ごとに絶対値と割合を記載して有効化前に固定する。都合のよい実行だけを選ばず同一環境で最低5回の比較を残す。未測定の基準値を達成済みと扱わない。保存失敗・権限混入・本文不一致・無期限待ちは計測値にかかわらず不合格。

3Dの有効化はAPI別に判断する。bootstrap-liteではxmin集約・接続貸出と本文構築の削減を比較する。5一覧は現行warm304のSQLが0なので、SQLの増加を自動的な改善とは扱わない。別インスタンスで確定した変更を検知する正しさと、本文構築の削減を、追加のSQL・接続保持・遅延と併記して説明できる場合だけ有効化する。説明できない一覧はその一覧だけを保留する。正しさを犠牲にして旧メモリだけで判定することを代替案にしない。

各APIで本文メモリあり/なしを両方測る。TESTの設定上の最大数だけから頻度を仮定せず、採取時の実際の稼働インスタンス数・リビジョン数、匿名化したインスタンス識別、採取期間、対象要求数と本文キャッシュhit/missを記録し、状態別の発生頻度を算出する。最大3だから1/3ずつに分かれるとは扱わない。取得できない場合は頻度未測定と明記し、重み付けした実環境効果は未確定とする。

PERF-R29: 同一Linux CI/同一Playwright WebKit・フォント・データ・固定時刻で主要団員/管理画面の画像とDOMを比較する。項目・順序・ボタン配置は維持する。JST日付変更は偽タイマーの位相を変え、日付変更後最大30秒以内の更新を維持する。実iPhone/BFCacheの結果はエミュレーションと分ける。

| 第3段階で追加する許容差分 | 検証 |
|---|---|
| 読取時のversion_clock_anomalyだけ、既存警告内に「データを確認できませんでした。管理者に連絡してください」と表示 | 実文言をS3-15で確認。保存の文言・レイアウト・再試行禁止は変更しない |

書込待ちの短縮や即時入場拒否は採用しないため、それらによるsave_busy・503増加を許容差分へ追加しない。第2段階までの既存許容一覧は維持する。

実装時の最終確認はcompileall、ruff、pytest、frontend syntax、frontend全件、Playwright全e2eを含める。文書作成だけの今回、その実装試験を実行済みとは記載しない。

## 10. 移行とロールバック

移行は次の順を変更しない。

1. 実DB事前検査、バックアップ、依存生成物を確認し、追加表・トリガーを適用する。既存行の初期化とトリガーの間に未捕捉書込を許さない。短いメンテナンス/書込排出とトランザクションで整える。全件を長時間ロックする場合は事前に所要時間を測る。
2. 初期値、空集合、団体・親子、トリガー有効性・権限・完全ダイジェストを検証する。
3. 読取は旧版のまま、旧アプリの保存・直接SQLで版が増えること、保存待ち時間を検証する。
4. TESTの対象ごとに整合読取、次に新ETagを有効化する。本番は同じ検証を経て段階的に有効化する。

切替は既存の環境変数を読み込む設定方式を使い、ReadContextと版ETagの有効対象を環境別に独立して指定できるようにする。未指定は未有効、版ETagだけの有効化は拒否する。必要な環境変数名は実装時に既存名との衝突を検査して固定する。新しい運用フラグ基盤・管理画面・設定DBは作らない。早期304だけを戻す場合は同一RRで最新本文を読み、既存本文ハッシュで判定する。未検証の旧メモリへ自動復帰しない。新版アプリ全体を戻す際は既存方式の制限を運用記録に残し、トリガー・版表を保持する。DDLを即削除しない。

番号が正常な限り、通常ロールバックだけで世代を毎回更新する必要はない。復元、番号の巻戻し、トリガー欠落期間、依存定義変更等があった場合は、原因解消後に世代再発行・全照合を行う。再デプロイで取りこぼしが再発しないことをS3-03で確認する。

将来の第4段階を旧版へ戻す場合は、回収ワーカーを停止し削除ガードを維持する。旧版へトラフィックを戻して削除を再開しない。この既存条件を第3段階の戻し方で緩めない。
