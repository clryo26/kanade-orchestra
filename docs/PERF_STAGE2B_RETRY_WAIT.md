# 第2段階B 手動再試行・要求単位の待機 実装記録 v1.1

2026-10-22。基準は仕様v1.6・第2段階詳細設計v1.3、修正前はcc61c61。通信・認証・HTTPキャッシュの承認済み部分を保ち、PERF-R02の残実装を追加した。DB、HTTP応答形式、画面要素・配置は変更していない。前後の数値とソースの識別は[比較記録](PERF_STAGE2B_RETRY_WAIT_20261022.json)に保存する。

## 対象と規則

既存の`fetchWithTimeout`のGET再試行層を拡張する。すべての503で、同じ要求にメモリ上の手動10秒の待機状態を持つ。Retry-Afterの有無で手動の規則を狭めない。

- 手動: 最後の503から10秒未満は送信せず、既存のshowAlertで残秒数を伝える。10秒後はサーバーが300秒を指定していても、終了を確認する取得を許可する。連打で期限を延長しない。許可された取得はネットワーク待ちに入る前に枠を予約する。
- 自動: 有効な正の秒数のRetry-Afterがある場合は、その期限まで送信しない。ユーザーの操作から始まった結果確認のポーリングも自動に分類する。待機中に長いタイマーを作って画面を止める方式にはしない。
- 同じ要求の実際の200/304成功で、その待機だけを解除する。遅れて届いた成功で、より新しい503の待機を消さない。キャッシュを読んだだけでは解除しない。
- ログイン開始・解除・ログアウト・認証関連storageイベントと利用者/認証世代の変更で待機を解除する。保存成功時はmutationRelatedCacheKeysの対象だけを解除し、portalResponseEpochの変更を理由に無関係な待機を解除しない。古い認証コンテキストの503を、新しい利用者の待機として登録しない。
- 不正・日時形式・0秒のRetry-Afterでは、サーバー待機期間を新設しない。既存の503分類とジッター付き再試行の規則を維持する。未知503の同じ論理要求内での自動再試行は従来どおり最大1回で、1,500msを超えるRetry-Afterでは直ちに応答を返す。
- version_clock_anomalyは一時的な混雑にしない。自動再試行を行わず、元の管理者向けメッセージを保持する。手動の連打には他の503と同じ10秒間隔を適用し、抑止中も管理者向けメッセージを案内に残す。
- POST/PUT/DELETE等はこの待機制御の対象外。保存本体を自動再送せず、結果不明の操作IDも作り直さない。

キーはportalCacheIdentity（表現版・端末・利用者・権限・認証世代）、ローカル認証遷移、URLのクエリを含む全体、強制更新の有無、credentials、取得ヘッダーから作る。ヘッダー名の大文字小文字と並びは正規化する。異なる団体ヘッダー等は別の待機となる。自動付与するIf-None-Matchと現在の端末IDの重複は除く。既存GET集約のキーは変更していない。

共有するのは待機情報と503応答のコピーだけで、アプリの成功データを待機用キャッシュにしない。待機中の応答も元の503・detail.code/message・Retry-Afterを維持し、Pの_structuredResultの3項目も変えない。内部のportalRetryWaitはHTTP本文に追加しない。IndexedDBの読込結果で503を成功に見せず、抑止をネットワーク例外の代替表示にも入れない。

状態はページ内のメモリだけに置く。新しいIndexedDB・ストア・Service Workerキャッシュ・永続形式は作らない。期限切れは次回参照時に除く。通信は既存のタイムアウト・一時的追加2回・別枠の401後再送1回・認証確認の別予算を維持する。

## 起点の扱い

内部プロパティ`_requestOrigin: 'automatic'`を起動・復帰・背景取得・ポーリングから明示的に渡す。既存の操作用API呼出しは既定で手動とする。グローバルな「ユーザー操作中」フラグやnavigator.userActivationから推測しない。プロパティは既存の一覧でfetch()の直前に除去し、呼出元のoptionsを書き換えない。

| 経路 | 分類 |
|---|---|
| タブ/メニューの押し直し、既存の更新/再試行ボタン、操作結果確認 | 手動。専用の再試行ボタンだけに限定しない |
| 初期起動の認証・enterPortal・ログイン画面用データ | automaticを渡す。既存の起動再試行ボタンは手動 |
| visibilitychange/pageshow/onlineからの認証・essential再取得 | automaticを渡す |
| bootstrap-coreの背景取得、起動後の出欠データ取得 | automaticを渡す |
| ホームの描画から派生するお知らせ取得 | 既定automatic。ホームタブの選択と履歴操作は手動 |
| プロモーションの6回の結果確認ループ | automaticを渡す。待機中は照会も警告の繰返しも省く。手動の状態確認とは分ける |
| portalFileOperationsResumeのactor確認 | automatic。利用者による保存前の確認・操作結果確認は手動 |
| 環境メニューの可否確認 | システム画面を開く操作からだけ呼ばれるため手動。単に補助的な確認であることを理由に自動へ変えない |
| 楽譜API | 呼出元の指定を401後へも引継ぐ。ZIPの繰返しstepやアップロード再確認はPOSTなので新しいGET待機制御に統合しない |

native fetchのリビジョン確認、GCSへのPUT、静的ファイル/AudioWorklet、チューナー・メトロノーム独自の通信は共通GET層へ移していない。

## 待機中の表示

全件が待機で抑止されたloadExtraDataは、読み込み済み扱いにせず、データ・DOM・入力・File・スクロールを維持して再描画前に戻る。一部の取得に成功した場合の既存の描画は変更しない。宣伝の同時再読込でloadStateがloadingのまま残ることも防ぐ。

団員紹介、通知設定、環境管理のように通信前に表示を消す経路は、同じ認証コンテキストの表示を確認したうえで保持する。別の利用者の表示を保持する条件にはしない。環境管理の一つのAPIが待機していても、別URLの履歴取得は止めない。

警告は既存のshowAlertのみ。「メンテナンス中です。あとN秒後に再試行できます。」等の文言を使い、新しい画面部品を作らない。起動・復帰で待機を判別できる場合は通信障害という案内に置き換えない。元の503本文・秒数や運用情報の非公開方針は変更しない。

## eed6a6eレビュー後の補正（2026-10-22）

仕様を狭めず、Retry-AfterのないHTMLの503、不正・日時形式・0秒のRetry-Afterにも手動10秒制御を適用した。自動の待機期限はこれらから新設しない。同じ論理要求内の未知503のジッター付き追加送信は最大1回のまま、論理要求全体の予算も変更しない。

保存成功時は、既存のinvalidateCacheForMutationから同じ対象キーの待機だけを解除する。extraの個別更新では親コレクションの一覧URLも共通の対象に加えた（例: /api/extra/albums/5 → /api/extra/albums）。これによりキャッシュの古い一覧も削除される。これは棚卸しで記録したextraの一覧無効化不足の、この対象決定に必要な補正であり、描画処理や全48箇所の取得起点の変更は行わない。対象パスのクエリ・強制更新・ヘッダーの各待機も解除し、他のコレクションの待機は残す。保存失敗では解除しない。

保存前から進行中の関連GETも識別し、その古い503で待機を再登録しない。対象外GETには影響させない。進行中の試行情報はfinallyで解放する。保存後の既存のorigin省略呼出しでも、待機警告を出さずに新しい一覧を取得できることを試験した。

最新確認: フロント全体**1,305件成功、失敗・保留0**、待機制御28件成功。全体実行後、試験に保存後の既定originとキャッシュ削除の検証を加え、28件を再実行して成功した。構文170ファイル、共有状態参照170ファイル/違反0、読込順index43/legacy70、node --check、ruff終了コード0、diff --checkを確認。バックエンドの変更はなく、今回バックエンド試験は再実行していない。
