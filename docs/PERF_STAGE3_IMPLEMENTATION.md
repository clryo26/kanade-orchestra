## 版管理とスキーマの前提

`collection_clock_schema.py`から対象閉包を定義し、既存の `JSON_COLLECTION_TABLES`、`DB_CHILD_TABLES`、`DB_CHILD_PARENT_KEYS`を参照して12物理表と親集合の対応を生成する。`generate_collection_clock_migration.py --check`で固定SQLと照合する。

023は2つの追加表と各表のINSERT/UPDATE/DELETEのAFTER STATEMENTトリガー、TRUNCATEガードを作る。初期化とトリガー設置は同じ移行トランザクション・書込排出で行う。遷移表から団体を集約し、UPDATEは旧・新双方、子の削除は子自身のOLDから版を更新する。0行なら増えず、rollbackで版も戻る。同値UPDATEは保守的に増える。一文のUPSERTでINSERT/UPDATE両方が発火し得るため、増分を常に1とは扱わない。executemanyは文数分発火する。

全対象表のNOT NULL organization_id、主キー、対象親子の参照制約と団体一致が前提。起動時にも有効トリガー・依存・ロール権限を検証する。データ不整合を要求時に修復しない。子を先に登録して親を後で補う通常書込は許可しない。

**隔離試験で判明した注意**: `ensure_db_schema_compatibility()`だけで作る会計子表には主キーがなく、対象2子表の参照制約もない。023はそのままでは停止する。試験fixtureでは専用DBにだけ主キー・FKを明示してから適用し、既存のマイグレーション全件試験にもその前提を追加した。これを実DBに存在する証拠と扱わない。実DBで欠落が分かった場合は、重複・NULL・孤立行を確認し、別の承認済み整備を先に行う。023が業務表の主キー・FKを自動追加することはない。

初期の団体×10集合を作る。新規/未知団体では、同じRRでその集合の親子依存表が空と確認できれば、欠落版を0として200/304を返す。読みながらINSERTしない。初回書込はトリガーで正の版を作る。init-tenantは任意の保守用初期化であり必須ではない。非空の欠落版は引き続き異常とし、完全ダイジェストでも同じ0正規化と非空検査を使う。移行SQLは未適用の今回のみ生成・変更し、適用後は023のchecksumを変更せず追加migrationで追従する。

## 接続・時間・認証

| 項目 | 実装値 |
|---|---|
| 読取枠 | 4 / プロセス |
| プール上限 | 既存5 / プロセス |
| 入場＋getconn | 待ち開始から合計2秒。入場1.5秒なら接続は残り0.5秒 |
| 読取全体 | 入場から5秒。取得後やSQLごとにリセットしない |
| SQL | 最大3秒か残時間。残りが短くなったときだけSETを短縮 |
| 読取ロック待ち | 最大1秒か残時間 |
| 通常書込のロック待ち | 既存5秒のまま |
| 容量拒否 | 503 / detail.code=read_capacity_exceeded / Retry-After: 2 / no-store |

DBを使わないヘッダー検査の後、枠取得→接続1本→REPEATABLE READ READ ONLY→認証→版→本文・モデル検証・JSON化の順。入場で拒否した要求は認証を含め接続0。認証で拒否した要求は認証のための1本を使う。この2種類を区別する。

認証の結果と例外はその要求内だけで共有する。スナップショット確立前に確定した取消を反映し、処理中の取消を実行中要求へ遡及させない。次の要求では再確認する。メモリ代替認証なら早期版304を使わず、旧本文メモリも使わない。

リポジトリは接続引数または明示的な読取借用を使う。スコープ内の別getconn、子async taskへの接続共有、並行利用、commit/rollback/autocommit変更、SQL書込、貸出終了後の接続・カーソル利用を禁止する。キャンセルでワーカーだけを置き去りにして接続を返却しない。SET LOCALはcommit/rollback後に漏れないことをアプリのアダプター経由で確認する。

新モードの起動時自己点検はDDLを行わない。スキーマは別のDDL所有者で適用済みである必要がある。通常アプリが所有者・保守グループ所属・superuser等の場合は版モードを起動しない。公開スキーマCREATEや業務表TRIGGER/TRUNCATE、版表DML権限も拒否する。

## HTTP契約と戻し方

版ETagは `clock-v1`、表現版、団体、パス・クエリ、デバイス区分、本文に依存する現在の主体、環境UUIDと依存版から作る。Cloud Run revisionは本文に現れるlite/coreだけ。将来表現・依存を変えるときはclock_schema_versionも更新する。

早期304は認証後。本文構築・xmin集約は行わない。200でも旧メモリ本文を混ぜず、同じ接続・スナップショットで構築する。Cache-Controlはprivate, no-cache、Varyは既存の3ヘッダーとAccept-Encodingを200/304で維持する。ETagはGZip前の表現に対する弱いvalidator。

版ETagだけ無効化したときもRR内の最新本文からハッシュを作る。旧メモリの版へ自動復帰しない。全アプリを旧版へ戻す場合も023の表・トリガーは残し、旧メモリ方式の制限を運用記録に残す。ロールバック後の再デプロイでも、旧版書込がトリガーで版に反映される。

世代欠落・非空の版欠落・逆行・照合不一致は既存形式のdetail.code=version_clock_anomaly。読取の案内だけ「データを確認できませんでした。管理者に連絡してください」。保存の既存文言・503待機・結果不明の扱いは変更しない。SQL timeout/lock待ちは破損扱いにせず容量503へ分類する。第3段階で許可した文言差分はこの読取異常だけ。

## 同期・復元・日次照合

専用の信頼グループ名は `portal_clock_maintainers`。作成・付与やSecretの変更は別の運用作業。SET LOCAL app.portal_sync_mode=onだけでは省略せず、実接続のsession_userがこのグループに属するときだけ省略する。アプリには付与しない。直接SQLでも同じ制約。

通常同期は既存のUPSERT/executemany/不要行DELETEを維持し、取得元0行のDELETEも同じ同期モードに入る。2版表は本番からコピーしない。信頼済みでない同期は版を通常どおり更新するが、最終の世代確定には保守権限が必須。

DB同期→GCS同期→トリガー/依存/データ検証→版とTEST固有UUIDを確定→完全内容照合→メンテナンス解除。gcs_onlyでも最終確定を省略しない。失敗時は解除しない。023未適用の環境だけ--allow-uninstalledで従来同期を継続できる。片方の版表だけがある不完全な状態は拒否する。

restore_db.pyは実行前後の版表を検査し、復元後に版が消えたら停止する。pg_restoreには--disable-triggersを加えない。版表がある場合は復元後にfinalizeを必須実行し、失敗時は完了と表示しない。復元用の実接続ロールも別途事前確認する。

`portal_collection_clocks.py`は暗黙のDB_URLを使わず、明示した環境変数・期待DB名・環境区分を要求する。preflight/checkはREAD ONLY、finalize/init-tenantは--executeと信頼ロールを要求。生データ・接続文字列を出力せず、前回の世代・版・内容hashと照合する。stateは正常COMMIT後だけ置換する。

導入時、同期・復元・保守後、TESTで日次に完全照合する。日次workflowは既定無効、前回成功artifactを復元して比較し、失敗時は前回を上書きしない。最初の成功を基準記録とする。artifact期限切れ・初期記録の扱いを運用で確認する。照合失敗時は対象の版ETagを無効化し、同一RR本文ハッシュに戻して調査する。
