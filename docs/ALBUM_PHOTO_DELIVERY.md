# アルバム写真の配信・登録情報の復旧

## 画像の取得

- 一覧の画像は `/api/albums/{album_id}/photos/{photo_id}/thumbnail` を遅延取得する。
- サムネイルは長辺384px以内、WebP品質65。撮影時のEXIFの向きを適用する。
- 写真を選択した時だけ既存の原画APIを取得し、閉じる時はビューアの画像参照を解放する。
- 写真IDがない旧形式でも、URLが既知のアルバム写真APIならサムネイルを取得する。それ以外のURLでは一覧に「選択して写真を表示」と出し、選択時だけ元のURLを取得する。任意のURLへ `/thumbnail` を付加したり、一覧で原画を取得したりしない。
- 既存写真のサムネイルは初回要求時にサーバー内で原画から生成し、GCS（ローカルモードではuploads）に保存する。ブラウザには縮小画像だけを返す。2回目以降は原画を読み直さない。
- キャッシュキーにはテナントと元ファイル参照・アップロード日時を含める。派生画像の形式変更時はキーのバージョンも変更する。
- 派生画像が残っていても、毎回DBの写真登録を確認する。削除済みの写真は取得不可。
- 生成できない画像に原画を返すフォールバックは設けない。原画は元のまま保持する。
- GCS通信には30秒のタイムアウトを設定。画像GETは同期ルートでワーカープールへ移し、縮小生成の同時処理数を制限する。
- DBモードのアルバム一覧はプロセスキャッシュを使わない。写真GETは対象アルバムだけをDBから読み、別インスタンスでの追加・削除も確認する。
- PillowはPython 3.10にも対応する12.3系を依存関係に追加した。

## 2026-10-19に確認した登録情報の欠落

本番・TESTともアルバム1（6/19作成）と2（9/6作成）のAPI写真件数が0、アルバム3（10/18作成）が8件。GCS原画はそれぞれ4・2・8件残っている。

旧処理はアルバム内の最大ID+1で写真を採番していた一方、DBのalbum_photos.idはテーブル全体で一意。バックアップでは6/19分にID 1～4、10/8バックアップでは6/19分の3・4と9/6分の1・2を確認。現在の1～8は10/18分に属し、1～4のcreated_atは過去の値を保持している。旧UPSERTによるID衝突・上書きと整合する。

現在のアップロード実装はDB全体のロック付き採番とUUIDのオブジェクト名に変更済み。登録情報の復旧は別途必要。

### 対象を限定した復旧

`scripts/repair_album_photo_metadata.py` はハッシュ固定した2つの既存バックアップからアルバム1・2の6件を合成する。実データ・秘密をソースに保存しない。

```powershell
# 既定は読み取り専用dry-run。pg_restore 18を指定する。
.venv/Scripts/python.exe scripts/repair_album_photo_metadata.py --service kanade-orchestra-test --pg-restore "C:/Program Files/PostgreSQL/18/bin/pg_restore.exe"
# 検証済みの計画を適用する場合は --execute を追加する。
# 本番は --service kanade-orchestra を指定する。
```

復旧元のハッシュ、件数、テナント、原画の存在を照合し、既存と異なる写真が対象アルバムにあれば停止する。適用時は現在の最大IDより大きいIDで不足分だけINSERTし、既存の全写真行が不変であることと復旧件数を同一トランザクション内で確認する。既存行・原画・シーケンスの置換や全DB復元は行わない。再実行は追加0件になる。

適用後は両環境のAPIで4・2・8件と全写真のHTTP 200を確認する。修正前の稼働中アプリの一覧キャッシュは自動失効しないため、DB復旧だけでは反映されない。ソースのデプロイ（新リビジョンへの切り替え）でキャッシュも更新する。新しいサムネイル機能の反映にもソースのデプロイが必要。

2026-10-19に本番・TESTとも上記6件をID 9～14で追加し、DB内で4・2・8件と既存行の不変を確認した。ソースは未デプロイ。稼働中TESTのAPIでは古い0・0・8件のキャッシュが残っており、画面での復旧確認と新しいサムネイルAPIの実環境確認は反映後に行う。
