### 2.2 音声取得から表示まで

```
マイク ─ getUserMedia（EC/NS/AGC を無効に要求）
  └ MediaStreamSource ─ AudioWorkletNode "portal-tuner-capture" ─ Gain(0) ─ destination
        └ 2,048 サンプルごと（48 kHz で 42.7 ms）に MessageChannel で Worker へ転送（主スレッドを通らない）
Worker: リングバッファー（容量 = max(YIN フレーム長, 16,384)）
  ├ 音程: 1/20 秒ごと（音声フレーム時刻で予定）→ {startFrame, endFrame, time=endFrame/sr, frequency, confidence, valid, reason, rmsDbfs}
  └ スペクトル: 1/10 秒ごと → {display(512点), harmonics(最大40), fundamental, axisId}
主スレッド: controller.onPitch → displayFilter.push（平滑化・ヒステリシス・保持）→ 30 fps 以下で描画
```

### 2.3 音程検出の条件（`pitch.js` の `frameGeometry` から計算）

| 項目 | 48 kHz | 44.1 kHz |
|---|---|---|
| 探索範囲 | 31～4,400 Hz（`minFrequency`・`maxFrequency`） | 同じ |
| 最大ラグ tauMax | 1,549 | 1,423 |
| 積分窓 W（= 1.5 × tauMax） | 2,324 | 2,135 |
| 1回の分析に使う長さ（W + tauMax + 1） | 3,874 サンプル = 80.7 ms | 3,559 サンプル = 80.7 ms |
| 実行間隔 | 平均 50 ms（2,048 サンプル単位で届くため、実際の間隔は 42.7 ms または 85.3 ms） | 同様 |
| スペクトル窓 | 16,384 サンプル = 341 ms、10 回/秒 | 371.5 ms |

- 窓長は最低音 31 Hz で決まるため、高い音でも 80.7 ms 分を使う。
- 報告時刻 `time` は窓の終端である。実験 E2 では、測定値は窓の中央付近（終端の約 40 ms 前）の音程に一致した（6章）。

棄却条件は `detect()` と `display_filter.push()` に分かれる。

| 条件 | 場所 | 値 |
|---|---|---|
| 無音 | `pitch.js` | RMS < −60 dBFS → `silent` |
| 欠落 | `pitch.js` | 振幅を持つフレームに、ちょうど 0 が16サンプル以上続く → `dropout` |
| 不安定（周期性） | `pitch.js` | 正規化差分の谷の深さ > 0.2（信頼度 < 0.8）→ `unstable` |
| アタック・急な停止・急な音量変化 | `pitch.js` | フレーム前半と後半のエネルギー比 > 4（6 dB）→ `unstable`（`levelChange` に比を記録） |
| 範囲外 | `pitch.js` | 31 Hz 未満または 4,400 Hz 超 → `out-of-range` |
| 音声の欠落・不連続 | `analysis.worker.js` | gap フラグ、または startFrame が連続しない → リングバッファーを初期化し `gap` を通知 |
| 立ち上がり確認 | `display_filter.js` | 新しい音は2フレームが 20 cent 以内でそろうまで表示しない（最大2フレーム待つ） |
| 跳躍 | `display_filter.js` | 前回の生の値から 30 cent 以上動いたら平滑化をやり直す |

表示補正（`display_filter.js`）の内容:

- 対数周波数での平滑化（時定数 120 ms）
- 音名切替の余裕 3 cent
- 合格判定のヒステリシス（±3 cent で入り、±4 cent で解除）
- 表示保持 1 秒

生の値は変更しない。ただし、`index.js` の `latestPitch`、`snapshot` とも最新値しか持たない。時系列は保存も保持もしていない。

### 2.4 純正律の目標

`temperament.justTarget(mode, rootMidi, A4)` は次のように計算する。

- 根音の周波数を12平均律で求める: `A4 × 2^((root − 69)/12)`
- 目標を求める: `根音 × 6/5`（短3度）または `× 5/4`（長3度）

目標の音は根音の3度上に固定され、検出した音には追従しない。平均律との差は +15.6413／−13.6863 cent である。根音の範囲は C1～A♭7。

### 2.5 再生と測定・ライフサイクル

- **再生（`index.js` の `onPlay`）:**
  - 次の順に処理する。
    1. 予約中の測定再開を取り消す（`cancelMeasurementResume`）。
    2. 再生エンジンを開始する。
    3. `controller.stop()` でマイクを解放する。
    4. 表示を消す。
  - 停止（`onStop`）では、タップ内で launcher が測定用の AudioContext を準備し、250 ms 後に測定を再開する（`resumeMeasurementFromGesture`）。
  - 再生中に測定開始が届いても、本体の `start()` は測定を始めない。
- **初回タップ:** iOS の Safari ではタップ内でしか AudioContext を開始できない。このため `prime()`（launcher 読み込み済み）または `prepareTunerTap()`（未読み込み）が、同期的に AudioContext を作って `resume()` する。
- **遅延読み込み中の退出:**
  - `leave()` は同期的で、何度呼んでもよい。世代番号を進め、準備中・開始中のコンテキストを閉じる。
  - 後から届いたマイク許可は `controller` が `isCurrent` で検出し、すぐに解放する。
- **履歴復帰:** `routes.js` の `preparePortalTunerHistoryRestore` が認証を確認してから復帰する。その間に別の画面へ移動していれば、ナビゲーション連番で無効にする。
- **ログアウト・認証解除:** `auth_feature.js`・`api_runtime.js`・`events.js` が `portalTunerLeave` を呼ぶ。
- **背景:** `visibilitychange`（hidden）・`pagehide` で `suspendForBackground` を呼ぶ（すべて解放し、復帰時に1回だけ自動再開を試みる）。
- **中断:** 次の場合は測定を終了し、`resume-required` 状態で再開ボタンを出す。自動での再取得はしない。
  - トラックの `ended`・`mute`
  - AudioContext が `suspended`・`interrupted`・`closed` になったとき
  - 3秒間 Worker から結果が来ないとき（監視）
- **Wake Lock:**
  - 測定中は controller が、測定の実行単位ごとに取得する。
  - 再生中は本体が、再生セッションごとに取得する。
  - 取得が遅れて届いたときは、その時点で不要なら解放する。
  - 取得に失敗しても機能は止めない。
- **設定の保存:**
  - 保存するのは A4 のみ（localStorage、端末・ブラウザー単位。ログアウトしても消さない）。
  - 保存に失敗した場合は、その画面の間だけメモリーで保持し、失敗を表示する（`lastSaveFailed`）。
  - 判定方式・根音・表示範囲・再生設定は保存しない（ページ内のメモリーのみ）。
- **読み込み・版管理:**
  - 本体は launcher が `async=false` のクラシックスクリプトで順に読み込む（`MAIN_SCRIPTS`）。
  - すべてのファイルが同じリリース識別子を持つ。Worker・Worklet・読み込み時点で版が混在していれば `version-mismatch` にする。
  - `?rev=` 付きの静的ファイルは1年の immutable キャッシュになる（`static_assets.py`）。
  - 初期ページのスクリプトは増やしていない（launcher は実験室モジュールから読み込む）。

## 3. 追加仕様と既存仕様の衝突・曖昧さ（推奨案は確定ではない）

| 論点 | 現行 | 追加仕様 | 推奨案と理由 |
|---|---|---|---|
| A4 の範囲・刻み | 430～450 Hz、整数、±ボタン（ユーザー決定事項） | 390～480 Hz、0.1 Hz 刻み、プリセット（440／441／442／443 など） | **未確定のため、ユーザーが判断する。** 推奨: 内部では 0.1 Hz 単位の整数で保持（4420 = 442.0 Hz）し、Phase 1 の既定範囲は現行の 430～450 のまま、プリセットと 0.1 Hz の微調整を追加する。390～480 にした場合の計算値は次のとおり。いずれも12平均律で、A4 からの比で求めた。<br>・音の周波数: C1 は A4 = 390 Hz で 28.99 Hz、C8 は A4 = 480 Hz で 4,566.56 Hz。現行の 430～450 Hz では 31.96～4,281.15 Hz<br>・探索範囲: 現行は 31～4,400 Hz。音の周波数に余裕を加えた値として決めている（設定値で、音の周波数ではない）<br>・必要な変更: 390～480 では上限・下限とも音の周波数が現行の探索範囲を外れるため、探索範囲を広げる必要がある。広げる幅（余裕）は音の周波数とは別に決める（例: 下限 28 Hz、上限 4,700 Hz。候補値）<br>・影響: 下限を 31 Hz から 28 Hz に下げると、分析長は 80.7 ms から約 89 ms に延び、遅延と計算量が増える。再生の上限（現行 4,400 Hz）も、C8 を鳴らすなら見直しが必要になる<br>設定できる範囲と、精度を評価した範囲は分けて表示する |

## 5. 現行検出エンジンの評価と判断

### 5.1 判断

**YIN の中核（`differenceFFT`・`cumulativeMeanNormalized`・`refinePeriod`）は再利用する。周辺は改修する。置き換えは推奨しない。** 理由は次のとおり。

- 定常音の精度は、合成音で既に十分である。改善が必要なのは精度そのものより、時刻の扱い（窓長・実効時刻）、高音域のオクターブ誤り、データの質の判定（回り込み・低信頼度）の3点である。
- 検出器の置き換え（pYIN、Mauch & Dixon 2014 など）は、候補を複数出して HMM で滑らかな経路を選ぶため、時系列の処理と遅延が増える。現行の要件（リアルタイム表示）とは別に「解析用の後処理」として比較する価値はあるが、Phase 1 の前提にはしない。
- 改修候補:
  1. 音域に応じて解析窓を短くする
  2. 高音域の基音欠落時に、スペクトルで基音を確認する
  3. 結果に実効時刻（窓の中央）を付ける
  4. エンジンの版を結果に付ける
  5. 再生中の混入判定（補助）と、同時再生区間のフラグを付ける

### 5.2 改修候補の根拠

| 課題 | 根拠（実験） | 改修候補 |
|---|---|---|
| 窓が長く、高い音でも 80.7 ms を使う | ビブラートの幅が 3～22% 小さく測られる（6.4）。発音後の最初の有効値は約 100 ms 後（6.2） | 2段階の検出器（例: 31 Hz 以上用と 110 Hz 以上用。後者は分析長 22.8 ms）を、直前の音程に応じたヒステリシスで切り替える。110 Hz 以上用にすると、ビブラートの幅の比は 0.98～0.99 になった |
| 高音域（C6～C8）の弱い基音・基音欠落でオクターブ誤り | 該当フレームの 13～23% が1オクターブ上（6.1） | YIN の2倍周期確認に加えて、スペクトルの基音帯域の電力を確認する。または、この条件を「信頼度低」として統計から除外する。実楽器での発生頻度は未確認 |
| 報告時刻が窓の終端 | グリッサンドで、終端時刻との差は −8～−49 cent、中央時刻との差は ±0.6 cent 以内（6.5） | 結果に `centerTime`（終端 − 分析長/2）を加え、解析と保存はこれを使う。表示は従来どおり |
| 50 Hz のハム音を正しい音程として検出する | ハム音＋ノイズで 100% 有効（6.1） | 物理的には正しい音程なので、検出器では除外しない。練習の文脈（目標音から 1 半音以上離れた音、音量の小さい持続音）で除外し、「環境音の可能性」として扱う |
| 再生音の回り込みで、オクターブ単位の誤りを「有効」と報告する | 別の音程の基準音が −10 dB 以上で混ざると 100% 誤る（6.6） | 再生と測定を同時に行う区間は、既定で統計から除外する。再生周波数の帯域電力による混入判定は補助（警告表示）に使う。奏者の音の倍音に重なる再生音（同音、オクターブ上、第3倍音など）は判定できない |

## 6. 測定精度・アナライザーの調査結果

条件は特記がない限り次のとおり。

- 48 kHz、`synth` で合成した音（ピーク 0.3、帯域制限あり）
- Worker と同じ 1/20 秒ごとの予定
- 「有効」は `valid === true` のフレーム

### 6.1 定常音（E1）

各セルは、有効率／粗大誤差率（有効フレームのうち 50 cent を超える誤差の割合）／有効フレームの |誤差| の 95 パーセンタイルである。粗大誤差を除いた後の値（cent）を示す。

| 音色（合成） | C1～B2 | C3～B5 | C6～C8 |
|---|---|---|---|
| 純音 | 100%／0%／0.000 | 100%／0%／0.000 | 100%／0%／0.005 |
| 1/n 倍音（弦楽器風） | 100%／0%／0.001 | 100%／0%／0.012 | 100%／0%／0.059 |
| 奇数倍音が中心（クラリネット風） | 100%／0%／0.000 | 100%／0%／0.008 | 100%／0%／0.095（44.1 kHz では粗大誤差 3.3%） |
| 弱い基音（−20 dB） | 100%／0%／0.000 | 100%／0%／0.004 | 100%／**13.3%**／0.063 |
| 基音欠落（2～8倍音） | 100%／0%／0.000 | 100%／0%／0.010 | 100%／**23.3%**／0.089 |
| 2倍音が強い（+6 dB） | 100%／0%／0.000 | 100%／0%／0.001 | 100%／0%／0.033 |

| SNR 0 dB | 0%（すべて `unstable`） | 0% | 0% |

- 粗大誤差はすべてオクターブ誤り（+1200 cent）である。
- 44.1 kHz でもほぼ同じ傾向だった。SNR 10 dB の C6～C8 では粗大誤差が 4.1% だった。
- **誤検出（音程のない入力が有効と判定された割合）:** 次の入力はすべて 0% だった。
  - ホワイトノイズ（−30／−50／−65 dBFS）
  - 低域通過ノイズ
  - 25 Hz（範囲外）・5,000 Hz（範囲外）
  - 毎秒3回のクリック
- 50 Hz のハム音＋ノイズは 100% が有効と判定された（物理的には 50 Hz の音）。
- 合成した定常音では、誤差は 0.1 cent 未満が中心である。ここから「1 cent の精度」を保証することはできない。実際の誤差は、マイク・部屋・楽器の揺らぎ・倍音の非調和性に支配されると考えられる（未検証）。

### 6.2 アタック・リリース（E2-A）

条件は次のとおり。

- 前後に 0.5 秒の無音
- 立ち上がり 5～200 ms、持続 1.5 秒、減衰 50～500 ms
- SNR 40 dB

| 項目 | 結果 |
|---|---|
| 発音から最初の有効値まで | 97 ms（立ち上がりの長さによらない） |
| 発音直後のフレーム | 窓が無音をまたぐため棄却される。合成音では無音がちょうど 0 なので `dropout` になったが、実マイクでは `unstable`（前後半のエネルギー比）になると考えられる |
| 持続部の有効率 | 100% |
| リリース区間 | 有効フレームは減衰区間の一部だけ（3フレーム中1～2、12フレーム中10）。最後の有効値は音の終わりの 7～82 ms 前 |
| 音程のしゃくり上げ（発音時 −40 cent から時定数 60／150 ms で戻る） | 最初の有効値（97 ms）は −15.4／−27.3 cent で、窓の中央時刻の真値（−15.5／−27.4）と一致した。それより前の部分（最初の約 60 ms）は測れない |

**設計への影響:**

- A-011（アタック検出）は、音程の有効フレームではなく、音量（RMS）の上昇から別に検出する必要がある。
- A-012（発音直後の音程）が測れるのは、現行の窓で「発音後 約 100 ms 以降」である。短い窓（110 Hz 以上用は分析長 22.8 ms）を使えば、約 30～40 ms 以降まで縮められる見込みだが、低音には使えない。
- 「発音直後の音程」を何 ms 後の値と定義するかは、設計前に決める（例: 有効になった最初の 50 ms の中央値。候補値）。
- A-018（リリース分析）は、最後の有効値が音の終わりの最大 82 ms 前になる。リリースの定義（例: 最後の有効値から遡って 200 ms）は候補値として検証する。

### 6.3 強弱変化（E2-B）

| 入力 | 有効率 | 備考 |
|---|---|---|
| クレッシェンド 10／30／80 dB/秒 | 100% | 前後半のエネルギー比 4（6 dB／40 ms ≒ 150 dB/秒）に達しない |
| スフォルツァンド風（100 ms で 20 dB 低下 = 200 dB/秒） | 96%（1フレーム棄却） | — |
| デクレッシェンド（2秒で −50 dB へ） | 100% | 終わり近くの誤差の 95 パーセンタイルは 0.067 cent |
| トレモロ 5 Hz ±3 dB | 100% | — |
| トレモロ 5 Hz ±6 dB | **81%** | 棄却はすべて `unstable`（前後半のエネルギー比） |
| トレモロ 8 Hz ±6 dB | **56%** | 同上 |

**設計への影響:** 通常のクレッシェンドとデクレッシェンドは、現行の除外条件と両立する。P-007（強弱変化練習）・I-008（強弱別分析）も、一般的な速さなら成り立つ見込み。

ただし、次の2点が分かった。

- 音量の揺れ（±6 dB 程度）が大きい奏法では、フレームの2～4割が除外される。
- 除外が音量の大小と相関するため、強弱別の統計に偏りが出る。

このため、除外条件を「音量の変化」と「周期性の低下」に分けて記録し、棄却率も強弱別に表示することを推奨する。

### 6.4 ビブラート（E2-C）

真値は中心 +3 cent、片側の幅 A（±A cent、山から谷までは 2A）、速さ r の正弦状の変化。推定方法は次のとおり。

- 0.2 秒以降の有効フレームを使う。
- 3～10 Hz で正弦を当てはめ、速さを推定する。
- 同時に直線のドリフトも推定する。

| 条件 | 速さの推定 | 幅の比（推定/真値） | 中心の推定 |
|---|---|---|---|
| 現行（20 回/秒、分析長 80.7 ms） | r = 4.5～7.5 Hz のすべてで真値と一致（0.05 Hz 刻み） | 4.5 Hz: 0.90～0.97、5.5 Hz: 0.86～0.97、6.5 Hz: 0.82～0.95、7.5 Hz: 0.78～0.95（幅が小さいほど比が小さい） | 2.8～3.7 cent（真値 3） |
| 表示用の平滑化（120 ms）を通した値 | 一致 | **0.21～0.35** | 2.1～5.6 cent |
| 50 回/秒（分析長は同じ） | 一致 | 現行とほぼ同じ | — |
| 50 回/秒、110 Hz 以上用の検出器（分析長 22.8 ms） | 一致 | **0.98～0.99** | 2.98～3.04 cent |

**設計への影響:**

- 毎秒約20回の推定でも、4.5～7.5 Hz のビブラートの速さは推定できる（ナイキスト 10 Hz 未満）。
- 幅は窓による平均化で過小評価され、速く狭いビブラートほど小さく出る。特に 7.5 Hz・±10 cent では 22% 小さい。
- 回数を増やしても改善せず、効くのは窓を短くすることである。
- **表示用の平滑化値を解析に使うと、幅が 1/3～1/5 になり、中心もずれる。解析では必ず生の値を使う。**
- A-021（ビブラート検出）で「ビブラート」と「単に不安定」を区別する指標の候補:
  - 当てはめの残差 RMS: 今回の合成音で 0.1～8 cent。不安定な音では大きくなる見込み
  - 周期ごとの速さ・幅のばらつき
- これらは実楽器で検証してから閾値を決める。
- 音楽的に適切なビブラートかどうかは判定しない。

### 6.5 跳躍・グリッサンド・ドリフト（E2-D）

| 入力 | 生の値が新しい音の ±5 cent 以内になるまで | 表示がそうなるまで |
|---|---|---|
| 半音上 | 53 ms | 96 ms |
| 完全5度上 | 96 ms | 181 ms |
| 1オクターブ上 | 96 ms | 181 ms |
| 完全4度下 | 96 ms | 181 ms |
| 20 cent 上（跳躍の閾値 30 cent 未満） | 53 ms | 224 ms（平滑化で徐々に移る） |

- 跳躍の途中で中間の値が有効と出たのは、完全5度上と完全4度下で各1フレーム。
- 生の値の時間は、変化の時点から報告時刻（窓の終端）までで、実際の端末の入出力遅延は含まない。

グリッサンド（半音を 500 ms、半音を 200 ms、1オクターブを 1 秒、2半音下降を 300 ms）の結果:

- 報告時刻（終端）の真値との差の平均は −8.2／−20.6／−49.0／+27.3 cent だった。
- 窓の中央時刻の真値との差の平均は −0.13／−0.38／−0.56／+0.42 cent だった。
- **解析で使う時刻は窓の中央（実効時刻）にする必要がある。**

ドリフト（3秒で +10 cent、4秒で −5 cent、2秒で +2 cent、SNR 30 dB）は、直線の傾きをほぼ真値どおりに推定した（3.333／−1.25／0.997 cent/秒）。

### 6.6 音符イベント分割・クリッピング・欠落・回り込み（E2-E～G、E2b、B4）

**音符イベント分割（試作した規則）:** 次のいずれかでイベントを区切る。

- 有効フレームが途切れたとき
- それまでの中央値から 50 cent 以上離れたとき
- 最大値から 10 dB 以上下がった後、6 dB 以上上がったとき

この試作規則の結果:

| 入力 | 真のイベント数 | 検出 |
|---|---|---|
| スタッカート（300 ms・無音 100 ms）×4 | 4 | 4 |
| 音の間で −15 dB に 60 ms 下がる（無音なし）×4 | 4 | 3（1つ見逃し） |
| 異なる音のレガート（400 ms ずつ） | 4 | 4 |
| ビブラート付きのロングトーン（6 Hz ±40 cent） | 1 | 1 |
| 同音の連打（150 ms・無音 30 ms）×6 | 6 | **2**（窓 80.7 ms が無音をまたぐため、ほとんどのフレームが棄却される） |

**設計への影響:** 音程フレームだけで分割すると、短い同音反復（P-006・A-020）を取りこぼす。必要な対応:

- 発音の検出は、短い窓の音量包絡（例: 10 ms ごとの RMS）で別に行う。
- 音程は「イベント内の有効フレーム」から求める。
- 1イベントに必要な最小有効フレーム数を決める（候補値: 3。実験で決める）。

**クリッピング:** ピークの 90%／50%／20%／5% で切り詰めても、音程はすべて有効で誤差は 0.06 cent 以内だった。

- 音程にはほぼ影響しないが、倍音構成（A-007・倍音分析）は大きく変わる。
- このため、クリッピングを検出し（連続する最大値、または ±1 付近のサンプル）、倍音分析から除外するフラグが必要になる。現行にはない。

**欠落:** 64 サンプルのゼロを挿入すると、そこを含む2フレームが `dropout` になった。

**回り込み（E2）:** 奏者の音（1/n 倍音、A4）に再生音（サイン波）を混ぜた。

| 再生音（奏者の音に対する大きさ） | 結果 |
|---|---|
| 同じ高さ（5 cent 違い）−30～−6 dB | 偏り −0.3 cent 以内 |
| 同じ高さ（5 cent 違い）0 dB | 偏り −1.1 cent（再生音のほうへ引かれる） |
| 1.5 Hz 違いのうなり | 偏り 0.2 cent 以内 |
| 純正5度上（E5）／1オクターブ下（A3）／純正長3度上（C♯5）−20 dB 以下 | 影響なし |
| 同上 −10 dB 以上 | **すべて有効のまま、−1200／−1200／−2400 cent**（両方の音に共通する周期を基音と判定する） |

**回り込みの判定（E2b）:** 再生周波数の帯域電力を、フレーム全体の電力と比べた。

- 回り込みがないとき: −67～−74 dB
- 回り込みが −40／−30／−20／−10 dB のとき: それぞれ −37／−27／−17／−8 dB（ほぼ比例）

再生音の成分が奏者の倍音と重ならない場合は、判定できる見込みがある（この実験では、A4 の奏者に対する純正5度上・長3度上・オクターブ下）。

**識別できない範囲:**

- 再生音の成分の周波数が、奏者の音の倍音（n × f0、n = 1, 2, 3, …）の帯域（帯域幅は FFT の分解能と同じく、16,384 点・48 kHz で数 Hz）に重なる場合、その帯域の電力は奏者の音と区別できない。
  - 該当する例: 同音（n = 1）、オクターブ上（n = 2）、オクターブ＋5度上（第3倍音、n = 3。例: A3 を吹いているときの E5）、2オクターブ上（n = 4）など。
  - 再生音がサイン波でない場合（音色・和音）は、その成分の一つ一つについて同じ制約がある。
- 奏者の音程は揺れるため、重なるかどうかは時間とともに変わる。
- 判定できる場合も、閾値（例: −30 dB）の妥当性は、合成音でしか確かめていない。部屋の残響や楽器の雑音でノイズ床が上がると、判定はもっと難しくなる。

**同時動作（B4、Chromium・疑似マイク）:**

- 再生用と測定用の AudioContext を同時に動かせた（どちらも `running`）。
- `getSettings()` の結果は、エコー除去・ノイズ抑制・自動音量調整のいずれも `false` だった。
- `navigator.audioSession` は存在しなかった（Chromium）。
- 疑似マイクなので、音響的な回り込みは測れない。

**同時使用についての結論:**

- スピーカーから鳴らす再生と測定の同時使用で、測定値の正しさを保証することはできない。
- エコー除去を有効にすると回り込みは減る見込みだが、持続音を雑音として扱う可能性があり、測定には使わない（現行と同じ方針）。
- 同時使用は、次の条件付きの機能として扱う（推奨）。
  1. 利用者の宣言（「イヤホンを使う」）があるときだけ使える。
  2. 混入判定は補助として使う。判定できた混入は警告を出す。判定できない組み合わせ（再生音が奏者の倍音に重なる場合）があることを前提にする。
  3. **同時再生の区間は、既定で診断・履歴の統計から除外する。** リアルタイム表示と、その場の練習のフィードバックにだけ使う。
  4. 統計に含める条件は、実機検証の後に決める。検証項目は、内蔵スピーカー・イヤホン・Bluetooth での回り込み量（11章）と、倍音に重なる組み合わせでの誤差。それまでは、データを保存する場合も「同時再生区間」のフラグを付け、集計から外す。
- イヤホンの使用宣言と自動判定の組み合わせだけで、診断データの正しさは保証しない。
- iPhone では、マイク使用中に音声の経路や音量が変わることがあると考えられるが、一次資料で確認できなかった。実機で確認する（11 章）。

### 6.7 音源（B1、Chromium の OfflineAudioContext）

- **複数音の合成:** 各音をゲイン 0.25 で重ねると、サイン波4音（長7の和音）でピーク 0.94 になった（ほぼ上限）。のこぎり波4音では 0.66。S-007・S-008 では次が必要になる。
  - 音数に応じた正規化（例: 1/N、または全体の上限ゲイン）
  - 位相をそろえた場合の最悪値の確認
  - 必要ならリミッター（DynamicsCompressorNode）
- **エイリアシング:** 次の波形を確かめた。
  - のこぎり波・矩形波・三角波（440／1,760／3,520 Hz）
  - 40倍音の PeriodicWave（1,760 Hz）

  いずれも、倍音以外の成分は −34～−62 dB で、測定方法の下限（Hann 窓の漏れ）と区別できなかった。明らかなエイリアシングは見られなかったが、仕様上の保証はまだ一次資料で確認していない（Web Audio API 仕様の OscillatorNode の記述は今回の調査で読めなかった）。Safari は未確認。
- **スケジューリング:** `start(time)` で 120 BPM のクリックを16回予定すると、すべて同じ1サンプルの差で鳴った。これは検出の閾値によるもので、オフライン描画では時刻どおりに鳴る。実時間の再生では、`setTimeout` の揺らぎを先読みスケジューリングで吸収する方式（web.dev "A tale of two clocks"）を使う。実時間の揺らぎは未測定。
- **クリックノイズ:** フェードなしで止めると、最大のサンプル間の差は 0.416 だった。30 ms のフェードを付けると 0.058 になり、定常のサイン波 440 Hz と同じ大きさになった。現行の S-011（フェード）の方式は有効である。

## 8. 音律モデル

### 8.1 目標周波数を一意に決める入力

| 音律 | 必要な入力 | 目標の計算 |
|---|---|---|
| 12平均律 | A4、（音名固定時は）目標の音名とオクターブ。自動判定時は最寄りの音 | `A4 × 2^((n − 69)/12)` |
| 純正短3度・長3度（現行） | A4、根音（音名＋オクターブ）、音程の種類 | 根音（平均律）× 6/5 または 5/4 |
| 純正長三和音・短三和音 | A4、根音、和音の種類、役割（根音・3度・5度）、目標のオクターブ | 根音（平均律）× {1, 5/4, 3/2}（長）または {1, 6/5, 3/2}（短）× 2^k |
| 役割指定（M-006） | 上記に加え、7度などを含む場合は比の選択 | 例: 短7度は 16/9、9/5、7/4 の3つの候補があり、どれを採用するか未確定（cent で −3.91／+17.60／−31.17） |
| ピタゴラス音律 | A4、基準音（調の中心）、五度圏の切れ目 | 基準音 × (3/2)^k を [1, 2) に折り返す |
| カスタム音律 | 基準音、12音それぞれの平均律からの偏差（cent）、または比 | 基準音 ×（指定した比）または 平均律 × 2^(偏差/1200) |

**基準周波数の決め方:** 現行は「根音を12平均律で決める」方式である。これ以外に「根音も A4 から純正の比で決める」方式もありうるが、どちらを採るかで根音そのものの目標が変わる。

**推奨:** 現行と同じ「根音 = 平均律（A4 基準）」を既定とし、他の方式は採用しない。理由は次の2つ。

- 合奏での一般的な使い方（基準 A に合わせた楽器の上で純正の和音を作る）に近い。
- 根音の目標が平均律チューナーと一致するため、説明しやすい。

この点は設計前に決める。

### 8.2 ピタゴラス音律の規則（E4 の計算値）

C を基準とし、五度を E♭（−3）から G♯（+8）まで積み上げた場合の12音と、平均律からの差は次のとおり（cent）。

| C | C♯ | D | E♭ | E | F | F♯ | G | G♯ | A | B♭ | B |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 0 | +13.69 | +3.91 | −5.87 | +7.82 | −1.96 | +11.73 | +1.96 | +15.64 | +5.87 | −3.91 | +9.78 |

- 切れ目は G♯ と E♭ の間（ウルフの5度は 678.49 cent）。
- ピタゴラスコンマは 23.46 cent。比較の参考として、シントニックコンマは 21.51 cent。

**決める事項:**

- 切れ目の位置（どの範囲の五度を使うか）
- 異名同音（C♯ と D♭ は 23.46 cent 違う）を12音のどちらに対応付けるか

推奨は「基準音（調）と切れ目を利用者が選び、既定は E♭～G♯」とすること。12音の音名表示は現行の `NOTE_NAMES`（C♯・E♭・F♯・A♭・B♭）のままでは異名同音を区別できないため、ピタゴラス音律とカスタム音律では、♯・♭の表記選択（T-003）と連動させる必要がある。

### 8.3 測定中に音律・役割を変えた場合

**推奨:** 生の値（Hz）は変えずに保持し、目標・条件のスナップショットに変更の時刻を記録して、区間を分割する。

- 判定（cent）は区間ごとの条件で計算する。
- 統計は同じ条件の区間だけをまとめる。
- 1つの音符イベントの途中で条件が変わった場合、そのイベントを統計から除外するか、条件ごとに分ける。どちらにするかは設計で決める。

### 8.4 単音解析の限界

再生側で和音を鳴らせても、入力の和音を楽器別・音別に分けて測定できるわけではない。

- 現行の検出器は単音用で、実験 E2-G のとおり、複数の音が混ざると共通の周期（低いオクターブ）を返す。
- M-004～M-006 の「和音の中の3度」は、利用者が1音ずつ演奏し、役割を指定して判定する方式とする。
- 複数音を同時に分離して測る機能は、この仕様の範囲では実現困難として扱う（多重音高推定は別の研究課題）。

## 9. 保存・認証・プライバシー

### 9.1 既存の認証・テナント・Repository（ソース確認）

- **認証:** 端末 ID（`X-Device-Id` ヘッダー）を `services/auth_service.py` の `device_auth_record` で `auth_devices` から引き、`member_id` があれば `members` の現在の権限を反映する。
  - 管理者の判定は `core/authorization.py` の `require_admin_device`（管理者・システム管理者）と `require_system_admin_device`（システム管理者のみ）で行う。
  - 隠しシステム管理者は `member_id` を持たない（`auth_service.py` のコメント）。
- **テナント:** `core/middleware.py` が `X-Organization-Id`（または `X-Tenant-Id`）ヘッダーから `organization_id` を決める。省略時は `default`。
  - 各 Repository は `get_current_tenant_id()` で絞り込む（`db_row_repository.db_fetch_all`、`improvement_suggestion_repository` など）。
  - フロントエンドはこのヘッダーを送っていないため、実運用は `default` の1テナントである。
  - `auth_devices` もテナントで絞り込まれるため、別テナントのヘッダーでは端末認証が通らない。
- **新規テーブルの例:** 新規テーブルは `db/migrations/NNN_*.sql`（現在 016 まで）で追加し、`organization_id TEXT NOT NULL DEFAULT 'default'` と索引を付けるのが既存の型である（例: `013_improvement_suggestions.sql`）。Repository は psycopg を直接使うクラス（`ImprovementSuggestionRepository`）とサービス（`improvement_suggestion_service.py`）、ルーター（`routers/improvement_suggestions.py`）の3層になっている。
- **会員の削除:** `member_service.delete_member` は会員を物理削除する。`BaseRepository.create` は `next_id(items)`（一覧から求める連番）を使うため、**削除後に同じ `member_id` が再利用される可能性がある**（要確認。DB 側に連番シーケンスがある表では `db_next_id` が `nextval` を使う）。練習履歴を `member_id` だけに結び付けると、削除した団員の履歴が新しい団員に付く危険がある。
- **公開範囲:**
  - 画面のメニュー表示は `menu_visibility_settings`（016）で団体ごとに切り替えられる。ただし、これは表示だけで、権限ではない。
  - チューナーの公開範囲は launcher の `browserIsAllowed` だけで決まっている（サーバー API を使わないため）。
- **本番はデータベースのみで運用する:** `src/data/*.json` は使わない。端末内保存（IndexedDB）はサーバー側のデータソースではないため、この方針とは衝突しない。ただし、アカウント連携で保存する場合は DB だけに保存する必要がある。

### 9.2 保存方式の比較

| 観点 | 端末内（IndexedDB） | アカウント連携 DB | 併用（推奨候補） |
|---|---|---|---|
| 容量 | Safari 17 以降は、ブラウザーアプリでオリジンあたりディスクの最大 60%（WebKit「Updates to Storage Policy」）。Chromium の見積りは 10.7 GB（B3、この PC） | 制限なし（費用・バックアップの対象） | 時系列は端末、要約は DB |
| 消える条件 | 容量超過、ストレージ不足、一定期間操作がない場合（ITP）。既定は best-effort で、`persist()` はホーム画面のアプリかどうかなどで判断される（同資料）。プライベートブラウズ・サイトデータの削除でも消える | 明示的な削除のみ | 端末側が消えても要約は残る |
| 共有端末・ログアウト | 端末に残る。アカウント別のキー（DB 名）で分け、ログアウト時の扱い（残す／消す／ロック）を決める必要がある | サーバー側で利用者ごとに分離 | 端末側は利用者ごとに分け、ログアウト時に消すかを選べるようにする |
| 管理者と団員・テナント間 | 端末内なので他人は見えない（同じ端末を除く） | 所有者の確認、`organization_id`、管理者が他人の履歴を見られるかの方針が必要 | 同左 |
| 削除 | 端末ごと。全履歴の削除は簡単 | 個別・全件の削除 API が必要。会員削除時の連動削除 | 両方に必要 |
| オフライン・再送 | オフラインで使える | 送信失敗・重複・部分保存への対策が必要（冪等キー） | 端末を正とし、DB へは要約を冪等に送る |
| 出力（CSV／JSON） | 端末内で作れる | API で作れる | 端末内で作る |
| 既存構成への適合 | フロントエンドだけで完結。初期読み込みの増加なし（遅延読み込み） | migration、Repository、サービス、ルーター、テナントの絞り込み、権限が必要 | 段階的に導入できる |

**推奨案（設計前に決める）:**

- Phase 4 の最初は端末内保存（利用者が有効にした場合のみ）から始める。
- アカウント連携は、要約（PracticeSession・NoteEvent の統計・PracticeResult・IntonationProfile）を DB に送る方式を次の段階で追加する。
- 生の時系列（MeasurementSeries）は既定では端末内のみとし、DB へ送るかどうかは別の選択にする。
- アカウント連携の所有者には、`member_id` に加えて再利用されない識別子を使う。会員削除時に連動して削除する。

### 9.3 隠しシステム管理者・公開範囲

- 現在の利用者はシステム管理者のみである。隠しシステム管理者（`member_id` なし）はアカウント連携の履歴を持てないため、その間は端末内保存だけになる。
- 団員へ開放する時期と、履歴の所有者を何にするか（`member_id`、または新しい所有者の識別子）は、ユーザーが決める必要がある。

### 9.4 保存容量の概算（E3、30分・毎秒20回）

| 形式 | 30分 | 1時間あたり | 備考 |
|---|---|---|---|
| 時系列 JSON（1フレームごとのオブジェクト: 時刻・Hz・信頼度・dB・理由） | 1.78 MB（gzip 0.34 MB） | 3.6 MB | 送信・保存には向かない |
| 時系列 JSON（列ごとの配列） | 0.71 MB（gzip 0.19 MB） | 1.4 MB | — |

| 時系列・標準形式（提案、計算値）18 B/フレーム: フレーム番号 u32、Hz・信頼度・RMS dBFS は各 Float32、理由 u8、フラグ u8 | 0.648 MB | 1.30 MB | 時刻を Float64 秒で持つ場合は 22 B/フレーム = 0.792 MB（1時間 1.58 MB） |
| 時系列・圧縮形式（選択肢、計算値）12 B/フレーム: フレーム番号 u32、Hz Float32、信頼度 u8、RMS i8、理由 u8、フラグ u8 | 0.432 MB | 0.86 MB | 時刻を Float64 秒で持つ場合は 16 B/フレーム = 0.576 MB（1時間 1.15 MB）。信頼度と RMS は量子化する（下記） |

**長期利用の例（候補値の計算）:** 1日30分・年300日の場合は次のとおり。

- 時系列（標準形式）: 約 194～238 MB/年（時刻が u32 か Float64 か）
- 時系列（圧縮形式）: 約 130～173 MB/年
- 音符イベントのみ: 約 110 MB/年（JSON、非圧縮）

DB には要約だけを送ることを推奨する。保持期間、間引き（例: 古い時系列は削除し、音符イベントと要約だけを残す）、件数の上限は、設計で決める。

### 9.5 データモデルの要点

- **生の測定値の扱い:** 生の測定値（Hz、実効時刻、信頼度、RMS、棄却理由、フラグ）には、表示用の丸め（0.1 Hz・1 cent など）や平滑化をかけずに保持する。保存時の精度は、形式ごとに次のとおり明示する。
  - Hz（検出器の内部は Float64）は Float32 で保存する。変換誤差は相対で最大 2^−24、cent では最大約 0.0001 cent。440 Hz での Float32 の刻み（ULP）は約 0.00012 cent。cent・0.1 Hz への丸めはしない。
  - 実効時刻は、フレーム番号（u32、48 kHz で約 24.8 時間まで）と標本化周波数で表す。誤差はない。
  - 信頼度と RMS は、標準形式では Float32 で保存し、量子化しない。圧縮形式を選ぶ場合は、量子化を「丸めた値」として形式の版に記録する。量子化の内容は次のとおり。
    - 信頼度: 0～1 を 255 段階。誤差は最大 0.002
    - RMS: 1 dB 刻みの i8（−128～+127 dBFS）。誤差は最大 0.5 dB。−128 dBFS 未満は −128 に切り詰める
    - 統計の除外の閾値（信頼度・音量）を量子化後の値で判定する場合、閾値の付近で結果が変わりうる。
  - **推奨:** MeasurementSeries は既定で端末内にのみ保存し、容量も小さい（30分で 0.65～0.79 MB）。このため標準形式とし、圧縮形式は DB や GCS に送る場合の選択肢として検討する。
- cent は条件（A4、音律、根音、役割、目標）から後で計算する。
- 各セッションと区間に、次の3種類を記録する。
  - 目標・条件のスナップショット
  - 検出エンジンの版（例: `pitchEngine = "yin-1"` と、リリース識別子・主要パラメーター）
  - 派生統計の版（例: `statsVersion`）
- エンジンや計算式の版が違う結果は「上達」の比較に混ぜない。比較する場合は、同じ版で再計算するか、違うことを表示する。
- 各エンティティの項目案は [TUNER_ADVANCED_IMPLEMENTATION_PLAN.md](TUNER_ADVANCED_IMPLEMENTATION_PLAN.md) の4章にある。

**音声を保存しない場合の再解析の範囲:**

| 時系列（Hz・信頼度・RMS）を保存した場合に後から再計算できるもの | 復元できないもの |
|---|---|
| A4・音律・目標の変更、音符イベントの分割規則、統計の計算式 | 検出エンジンの変更（窓・閾値・オクターブ判定）による再検出、倍音構成（保存していなければ）、棄却したフレームの本当の音程、音色 |

音符イベントと要約だけを保存した場合、分割規則や閾値を変えた再計算もできなくなる。

### 9.6 入力検証・CSV 出力

- 楽器名・メモなどの自由入力は、長さの上限を設け、制御文字を除く。
- CSV に出力するときは、先頭が `=`・`+`・`-`・`@`・タブ・CR の値を文字列化（先頭に `'`）して数式の実行を防ぐ。
- 数値の範囲（Hz・cent・気温・湿度）は API とクライアントの両方で検証する。

### 10.1 SharedArrayBuffer と COOP／COEP

- 現行は、Worklet → Worker を MessagePort とバッファーの転送（コピーなし）で結び、固定プールで上限を設けている。SharedArrayBuffer は不要である。
- 導入すると、ページ全体に COOP `same-origin` と COEP `require-corp`（または `credentialless`）が必要になる。現行のポータルは Bootstrap 5.3.0 を cdn.jsdelivr.net から読み込んでおり（`src/index.html`）、COEP を付けると、CORS の属性や CORP ヘッダーへの対応が必要になる。また、別ウィンドウとの連携（`window.opener`）が切れる。
- **推奨:** 導入しない。代替策は次のとおり。
  - 現行の転送方式を続け、プールの大きさとチャンクを調整する（例: 1,024 サンプルにすると最大約 47 回/秒まで分析できる）。
  - 解析結果は Worker 内で時系列にまとめ、一定間隔で主スレッドへ送る。
