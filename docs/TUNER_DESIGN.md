# チューナー設計書

最終更新: 2026-10-16

「実験室」のチューナー（システム管理者のみ）の構成・動作・調整値・制約・検証結果をまとめる。
iPhone 実機での確認手順は `docs/MANUAL_DEVICE_QA_CHECKLIST.md` の「7. チューナー」を参照。

## 1. 範囲

- マイクから楽器の単音を入力し、音名・測定Hz・cent・判定（低い／合っています／高い）・メーター・周波数スペクトラムをリアルタイム表示する。
- 利用者はシステム管理者のみ。団員への公開は行っていない（将来 `memberPanel` へ移せるよう、実験室から独立したモジュールにしている）。
- フロントエンドのみ。バックエンド・DB・API の追加はない。音声は端末内で解析し、録音・保存・サーバー送信はしない。保存するのは基準Hzだけ。
- 初期版の対象外: 和音・合奏の楽器別判定、基準音再生、移調表示、純正律、測定履歴、目標音登録、音色採点、団員公開。

## 3. 既存ポータルとの接続

index.html の初期スクリプトは増やしていない（既存テストが本数を固定している）。読み込みは次の順になる。

1. システム管理者が実験室モジュール（`improvement_suggestions.js`）を読み込むと、`launcher.js` を読み込む（団員には読み込まない）。
2. 「実験室」タブを開くと本体を先読みする。AudioContext 生成とマイク取得は行わない。
3. 「チューナー」タップで `PortalTunerLauncher.prime()`（同期）→ `switchTab('systemPanel', 'system-tuner')` → `enter()`。
   launcher がまだ届いていない場合（低速通信・キャッシュなし）は、読み込み済みの実験室モジュールがタップの処理内で AudioContext を同期的に生成・resume する（`prepareTunerTap()`。マイクには触れない）。launcher の到着後に `adoptPrimed()` で引き渡す。引き渡しの前には、タップ要求が取り消されていないこと、親パネルを含めて画面が表示中であること、管理者であることを再確認する。
   launcher 到着前にバックグラウンドへ移るかページを離れた場合は、実験室モジュールが保留中のコンテキストを閉じる（launcher 到着後は launcher 側が処理する）。「チューナーを開きたい」という要求は、コンテキストとは別に保持する（`tunerStartRequested`）。画面に戻ったときに要求が残っていれば、タップ扱いなしで開始する（「タップして測定を再開」が出ることがある）。

| 既存処理 | 接続内容 |
|---|---|
| `improvement_suggestions.js` の実験室生成 | 「PDF編集」の隣のボタン、`#system-tunerTab` と表示先 `#systemTunerHost`、launcher 読み込み、改善案画面を開くときの退出 |
| `routes.js` の `switchTab()` | チューナー以外への切り替えで退出、タブ表示後に入場、実験室表示で先読み |
| `showAdminPanel` / `showSystemPanel` / `showMemberTab` | パネルを直接隠す前に退出 |
| `restorePortalHistoryState()` | `system-tuner` への復帰: 認証・権限確認 → `ensureImprovementSuggestionsLoaded()` → launcher と本体の読み込み → 表示・再開 |
| `auth_feature.js` の `logoutPortal` | 通知停止の await より前に退出（実行時に有効なのは events.js より後に読み込まれる auth_feature.js 側。events.js 側にも同じ処理を入れている） |
| `showPortalLogin()` / `clearPortalAuthState()` | ログイン画面表示・認証解除（セッション切れを含む）で退出 |

各経路は共通の退出関数 `window.portalTunerLeave(reason)`（実験室モジュールが定義）を呼ぶ。この関数は、launcher 到着待ちのタップ要求を取り消してコンテキストを閉じたうえで、`PortalTunerLauncher.leave()` を呼ぶ。`leave()` は同期処理で、何度呼んでも安全なため、無関係な遷移で呼ばれても問題ない。

チューナーへの履歴復帰は、認証確認・実験室モジュールの読み込み・本体の先読みを待つ。この待機中に別の画面へ移った場合に古い復帰処理が上書きしないよう、routes.js は画面遷移の世代番号（`portalNavigationSequence`）を持つ。この番号は次のときに進む。
- `switchTab()`
- パネルの切り替えや履歴復帰での退出（`leavePortalTuner`）
- 共通の退出関数（ログアウト・ログイン画面・認証解除を含む）

復帰処理は、待機のたびに自分が最新の遷移要求かどうかを確認する。画面を切り替える直前には、最新の遷移要求であることに加えて、認証済みかつシステム管理者であることも再確認する。共有状態（`portalAppState`）には何も追加していない。認証・権限は `portalRuntimeContext.appState` から読むだけで、マイク・AudioContext・Worker・描画・測定状態はチューナー内部に閉じている。

## 4. 開始・終了

### 4.1 初回タップ（iOS Safari）

iOS Safari では、AudioContext はユーザー操作の中でしか開始できない。そのため、動的読み込みの後に AudioContext を生成する作りにはしていない。

- `prime()` はクリック処理の中で、何も await しないうちに権限・多重起動を確認し、`new AudioContext()` と `resume()` を実行する。resume は待たない。
- 生成したコンテキストと世代番号を `enter()` が本体に渡す。
- 本体の読み込み中も、起動途中のコンテキストは launcher が保持する。そのため `leave()` で即時に閉じられ、読み込みが完了・失敗するまで残ることはない。読み込み失敗・権限喪失のときも閉じる。
- 「タップして測定を再開」と「もう一度試す」も、同じく押した処理の中で `prime()` を実行する。
- launcher の読み込み前のタップでも、実験室モジュールがタップ内でコンテキストを準備する（3章）。そのためタップ扱いは失われない。
- 表示状態（親パネルを含む）は、入場時、本体読み込み後、controller の開始直後と getUserMedia の直前に確認する。非表示であれば AudioContext の生成もマイク取得もしない。

### 4.2 状態

| 状態 | 表示 |
|---|---|
| hidden（非表示） | すべて解放済み |
| starting（起動中） | 「マイクを準備しています。許可を求められたら『許可』を選んでください」。許可待ちもここに含める（getUserMedia が未完了の理由は判別できないため） |
| measuring（測定中） | 無音時の「音を待っています」も測定中の一部 |
| resume-required（再開操作待ち） | 「タップして測定を再開」。AudioContext が running にならない場合、マイク終了・ミュート、AudioContext の中断、3秒間分析結果が届かない場合。エラー扱いにしない |
| unavailable（利用不可） | 理由と、必要に応じて再試行・再読み込み |

自動での再取得は、バックグラウンドからの復帰時（`visibilitychange` と bfcache からの `pageshow`）に1回だけ試みる。中断後に繰り返し再取得することはない。

### 4.3 競合制御

- 起動ごとに世代番号を振る（launcher が採番する。enter・leave・prime のたびに進む）。
- await の後は毎回、世代番号・表示状態・認証・管理者権限を確認する。
- 退出後に許可・取得されたマイクは、その場で停止する。
- 古い世代の分析結果は破棄する。
- 同じ世代の重複 start と、連続タップによる多重生成は行わない。
- 終了処理は何度呼んでも安全で、未完了の起動処理や resume を待たない。
- 明示的な `track.stop()` では `ended` が発火しないため、終了処理はイベント任せにせず、すべて自分で行う。

終了時の処理: トラック停止、ノード切断、Worklet への停止通知とポート終了、MessageChannel の両ポート終了、Worker への停止通知と terminate、AudioContext の close、Wake Lock の解放、タイマー解除、描画停止、待機中 Promise の取り消し、バッファー参照の破棄。

### 4.4 画面離脱の安全網

明示的な退出処理に加え、Worker からの結果・状態通知を受け取るたび、および 0.5 秒ごとの監視タイマーで、次の条件をすべて確認する。満たさなければ描画せずに退出する。

- 表示先が DOM に接続されている
- 親パネルを含めて `hidden` でなく、描画領域がある
- `document.visibilityState === 'visible'`
- 認証済みかつシステム管理者
- 測定世代が一致する

無音時も Worker は状態通知（音程結果、または `status`）を送り続ける。

## 5. 音声処理

```
マイク → MediaStreamSource → AudioWorkletNode(出力1・無音) → GainNode(接続前に gain=0) → destination
                                   │ MessagePort（メインが生成し、Worklet と Worker に1つずつ転送）
                                   ▼
                              analysis.worker.js → 結果のみメインへ
```

- `numberOfOutputs: 0` や destination 未接続の状態には依存しない（Safari では処理されないことがあるため）。
- マイク取得では、エコー除去・ノイズ抑制・自動音量調整を無効にするよう要求する。`getSettings()` で `false` と確認できた項目だけを「無効」として記録し、報告されない項目は「未確認」とする。
- サンプルレートは実際の AudioContext の値を使う（44.1 kHz や 48 kHz に固定しない）。
- Worklet: 処理単位の長さは毎回入力配列から読む（128 と決め打ちしない）。2,048 サンプルずつまとめ、`ArrayBuffer` を transfer する。バッファーは 8 個の再利用プールで、Worker が使い終えたら返却する。プールが空のときは音声を捨て、次の塊に `gap` と欠落数を付ける。待ち行列は無制限に伸びず、遅延の上限はプール分（約 0.34 秒）に収まる。
- 入力配列がないブロック（ブラウザーによる切断・ミュート）があった場合、Worklet は途中まで溜めた塊を捨て、次の塊に `gap` を付ける。塊の開始時刻は、空の状態から書き始めた時点で記録する。
- Worker は `gap` を受け取ったとき、または `startFrame` が直前の塊の終わりと一致しないときに、連続性（リングバッファー・予定時刻・直近の基音）をリセットし、メインへ通知する。メインは表示補正をリセットする。
- SharedArrayBuffer、COOP/COEP ヘッダーは使っていない。

## 6. 分析方式

### 6.1 音程（`pitch.js`）

- YIN 方式。差分関数 d(τ) = Σx²(j) + Σx²(j+τ) − 2Σx(j)x(j+τ) は、ゼロ埋めした FFT 相関と累積二乗和で求める。FFT サイズは「フレーム長＋窓長」以上とし、循環相関の回り込みを防ぐ。全探索（O(W·τmax)）は行わない。小さい配列で直接計算と一致することをテストしている。
- 探索範囲は 31～4,400 Hz（C1～C8 を A4 = 430～450 Hz で使える余裕を含む）。窓長は最長周期の 1.5 倍、フレーム長は 3,874 サンプル（48 kHz で約 81 ms、44.1 kHz で 3,559 サンプル）。
- 処理の流れ:
  1. 直流成分の除去と RMS の計算
  2. 正規化差分（CMND）で、補間後の深さが閾値 0.15 未満となる最初の谷を探し、その谷の最深点を選ぶ
  3. 2倍周期の谷が十分深く、かつ3倍周期では谷にならない場合は、1オクターブ下の候補を採用する
  4. 放物線補間を行う
  5. 周期の整数倍の谷で補間し直す「多周期精密化」で、高音域の補間誤差を抑える
- 無効と判定する条件:
  - 無音: RMS < −60 dBFS
  - 不安定: 谷の深さ > 0.2、またはフレームの前半と後半のエネルギー比 > 4（6 dB）。音の立ち上がりや急な停止を含むフレームは推定値が偏るため
  - 欠落: 音が出ているフレーム内に、ちょうど 0 のサンプルが16個以上連続する。バッファー不足による欠落で、試験では −20～−45 cent の誤表示の原因になっていた
  - 範囲外
- 信頼度 = 1 − 谷の深さ。RMS は「RMS 1.0 = 0 dBFS」と定義する（フルスケールの正弦波は −3.01 dBFS）。

### 6.2 スペクトラム（`spectrum.js`）

- 16,384 点 FFT、Hann 窓。全 FFT データは Worker 内だけに保持する。
- 1点ごとのレベル = 20·log10(2|X[k]|/Σw)。ビン中心にあるフルスケールの正弦波が 0 dBFS になる。
- 帯域電力 = 2Σ|X[k]|²/(N·Σw²)（Parseval の定理による成分の平均電力）を 10·log10(2P) で表す。正弦波がビンの間にあっても 0 dBFS になる。
- 倍音の強さは、n·f0 の周辺 ±3 ビン（f0/2 を上限）の帯域電力で求める。f0/2 が Hann 窓のメインローブ＋1ビンより狭い場合（隣の倍音と分離できない場合）や、ナイキスト周波数を超える場合は `valid: false` とする。分析データとしての倍音は最大40個まで持つ。
- 表示用データは 25 Hz～10 kHz を対数間隔の 512 点に縮約する（区間内の最大値。ビンより細かい低域は線形補間）。ナイキスト周波数を超える点は NaN とし、グラフでは網掛けにして描かない。縦軸は −100～0 dBFS で固定し、自動で拡大縮小しない。

### 6.3 更新頻度

Worker は音声フレーム時刻を基準にした予定時刻で動く。2,048 サンプルの塊（約 43 ms）でも、上限どおりの回数で動く。遅れた場合は予定を現在時刻から組み直し、追いつくための処理を溜めない。

| 処理 | 上限 |
|---|---|
| 音程検出 | 20 回／秒 |
| スペクトラム | 10 回／秒 |
| 描画（requestAnimationFrame） | 30 回／秒。測定中かつ表示中だけ |

更新回数と応答時間は別物である。低音の検出には約 81 ms の分析窓が必要で、さらに立ち上がり確認で1フレーム（約 50 ms）待つ。

## 7. 表示補正（`display_filter.js`）

分析値は変更せず、表示用の値だけを作る。

| 項目 | 値 |
|---|---|
| 平滑化 | log 周波数の cent 領域で指数平滑（時定数 120 ms） |
| 合っています | ±3 cent 以内で入り、±4 cent を超えたら解除 |
| 音名切り替え | 半音の中間点からさらに 3 cent 進んだら切り替え |
| メーター | ±50 cent。超えた場合は針だけ端に寄せ、内部値は保持 |
| 表示保持 | 有効な測定が途切れてから 1,000 ms |
| 平滑化リセット | 音名変更時、または平滑化前の値で直前から 30 cent 以上跳躍したとき |
| 立ち上がり確認 | 新しい音（無音後・跳躍後）は、連続2フレームが 20 cent 以内で一致してから表示する。一致しなくても3フレーム目で採用する（ビブラート対策） |
| 基準Hz変更 | 最新の表示周波数から音名・cent・基準線を即座に再計算する。入力の跳躍とは扱わない |
| 読み上げ | 同じ音名が 800 ms 続いたときだけ。最短間隔 2 秒。数値は毎フレーム読み上げない |

## 8. 基準Hz（`settings.js`）

- A4、初期値 442 Hz、整数 430～450。「−」「＋」で 1 Hz ずつ変更する（直接入力・プリセットなし）。端の値ではボタンを `disabled` にし、破線枠で見た目も変える。
- 保存キーは `portalTunerReferenceA4Hz`（端末・ブラウザー単位）。ログアウトでは削除しない。
- 読み込み時は文字列全体が `^[1-9][0-9]{2}$` に一致し、かつ範囲内であることを検証する。それ以外（小数・前後の空白・範囲外・読み込み例外）は 442 にする。
- 保存先は呼び出し側から渡す。localStorage が使えない場合も、画面内では変更後の値で測定を続け、保存できなかったことを表示する。

## 9. 版管理・キャッシュ

- 静的ファイル配信は `?rev=` 付きの URL を1年間 immutable としてキャッシュする（`static_assets.py`）。
- そこでチューナー全体で1つのリリース識別子 `t-xxxxxxxxxxxx` を使う。識別子はチューナーの全 JS と `tuner.css` の内容（識別子の行を除き、改行コードを正規化）の SHA-256 から求める。内容が変われば必ず URL も変わる。
- `npm run generate:tuner-release` で、各ファイルの `TUNER_RELEASE_ID = '...'` 行と、実験室モジュール内の launcher URL を書き換える。**チューナーのファイルを編集したら必ず実行する。**
- `npm run check:tuner-release`（`pre-release` と Vitest の契約テストに含む）で、識別子が古いと失敗する。
- launcher・本体の JS・CSS・Worker・Worklet・Worker 内の `importScripts` 依存まで、同じ `?rev=` で読み込む。
- 実行時の照合:
  - launcher が期待する識別子と、本体の各ファイルが登録した識別子を照合する
  - Worklet は `processorOptions`、Worker は init メッセージで照合する
  - すべてのメッセージにリリース識別子・プロトコル版・測定世代を含める
- 不一致の場合は解放したうえで「チューナーが更新されています」と表示し、再読み込みを案内する。URL のクエリーだけで混在を完全に防げるとは考えていない（中継キャッシュや配信途中のデプロイなど）。そのため実行時にも照合している。
- 読み込みに失敗した Promise は破棄し、再試行できるようにする。

## 10. エラー案内（`errors.js`）

| 区分 | 主な原因 | 操作 |
|---|---|---|
| マイクが見つからない | NotFoundError / OverconstrainedError | もう一度試す |
| マイクが許可されていない | NotAllowedError / SecurityError（安全な接続のとき） | 許可の変更方法＋もう一度試す |
| ブラウザーが対応していない | getUserMedia・AudioWorklet・Worker・MessageChannel がない | — |
| 安全でない接続 | `isSecureContext === false` | — |
| マイクを読み取れない | NotReadableError / AbortError など。「ほかのアプリで使用中、または端末側で利用できません」 | もう一度試す |
| 自動再開できない | AudioContext が running にならない、中断 | タップして測定を再開 |
| 読み込み失敗・版不一致 | スクリプト・Worker・Worklet の読み込み失敗やタイムアウト、識別子の不一致 | もう一度試す／ページを再読み込み |

画面には内部のファイル名や保存先を出さない（契約テストで確認している）。

## 11. 将来の音色分析への備え

- 音程フレーム: `startFrame`・`endFrame`（分析区間）、`time`、`frequency`、`confidence`、`valid`、`reason`、`rmsDbfs`
- スペクトラムフレーム: 分析区間・時刻、`fundamental`、`harmonics[{number, frequency, powerDbfs, valid}]`、表示用 `display`
- セッション情報（`PortalTunerBody.getSession()`）: サンプルレート、音程のフレーム長と窓長、FFT サイズ、窓関数、ビン幅、要求したマイク条件、確認できたマイク条件
- 分析値と表示用の平滑化値は分けて持つ。履歴は蓄積しない（最新フレームのみ）。dBFS はデジタル信号上の強さであり、音圧ではない。倍音の多さや揺れの少なさだけで良し悪しを判定しない。

## 12. 制約・既知の限界

- **iPhone Safari での動作は未確認。** PC の Chromium（疑似マイク）でしか自動確認していない。初回タップ、自動再開、マイク解放の表示、Wake Lock、発熱・電池は実機チェックリストで確認する必要がある。
- 基音を欠いた音（倍音2～8が同じ強さの合成音）は、C1～C7 では正しく判定できる。C7 を超える高音（約 2.2 kHz 以上）では 48 kHz で 3 音、44.1 kHz で 4 音が1オクターブ下に誤判定された。実際の高音楽器は基音が強いため影響は小さいと見込むが、実機で確認していない。基音欠落には原理的な曖昧さがある。
- 白色雑音を混ぜた音（SNR 20 dB）では、1フレームの誤差が C1～B1 で最大約 5.2 cent、C2～C7 で最大約 2.4 cent になり、±2 cent の目標を超える。SNR 30 dB では C2～C8 が ±0.7 cent 以内。表示では平滑化されるが、その効果は数値で検証していない。
- 空調音などの周期性を持つ環境音と楽器音は、完全には区別できない（音量と信頼度で判定している）。
- iPhone の内蔵マイクは低域が弱く、C1～E2 付近では基音が小さくなりやすい（実機で確認していない）。
- フレーム前後半のエネルギー比による除外は、減衰が非常に速い音（強いピッツィカートなど）の測定を遅らせる可能性がある。
- 立ち上がり確認のため、新しい音の表示は約 50 ms 遅れる。
- Playwright 標準の headless shell 版 Chromium は、疑似デバイスでも getUserMedia が `NotSupportedError` になる。チューナーの E2E は `channel: 'chromium'`（通常版 Chromium の headless）で実行している。
- 処理時間（PC、Node.js 24 で計測、参考値）: 音程1回 約 0.96 ms、スペクトラム1回（縮約・倍音を含む）約 0.74 ms。iPhone での処理時間は未計測。

### 13.2 自動試験

- Vitest: チューナー関連 7 ファイル・108 件（FFT と差分関数の一致、精度、dBFS の正規化、倍音、表示補正、ライフサイクルの競合、Worklet と Worker の転送・欠落、版管理、既存コードへの接続契約）。全体で 73 ファイル・726 件が成功。履歴復帰の競合テストは実際の routes.js を VM で実行して確認している。
- Playwright（`tests/e2e/tuner.spec.js`、通常版 Chromium と疑似マイク 440 Hz）: 14 件が成功。内容は次のとおり。
  - キャッシュが空の状態での初回起動
  - launcher の配信を遅らせた状態でのタップ（タップ内で作ったコンテキストが引き渡されること）と、到着前に退出した場合にマイクを要求しないこと
  - launcher 到着前のバックグラウンド移行・ページ離脱でコンテキストが閉じること、戻ったときに開始されること
  - 先読みでは音声を開かないこと
  - 二重タップでマイクが増えないこと
  - 基準Hzの変更・端の値・復元・ログアウト後も保持されること
  - タブやパネルの移動による解放
  - 戻る／進むでの解放と復帰
  - ログアウト・セッション切れによる解放
  - バックグラウンドでの解放と復帰
  - 安全網（パネルを直接隠した場合）
  - 権限拒否時の案内
  - 一般団員が起動できないこと
  - 表示値に一瞬の外れ値がないこと

  疑似マイク用の WAV は、実行時に OS の一時ディレクトリ（`portal-tuner-e2e/a440.wav`）へ合成する。リポジトリと共有 ZIP には含めない。
