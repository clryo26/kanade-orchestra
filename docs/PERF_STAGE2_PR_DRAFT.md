# PRタイトル案

ポータル性能改善 第2段階A・B：通信棚卸し、再試行・認証確認の集約、HTTPキャッシュ

## Summary

同じ論理要求でも401回復後に再試行予算が作り直され、データGETが最大6回送信されること、同時の認証確認がそれぞれ通信すること、503後の連打や保存後の待機により不要な通信・表示待ちが生じることを改善する。

- 第2段階Aの通信経路・認証副作用・取得状態・描画依存・bootstrap契約・監査再利用可否の棚卸しと、修正前計測を含める。これらを第2段階Bの変更根拠として同じPRでレビューできる単位にする。第1段階Bのコミットは含めない。
- データGETの一時障害による追加送信は通算2回、401回復後の再送は別枠1回とし、合計最大4回に制限する。認証確認は進行中の送信・解析結果だけを共有し、呼出元ごとの適用・解除・戻り値は維持する。
- GETの全503で同じ要求の手動確認を10秒間隔にする。有効なRetry-Afterは自動取得に適用し、保存成功時は関連する待機とキャッシュだけを解除する。保存前の古い503による待機の再登録も防ぐ。管理者への連絡を促すversion_clock_anomalyの文言に、再試行の案内は付けない。
- 本人別の一覧APIにprivate/no-cacheと本文ハッシュのETagを適用する。認証・full bootstrap・操作確認等はno-store。304でも本文構築やDB読取は省略せず、転送量の削減とDB負荷の削減を混同しない。
- 既存の警告以外に画面要素を追加せず、待機中は同じ利用者の表示・入力・Fileを保持する。保存結果が不明の経路は、非JSONの503でも「結果不明」を維持する。

## Impact Scope

- バックエンド：対象の一覧・bootstrap・団員紹介にCache-Control・ETag・Varyを付与・調整し、認証・操作確認等にはno-storeを設定する。DBバージョン管理、接続プール、回収ワーカーは変更しない。
- フロント：共通通信層、認証確認、起動・復帰、取得起点の指定、待機中に表示を保持する画面、保存結果確認。
- extraの個別更新では親一覧も共通の無効化対象に加える。棚卸しで記録した一覧無効化不足をこの経路で解消する。
- IndexedDBの応答キャッシュの記録にvalidatedAtを追加した（旧記録はtimestampで代用。移行・削除は不要）。段階ごとの戻し方は[実装記録](PERF_STAGE2B_IMPLEMENTATION.md)と[待機制御記録](PERF_STAGE2B_RETRY_WAIT.md)を参照。
- 既存の警告に「現在、取得を待機しています。あと◯秒後に再試行できます。」「メンテナンス中です。あと◯秒後に再試行できます。」を表示する（PERF-R29の許容範囲）。version_clock_anomalyは既存の管理者向け文言のみ。
- 旧JSクライアントも、キャッシュ済み本文がある場合は新しいETagと304を既存の経路で処理でき、サーバー先行リリースに対応する。これは旧コードの読取で確認した互換性であり、古いJSを保持した実機での確認は未実施。
