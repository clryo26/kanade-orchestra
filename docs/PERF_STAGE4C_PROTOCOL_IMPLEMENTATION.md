# 第4段階4C 第4単位：書込プロトコル検査

2026-10-25。設計7.2のv2設定・プロトコル検査部分を実装する。**参照先状態を含む完全なDBガードの完成ではない。** 写真の内部UUID、asset状態ロック、候補生成、lease操作、同期/保守の許可ロールは後続であり、今回の025だけでガードを有効化して運用できない。

## 1. アプリ側

既存の環境変数方式で `PORTAL_ALBUM_WRITE_PROTOCOL_V2` を追加した。未指定は無効。`1`/`true`/`yes`/`on`（前後空白・大小文字は無視）の場合だけ、PostgresRowStoreのalbums書込で、同じ接続の同じトランザクション内に `SET LOCAL app.album_delete_protocol='v2'` を一度設定する。新しい設定管理基盤は作らない。

対象はinsert/update/update_columns/update_many/deleteと内部の写真差分更新。共有ItemContextに設定済みかを保持し、親と子の更新や同じctxで複数の更新をしても重複設定しない。autocommit=Trueのctxは、SET前に拒否する。設定に失敗した場合は成功済みと記録しない。通常のtransactionは既存どおりautocommit=Falseで、ロック待ち5秒等を変更しない。

既定無効時はアプリから追加SQLを発行しない。他集合、読取、ListRowStore、明示的ローカルJSONは対象外。v2設定は認可や保守権限の代わりではなく、既存の所有者/管理者判定、期待版、#150の契約、全置換禁止を変えない。データ本文・画面文言・配置・HTTPヘッダーも変更しない。

この環境変数を有効にしてもDBのガードは有効にならない。逆に、設定が送られていても、必要なmigration/トリガーが存在する証拠にはしない。

`album_service`の即時削除・upload失敗時の補償など、既存のGCS操作は今回変更していない。v2マーカーを送るだけで、7日猶予の回収方式へ移行したとは扱わない。これらを台帳・候補と同じ確定処理へ切り替えることも、有効化前の必須残件である。

## 2. Migration 025

`025_album_write_protocol.sql`を追加した。024のチェックサムは変更せず、**`album_gc_foundation_guard_disabled CHECK (NOT guard_enabled)` をそのまま維持する**。制約の存在・検証済み状態と、内部4表を025の実行者が所有していることを確認し、条件不一致なら1トランザクション全体を失敗させる。既存albums/album_photosをロックしてトリガーを追加するため、実適用にはバックアップと書込排出が必要。

`album_require_write_protocol()` はSECURITY DEFINERで、search_pathをpg_catalogへ固定し、制御表をpublic修飾で読む。PUBLICのEXECUTEを取り消し、既定権限による非ownerへの直接付与が残る場合も適用を止める。アプリに内部4表の直接権限や関数の直接EXECUTEは付けない。通常の表DMLからトリガーが動くことは、別ログインで確認する。

albums/album_photosそれぞれにBEFORE行トリガー（INSERT/UPDATE/DELETE）とBEFORE文トリガー（TRUNCATE）を追加する。制御行がない、またはguard_enabled=falseの場合は、既存書込を許可する。この時点で回収を許可するものではない。有効状態ならv2なしの実際の行書込を拒否し、TRUNCATEはv2でも拒否する。0行のUPDATE/DELETEは変更自体がないため、行トリガーの検査も発生しない。

制御行はFOR SHAREで読み、falseを観測した書込が確定する前に、同じ行をtrueへ更新することを防ぐ。共有ロック同士は並行書込を直列化しないが、制御行の変更は待たされる。行がない場合を含め、有効化前に書込を排出する運用条件は省略しない。

**有効化するコード・CLI・実環境向けSQL例は追加しない。** 試験だけが、所有確認付きの隔離DB内で024の禁止制約を外し、trueにして旧書込の拒否を検証する。その結果を、完全なガードや4Dの実行条件がそろった証拠にしない。同期設定だけによる例外も設けていないため、信頼済み同期・保守を含む正規経路の完成まで、実運用の有効化はできない。

## 3. 追加負荷と比較

アプリの既定無効は追加SQL0。有効にした書込は1トランザクションにつきSET LOCAL 1文を追加し、接続の延べ貸出は増やさない。HTTPの最初の要求では認証テーブルのschema確認が入るため、最初の値とwarm状態の値を分けて記録する。

025をDBへ適用すると、制御がfalse/未投入でも、変更した行ごとにトリガー関数から制御表のSELECTが1回入る。これはPython側のSQLカウンターに含まれない。`track_functions`と`pg_stat_xact_user_functions`で、親1行UPDATEに対する呼出し1回を別に確認する。これを「既定時のDB負荷も0」や通信削減と報告しない。

[PG16](perf_stage4/STAGE4C_PROTOCOL_PG16.json) / [PG18](perf_stage4/STAGE4C_PROTOCOL_PG18.json) に、合成データの計測を保存する。実Cloud Runの待ち時間・実GCS通信・課金の値ではない。後続のassetロック/候補/leaseの負荷もまだ含まない。API別の有効化判断は、残る実環境計測と全機能の追加負荷を合わせて行う。

HTTP試験では、offは制御行未投入、onは隔離内で強制的に有効化した状態である。schemaキャッシュのwarm条件はそろえるが、制御状態は異なるため、比較対象はアプリ発行SQLと貸出の回数だけに限定する。DB内部のロック負荷や応答時間の比較には使わない。

## 4. 検証と残件

新しい単体試験は既定で接続に触れないこと、一度だけ固定SQLを送ること、他集合、autocommit拒否、設定失敗を対象にする。PG16/18ではプロトコル拒否、偽の同期設定、autocommitのSET LOCAL、TRUNCATE、通常v2書込、権限、025のrollback、既存migration実行器、制御ロック、5種類の行APIと実HTTP PUT、プール上限1での同じ物理接続への設定漏れを確認する。

[検証記録](perf_stage4/STAGE4C_PROTOCOL_VALIDATION.json)に結果を保存する。既存の台帳39件・全置換3件・写真差分18件・#150の23件も実行する。旧計測と固定画像を上書きしない。実DB/GCS/R25、実接続ロール、同期/バックアップの読取権限、実機・WebKit画像比較は未完了。

プロトコル未設定のSQLは旧書込の代用として試験したもので、旧サーバーの並行稼働やrollbackを実際に行ったS4-15の完了ではない。
