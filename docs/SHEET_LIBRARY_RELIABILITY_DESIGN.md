# 楽譜管理・楽譜ライブラリ 信頼性設計

作成日: 2026-10-18。対象: 楽譜の登録・変更・削除、一覧の同期、PDF表示、個別PDF・曲ZIP・演奏会ZIPの保存。
本書は実装済みの方式と、実機で未確認の事項を記録する。**対象iPhone（iPhone 12 Pro／iOS 26.6.2）での保存・復帰は未確認のため、本番公開可能とは判定しない**（9章）。

## 1. 修正した問題（原因）

| 問題 | 原因 |
|---|---|
| 別端末で登録した楽譜がスマホに出ない | `sheet_library` をサーバーのプロセス内キャッシュ（期限なし）から返していた。Cloud Runの別インスタンスは古い一覧を返し続ける。画面側も `sheetsLoaded` が立つと再取得しなかった |
| 登録・削除で他の楽譜が消える | 登録・パート変更・削除のすべてが「一覧全体を読み込み→変更→一覧全体を保存」。保存は一覧に無い行を削除する（`replace_collection`）。古い一覧を持つインスタンスからの保存で、他端末の登録が消えた。IDもアプリが `next_id` で採番していた |
| 「更新」が再取得を保証しない | 汎用 `request()` はGET失敗時にIndexedDBの古い応答を返し、同じURLの取得を共有する。古い一覧が成功として表示された |
| 楽譜ライブラリから直接PDFを表示できない場合がある | PDFビューアーが `practice_casting.js` にあり、楽譜機能の読み込みに含まれていなかった。互換ファイル `scores.js` が分割ファイルの後に読み込まれ、同名関数を上書きしていた |
| スマホで保存すると元のポータルへ戻れない | 「DL」がPDF・ZIPへの通常のリンク（`<a download>`）。ホーム画面に追加したポータルでは、ファイル表示がポータルの画面を置き換えた |
| 一括DLが不足を隠す | 取得できないファイルを黙って除外し、正常なZIPとして返していた |
| 楽譜ファイルを認証なしで取得できる | `/api/sheets/cloud/view/{名前}` などが認証なしで、楽譜として登録されていないバケット内のオブジェクトも名前で返していた |

修正前のHEADのコードで、2つのサーバー相当（同じ保存先、別々のキャッシュ）を使い「Bの一覧に最新が出ない」「Bの保存でAの登録が消え、IDも重複する」ことを再現した（`.tmp/sheet-baseline-repro.py`、共有ZIP対象外）。

## 2. 登録・変更・削除（行単位・操作ID）

- 一覧全体の保存を廃止し、対象行だけをDBで操作する（`src/backend/services/sheet_library_service.py`、`repositories/sheet_repository.py`）。IDはDBで採番（migration 020で連番の既定値を保証）。
- 変更・削除は、利用者が見た保存版（`revision`）を送る。保存版が違えば `409 sheet_revision_conflict`（変更・削除されたIDを返す）。一括変更・一括削除は全件そろわなければ何も変えない。
- 「曲名配下を削除」「演奏会配下を削除」は、画面に表示中の楽譜のIDと保存版に展開して送る。範囲指定（演奏会ID・曲名）での削除はサーバーが受け付けない（`428`）。一覧を読んだ後に他端末で追加された楽譜は消えない。
- 汎用API `/api/extra/sheet_library` の書込と、DBモードでの一覧全体の保存（`save_json_data("sheet_library")`）は `409` で拒否する。開発用のローカルモードだけ、明示的な初期データ投入として許す。
- 操作ID（`Idempotency-Key`）: 登録・パート変更・一括変更・削除ごとに画面が採番する。
  - 同じ操作の再送は、確定済みの同じ結果を返す（応答が失われた後の再送でも重複・誤った失敗にならない）。
  - 同じ操作IDで内容が違えば `409 sheet_operation_conflict`。保存版の競合（別の操作による変更）とは別のコード。
  - 処理中の操作は `202`（同じIDで後から確認）。処理していたサーバーが止まった場合、10分のリースが切れた後の再送が引き継ぐ。終了の書込はリースを持つ試行だけができる。
- 更新前の画面（操作IDを送らない）からの登録は、新しい行単位の登録として受け付ける（再送保護はない）。保存版を送らない変更・削除は `428`（「画面を再読み込みしてから」）。
- 楽譜の登録・変更・削除では団員向けプッシュ通知を作らない（`notification_types.py` に楽譜・録音の分類はない。回帰試験あり）。

## 3. DBとファイルの整合性・清掃

- 登録の順序: 操作を予約 → ファイル記録を `staged` で作成 → ファイルを保存（GCSは `if_generation_match=0` で新規作成のみ、ローカルは排他作成）→ 1つのDBトランザクションで楽譜行の追加・ファイル記録の `active` 化・一覧更新番号の加算・操作結果の確定。DBとGCSを1つの原子的トランザクションとは扱わない。
- 新しいファイルはファイルID（UUID）ごとの固有名（`sheets/v2/<組織ハッシュ>/<ファイルID>.pdf`）で、保存版（GCSのgeneration）を記録する。既存の楽譜はURL・パス・分類をそのまま使い、migrationで固有のファイルIDだけを付ける。
- 削除: 楽譜行を削除し、ファイル記録を `retired` にする（同じトランザクション）。実体の削除は清掃が行う。
- 清掃（`sheet_cleanup_service.py`、`scripts/cleanup_sheet_storage.py`、既定は確認だけで `--execute` で実行）: 状態はすべてDBにあり、停止後の次回実行で続きから再開する。削除するのは次をすべて満たすファイルだけ。
  - `active` ではない
  - どの組織の楽譜行も同じオブジェクト・パスを参照していない（旧データでは同じファイル名の再登録で1つの実体を複数行が共有していた）
  - 有効なリース（ZIP作成中）がない
  - 退役から15分経過（表示・取得の途中を保護）、または `staged` で24時間経過かつ操作のリース切れ
- 削除は記録した保存版を指定して行い、同名の新しい実体を消さない。旧データ（保存版不明）は削除直前の保存版を読んで指定する。失敗は `delete_pending` のまま 60秒×2^n（最大24時間）で再試行し、対象は同じファイルIDだけで範囲は広がらない。
- 有効期限切れのチケット・リース、30日を過ぎた終了済みの操作記録も清掃が削除する。
- 確認モード（`--execute` なし）は再試行予定を含めDBを変更しない。本番DBでは読み取り専用トランザクションを使う。件数確認・削除ともに指定した組織だけを対象とする。共有実体の参照確認は、削除防止のため全組織を確認する。
- ZIP放置候補の選択後に処理が再開する可能性があるため、清掃UPDATE時にもリース期限・最終更新時刻を再確認する。実際に放置状態へ遷移したジョブだけを清掃し、再開したジョブのリース・部品を保持する。

## 4. 一覧の同期（別端末の反映）

- 組織ごとの「一覧更新番号」（`sheet_library_state.list_version`）を、楽譜行の変更と同じトランザクションで加算する。読み取りは一覧と番号を同じスナップショットで返す。複数サーバーでも同じDBの番号を見るため、サーバー内キャッシュに依存しない（`load_json_data("sheet_library")` もキャッシュを使わない）。
- 画面（`scores/sync.js`）は、楽譜ライブラリ・楽譜管理を開いた時に番号を確認し、変わった時だけ一覧を取得する。開いた時点の最新の一覧を表示する。
- 開いている間の定期確認、ポータルへ戻った時（`visibilitychange`・`pageshow`・`online`）の確認、「更新」ボタンは設けない（2026-10-19 変更。秒単位の自動更新は不要という運用判断）。別端末で追加された楽譜は、楽譜ライブラリを開き直すと表示される。
- 自分の登録・変更・削除の後は、その操作の中で一覧を取り直す（番号に関係なく取得し、取得完了まで待つ）。
- ログアウト時は確認しない。確認は同時に1つだけ。
- プッシュ通知は同期に使わない。
- 応答の採用: 要求番号・一覧更新番号・アカウント（端末ID・団員ID・権限）が一致し、表示中より新しい場合だけ。遅れて届いた古い応答、ログアウト・アカウント切替前の応答は捨てる。
- 一覧の上の表示は、失敗時とサーバーの新しい版の案内だけ。通常時はボタンも最終確認時刻も出さない。
- 失敗時は表示中の一覧を残し、「一覧を更新できませんでした（理由）。表示中の一覧は 時:分:秒 時点のものです。楽譜ライブラリを開き直すと、もう一度取得します」と表示する。キャッシュや古い一覧を成功として扱わない。
- 一覧の反映では絞り込み・開いている演奏会と曲・スクロール位置を保ち、表示中のPDFは閉じない。
- サーバーの版が画面より新しい場合は案内だけを出す。登録・保存中を含め、自動で再読み込みはしない。

## 5. PDF表示

- 実装は `scores/pdf_viewer.js` の1つだけ。楽譜ライブラリの読み込みに含めた（配役画面を先に開く必要はない）。
  - `practice_casting.js` と `scores.js` には同名関数を置かない（本番の読み込み順では後に読まれる側が上書きするため）。
  - 希望曲の参考スコアも同じビューアーと保存ダイアログを使う。
- PDF.js 4.10.38 のlegacy ES module本体とWorkerをポータル内（`src/static/vendor/pdfjs/4.10.38/`）から読み込む。同じ版・ビルドのjsDelivrは予備。本体とWorkerは同じ場所・同じ版を使い、別版は拒否する。CVE-2024-4367の修正版を使い、すべての `getDocument` に `isEvalSupported: false` を渡す。出典・SHA-256はvendor内のREADME。
- 開く・拡大縮小・幅に合わせるは要求ごとに番号を持つ。新しい要求は古い取得を中断し、未完了のページ描画を取り消す。同じPDFの拡大縮小は再取得しない。
- 終了（戻る・別の画面へ移動）でPDF文書（とそのWorker）、描画タスク、Canvasのメモリーを解放する。
- 取得失敗（通信・404・認証）、PDFの破損、描画失敗を区別して表示し、再試行ボタンを出す。
- PDFの取得には端末の認証情報を付ける。ファイルの経路は、その組織に楽譜として登録されたオブジェクトだけを返す。

## 6. 個別PDF・ZIPの保存

### 6.0 PCとスマートフォンの区別（2026-10-19 変更）

楽譜（ライブラリ・楽譜管理・ビューアー・希望曲の参考スコア）と録音（録音部屋）の「DL」「一括DL」は、端末によって保存方法を変える。判定は `save_dialog.js` の `saveMode()`。

- スマートフォン扱い: ホーム画面に追加したポータル、`navigator.userAgentData.mobile`、UAに iPhone / iPad / iPod / Android を含む、iPadOS（`MacIntel` かつ `maxTouchPoints > 1`）。iPadとAndroidタブレットもスマートフォン扱い。
- それ以外はPC扱い。`navigator.canShare` だけでは判定しない（Windows の Chrome / Edge、macOS の Safari もファイル共有に対応しており、PCで共有画面が開いてしまうため）。
- 試験・調査用に `window.portalSaveDeviceMode`（`'mobile'` / `'desktop'`）で上書きできる。

| 操作 | PC | スマートフォン |
|---|---|---|
| 楽譜「DL」 | 「ダウンロードしますか？」の後、チケットURLをブラウザーでダウンロード（ダイアログ・新しいタブなし） | 6.1の保存ダイアログ（共有画面） |
| 録音「DL」 | 「ダウンロードしますか？」の後、ブラウザーでダウンロード（`<a download>`） | 6.1の保存ダイアログ（音声ファイルとして共有画面） |
| 楽譜「一括DL」 | ダイアログでZIP作成の進み具合と大きさを表示し、完成後に自動でダウンロード | ZIP作成後に大きさを表示し、「別の画面で開いて保存」 |
| 録音「一括DL」 | ダイアログで大きさ（約）を表示し、自動でダウンロード | 大きさ（約）を表示し、「別の画面で開いて保存」 |

- 一括DLのZIPは大きさに関係なくページのメモリーに読み込まない（共有画面は使わない）。ダウンロードの前に大きさを表示する。
- 録音のZIPはダウンロード中にサーバーで作る（無圧縮）ため、大きさは `GET /api/recordings/download-zip/info` が返す録音の合計（約）。取得できない録音は件数を表示し、ZIPに含めない。
- ダイアログを使う操作では、ポータル全体の「ダウンロードしますか？」（`bootstrap_loader.js`）を重ねて出さない（`data-download-confirm="off"`）。

### 6.1 共通の保存ダイアログ（`scores/save_dialog.js`）

スマートフォンの個別DLの手順。PCでは一括DLの進み具合と大きさの表示にだけ使う（6.0）。

1. 「DL」で、元の画面の上に保存ダイアログを開く（一覧・絞り込み・表示中のPDFはそのまま）。
2. 準備中は対象名・件数・進み具合・キャンセルを表示する。
3. 準備ができたら「保存先を選ぶ」。押した操作の中で、OSの共有・保存画面（`navigator.share`）を開く。準備に時間がかかっても、利用者のタップから開く。
4. 共有の可否は形式ごとに判定する（`navigator.canShare` にPDF・音声の各形式のファイルを渡す）。
5. 共有画面を閉じた後も「保存できたかは保存先で確認してください」と表示し、保存完了とは表示しない。
6. キャンセル・失敗の後も元の一覧のまま、閉じる・再試行を選べる。

### 6.2 代替保存経路

次の場合は、ファイルをページに読み込まず、短期チケットURL（10分、`/api/sheets/tickets/<ランダム値>`）を別の閲覧画面で開く。録音は認証不要の経路のため、チケットを使わずそのURLを開く。

- その形式を共有できない場合
- メモリー上限を超える場合
- 共有が拒否された場合
- 一括DL（ZIP）の場合（大きさを表示した後）

- チケットは認証済みの端末にだけ発行し、サーバーにはそのSHA-256だけを保存する。使うたびに端末のログイン状態と組織を確認する。
- 別の閲覧画面とは、スマートフォンのブラウザーでは新しいタブ、ホーム画面に追加したiPhoneのポータルではアプリ内のブラウザー画面。PCでは別画面を開かず、ブラウザーのダウンロードにする（6.0）。元のポータルの画面は置き換えない。
- 「別画面を開く」実装だけで、PWAの元画面を維持できたとは判定しない。iPhoneでの確認が必要（9章）。
- 期限切れ・残り30秒以内のチケットは、そのタップでは更新だけを行う。更新後に再タップを案内し、次のタップ中に同期的に別画面を開く。閉じたダイアログや切替前のアカウントの応答は使わない。開けたことをブラウザーから確認できないため、表示や保存の成功は断定しない。

### 6.3 端末メモリーの上限（調整値）

| 対象 | 上限 | 根拠 |
|---|---|---|
| PDF・録音（1ファイル） | 30 MiB | 登録できるPDFの上限と同じ。それ以下のファイルは共有画面で渡せる。録音は一覧の大きさで事前判定する |
| ZIP | 100 MiB | 現在は一括DLのZIPを共有しない（6.0）。値は互換のために残す |

いずれも、対象iPhoneでの確認で見直す。上限を超えるものは6.2の経路で保存する。

登録サイズとContent-Lengthで事前判定し、受信中も実バイト数を上限と照合する。上限超過チャンクは保持せず、Readerと転送を中止し、保持済みチャンクを解放してチケット経路へ進む。Content-Lengthとの不一致は通信エラーとして再試行を案内する。本文受信中も120秒の期限とキャンセルを維持する。試験用の上限変更は引下げだけを許す。

## 7. 一括DL（ZIPジョブ）の完全性

- 同期DB・GCS処理はFastAPIのワーカープールで実行する。非同期のリクエスト本文読取後も、保存・変更・削除・チケット作成はワーカーへ渡す。ZIP実行中も別の要求（キャンセル等）を受け付け、組織コンテキストを引き継ぐ。

- 作成時に対象を固定する（楽譜ID・保存版・ファイルID・GCSの保存版・ファイル名・件数）。対象ファイルにはリース（15分、作成中は各段階で延長）を付け、清掃から保護する。作成中に削除・変更されても、固定した内容でZIPを作る（完了後に「作成後に変更があります」と分かる）。
- 作成は段階実行。15秒の処理予算と8MiBの部品上限を各チャンクの間で確認し、ファイル途中でも読取位置・CRC・開始位置・保存版をDBに記録して再開する。進捗確保のため各段階の最初のチャンクは実行する。部品は試行ごとの新規名に書き、32部品に達した段階で連結する。最後の終端部作成・連結・読戻しは独立した段階で行う。
- **旧仕様の「要求全体が20秒以内」は撤回する。** 開始済みの外部I/Oは15秒で強制終了できない。読取等はHTTP 10秒＋再試行期限10秒、部品書込は30秒＋20秒、連結はcomposeとreload各10秒＋再試行期限10秒を設定する。呼出し回数とDB処理の余裕30秒を含む設定上の見積りは最大205秒、試行リース240秒、クライアント待機270秒。DBロック待ち・ネットワーク・実GCSを含む絶対的な所要時間保証ではなく、実環境の計測は未実施。
- 途中結果の確定と同時に試行ID・リースを解放し、次の要求がすぐ続行できるようにする。別の要求が実際に処理中のときだけ `busy` を返す。確定時に試行ID・期限・状態をDBで再確認する。古い試行は公開済みZIPを上書きできず、自分の試行で作成した部品だけを削除できる。
- 連結後のZIPの終端レコードを保存先から読み戻して一致を確認してから、ダウンロード可能（`ready`）にする。端末に大容量ZIPを丸ごと読み込まない（100 MiB超はチケット経路）。
- 取得できないファイルがあれば全件入りのZIPは作らず `incomplete` とし、不足の一覧を示す。不足分を除いたZIPは、利用者が「不足分を除いてZIPを作成」を押した場合だけ作り、ZIP内に不足一覧（`不足している楽譜.txt`）を入れ、ファイル名に「_一部」を付ける。
- 状態: `building`・`ready`・`incomplete`・`failed`・`cancelled`・`expired`。作成状況は端末にジョブIDを保存し、画面を開き直しても続きから進める（サーバーにも状態がある）。

| 項目 | 値 | 根拠 |
|---|---|---|
| 1つのZIPの件数 | 1000件まで | 20曲×30パートの演奏会が入る。作成はファイル1件ずつのストリーム |
| 合計容量 | 1 GiBまで | 32ビットのZIP形式の範囲内。端末の保存・通信の現実的な大きさ |
| 1段階の時間 | 処理予算15秒、設定上の見積り最大205秒 | 開始済みI/O・部品書込・連結・DB処理の余裕を加算。実GCSの時間は未計測 |
| 試行リース／クライアント待機 | 240秒／270秒 | 設定上の処理見積りより長くする。中間確定では待たずに解放 |
| 作成中の放置 | 30分で `failed`（abandoned） | 段階の要求が来なくなったジョブの部品を清掃する |
| 完成したZIPの保持 | 24時間 | 期限後は保存先から削除し、もう一度作成する |
| 対象ファイルの保護 | 15分（段階ごとに延長） | 作成が止まっても期限で解放される |

## 8. 旧画面・再読み込み・PWA復帰

- 遅延読み込みのスクリプトはページと同じリリース番号で読み込む（既存の修正）。サーバーの版が新しくなると、楽譜画面に案内を出す（自動の再読み込みはしない）。
- 更新前の画面からの要求:
  - 範囲削除・保存版なしの変更は `428` で拒否し、新しい保存処理の整合性を崩さない
  - 登録は行単位で受け付ける
  - ファイルへの直接リンク（認証ヘッダーなし）は、ポータルに戻るリンク付きの案内ページを返す
- 複数ファイルの登録で保存する情報（`localStorage`、アカウントごと）:
  - 演奏会・曲
  - 各ファイルの操作ID・名前・大きさ・更新日時・SHA-256
  - 完了・未完了の別
- 再読み込み後は「前回の登録が途中です」と未完了のファイル名を示す。ファイルそのものはブラウザーに残らないため、選び直しが必要と明示する。選ばれたファイルは名前・大きさ・SHA-256で元の内容と照合し、元の操作IDで再開する。照合できないファイルは使わない。
- キャンセルは送信前のファイルを止めるだけで、登録済みの楽譜は削除しない。
- ZIPの作成状況はジョブIDで再開できる。PDFの表示・拡大率、保存ダイアログの途中状態は再読み込み後に復元しない（再度の操作が必要）。

## 10. 運用（本番反映時）

2026-10-19の追加レビュー修正と最新の検証状況は [公開準備状況](SHEET_LIBRARY_RELEASE_READINESS.md) を参照。使い捨てPostgreSQLでは、既存形式の基礎表を用意して001〜021を実際の `scripts/migrate_db.py` で通し適用し、再実行時のスキップ・既存楽譜保持・トリガー作成まで確認済み。

1. migration 020・021 を通常の手順（`scripts/migrate_db.py`）で適用する。追加だけで、既存の楽譜行・URL・分類は変わらない。既存行にはファイルIDとファイル記録（`legacy`）が付く。
   - 020適用済み環境には021で `sheet_zip_jobs.progress` を追加する。020を書き換えて適用し直さない。ローカルSQLiteも既存表に同列がなければ追加し、既存行を保持する。
2. 清掃は確認実行（`--execute` なし）で対象を確認してから実行する。`scripts/cleanup_sheet_storage.py --organization <組織> --environment <環境> --db-name <DB名>`。
3. GCSの `sheet-zips/v1/` 配下は作成途中・完成したZIPの一時領域（24時間で清掃）。本番→テストの同期対象（`sheets/`・`albums/`）には含まれない。新しい楽譜ファイルは `sheets/v2/` 配下で、既存の同期対象 `sheets/` に含まれる。
   - DBの同期は `sheet_library` だけを写し、`sheet_files`・操作・ZIP・チケット・一覧更新番号は写さない（環境ごとの状態）。ファイル記録のない行は、ZIP作成・削除の時にファイル記録（`legacy`）を作ってから扱う。
   - 同期やDBの復元で一覧更新番号が画面の値より小さくなった場合、画面はそれを初期化とみなし、サーバーの一覧をそのまま採用する。
4. 戻し方: 前の版のアプリは追加した表・列を参照しないため、アプリだけを戻せる。ただし前の版は一覧全体の保存で、戻した後の同時操作では以前と同じ問題が起きる。戻した間に前の版が追加した行（ファイルIDなし）は、再び新しい版にした後、ZIP作成・削除の時にファイル記録が補われる。表・列の削除はデータ削除になるため行わない。
