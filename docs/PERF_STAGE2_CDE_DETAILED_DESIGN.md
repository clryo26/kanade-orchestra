## 2. 現行実装と設計上の制約

### 2.1 維持する実装

- GET集約、認証確認の実行中の送信・応答分類の共有、再試行予算を再実装しない。一時的障害の追加2回と401回復再送1回は別枠。認証確認の予算も別に共有する。
- GETの既存識別要素と`_forceRevalidate`、団体ヘッダー指定時の集約・キャッシュ除外を維持する。
- 全503の手動確認は要求単位で10秒間隔。自動取得は有効なRetry-Afterに従う。成功・認証切替・関連保存成功時の解除、古い503による待機復活防止を維持する。
- 楽譜専用`sheet_api.js`は汎用手動待機の対象外。「開き直すと再取得」と401再送時の予算引継ぎを維持する。
- 確認済み保存をキャッシュ削除失敗で失敗扱いにしない。削除未確定の旧キャッシュを短期再利用・代替表示へ戻さない。
- `portalResponseEpoch`は保存でも進むため、認証切替の判定に使わない。

### 2.2 対象外と既存不具合

DBスキーマ・バージョントリガー、プール・READ ONLYコンテキスト、物理回収、静的配信方式、依存更新は対象外。第3段階以降や別PRの変更を混ぜない。

入口`main.js`、共有状態`portalAppState`、公開関数、分割ファイル順序、既存イベントを維持する。通信ラッパー、汎用状態管理基盤、通知部品、ビルド工程を新設しない。

[#145](https://github.com/clryo26/kanade-orchestra/issues/145)の利用者切替時のデータ残存候補、[#146](https://github.com/clryo26/kanade-orchestra/issues/146)の描画抑制フラグの例外復旧は別変更。Cで全データのログアウト初期化や抑制処理の全面改修を行わない。対象で問題が再現したらその対象を保留し、別修正との統合順を決める。

### 2.3 棚卸しとの差

extra更新の親一覧へのキャッシュ無効化・待機解除はBで追加済み。旧資料の無効化不足は現在の一般更新経路では修正済みで、Cで再実装しない。プロモーション保存・結果確認後の解除も既存処理を利用する。

## 4. 修正前計測と比較方法

## 5. 第2段階C：取得状態と適用処理

### 5.1 対象と既存状態

主対象は`bootstrap_loader.js`の`loadExtraData`と`ensureDeferredTabDataLoaded`。まずextraに限定し、`loadEvents`/`loadAuthManagement`は独立した計測・試験後に追加する。

19個の`deferredPortalDataFlags`はevents、absences、eventResponses、dateAdjustments、dateAdjustmentResponses、payments、castings、pieceInfos、practiceInstructions、performanceDayInfos、albums、flyerDistributions、flyerDistributionAssignments、concertRecordVideos、desiredPieces、promotions、venueSettings、connectionSettings、authDevices。

boolは有効データの適用履歴で、空配列成功でもtrue。最新性・取得中・認証済みを兼用しない。再取得失敗で旧データを空にせず、保存後の明示再取得をboolだけで省略しない。

`essentialDataLoaded`、`essentialLoadPromise`、`dataLoaded`、`backgroundLoadScheduled`、時刻・描画キーは既存責務を保つ。団員詳細・紹介・notices・楽譜・録音・`promotionLoadState`・JS読込Promiseは専用状態を残す。サマリーを詳細済みとせず、本人会計を管理全件済みとしない。

### 5.2 合流と適用の所有

通信合流は既存`request()`に任せる。追加状態はローダー内の実行中取得と適用識別に限り、完了本文の新キャッシュを作らない。

1. 引数省略は既存全spec、配列は重複除去した指定集合、未知名は既存同様エラー。19フラグと全specを同一集合とみなさない。
2. 集合・利用者識別・応答世代・強制再検証等が同じ実行中処理だけ合流候補とする。手動/自動の待機判定は通信層を優先し、抑制応答を取得中として登録しない。自動待機が許可された手動確認を妨げない。
3. 集合別の開始順序・コンテキストを持ち、共有呼出元は同じ結果識別を受け取る。呼出元optionsを変更しない。
4. `Promise.allSettled`による指定集合の完了待ちを維持し、ネットワーク完了ごとの逐次表示へ変えない。
5. 完了待ち後、現在のコンテキスト・最新開始順序を確認。同じ結果の最初の適用者だけが所有し、他は適用・描画を繰り返さない。
6. 別集合を待つ間に新しい同集合結果が採用されたら古い結果で上書きしない。保存・認証切替をまたぐ結果も破棄する。
7. 採用集合だけを`appliedCollections`として6章へ渡す。失敗・抑制・古い結果を入れない。全抑制ならDOMを維持する。
8. 完了時に実行中登録を解除。古い処理が別登録を消さないよう同一性を確認する。完了結果を要求間でキャッシュしない。

下位`request()`の検査だけでは、別集合を待つ間の変更を防げないため適用直前にも検査する。描画判定のための全本文ハッシュ・深い複製は導入しない。

ローダー側では`_requestOrigin`が異なる呼出しを合流させない。省略時の既存扱いを変えず、自動処理の判定結果を手動操作へ転用しない。下位GET集約のキーは変更しない。適用済みの印はデータ代入が成功した後に設定する。描画例外を正常完了や取得失敗へ読み替えず、例外を握りつぶさない。

状態遷移は「未取得→取得中→成功適用」または「未取得→取得中→失敗」。適用済みの再取得では「旧データ保持＋取得中→新データ採用」または「旧データ保持＋失敗」とする。待機抑制と古い結果の破棄は取得成功と区別し、読込済みフラグを新たに立てない。

### 5.3 特殊経路とエラー

部分失敗は成功分だけ採用し失敗分を保持。503警告・待機、`version_clock_anomaly`の文言、保存結果の「結果不明」を維持し、合流で警告を増やさない。

楽譜専用同期、録音再生、団員詳細/紹介、プロモーション保留操作確認を一般ローダーへ統合しない。既存sheets specは互換経路として試験し、新しい楽譜取得をそこへ集約しない。

### 5.4 PERF-R06：復帰時の更新範囲

第2段階Bで、起動・復帰・401回復の認証確認は実行中の1送信へ集約済み。本節はその後の取得範囲だけを扱い、認証確認の共有・副作用の配置は変更しない。

- 鮮度判定は既存の`PORTAL_RESUME_SYNC_MAX_AGE_MS`（60秒）と`syncPortalSessionOnResume`の実行中ガードを使う。新しい周期確認・ポーリングを追加しない。
- 60秒を超えた復帰では、既存どおり基本データを再確認する。追加データは表示中タブが必要とする集合だけを再確認し、それ以外の取得済み集合は「再確認が必要」とする。
- 「再確認が必要」は5.2の状態に一つの印として持つ。旧データは表示・保持したまま、次にそのタブを開いたときに取得する。読込済みフラグを未取得へ戻さない。
- 利用者の明示的な更新は60秒判定で省略しない。復帰からの取得は`_requestOrigin: 'automatic'`のまま扱う。
- 入力中のフォーム・選択File・開閉・スクロールを復帰処理で初期化しない。
- C0で現在の復帰が取得する集合と回数を記録する。表示中以外の集合を取得している場合だけ変更し、既に表示中の範囲に限られていれば変更しない。

### 6.3 適用規則

採用集合の和から必要な描画関数を選び既存順序で一度ずつ呼ぶ。末端関数・ラップ後homeまで計数し、上位の重複除去だけで完了としない。

削除・空配列も描画し、同一本文か推測して省略しない。非表示タブの次回表示まで試験する。既存`renderPaymentAdmin`の`preserveForm`等を活用する。団体File初期化・接続設定上書き・select再構築を無関係な取得で起動しない。保存成功時の対象フォームのクリア・閉じる操作は維持する。汎用の入力退避/復元基盤は作らない。

### 6.4 PERF-R12：重複したソート・検索

C2の対象描画で、同じ描画内に繰り返されるソート・ID検索・集計の回数と時間をC0で記録する。

- 計測で効果を示せた箇所だけ、データ世代と取得条件を鍵にした並び順・検索Mapの再利用を行う。依存データの変更で確実に無効化する。
- SQLやサービスで保証した並び順を理由なく再ソートしている箇所は、並び順の契約を試験で固定したうえで除く。
- 元配列を破壊的に並べ替えない。日付・時刻は既存のJST・瞬間時刻の比較を維持する。
- 件数が小さく効果のない処理を別キャッシュへ置き換えない。効果がなければ対象外とした理由を記録する。

| API | 内容 | 維持条件 |
|---|---|---|
| `/api/bootstrap-lite` | 基礎一覧・団員サマリー・本人payments・part/org/sns設定・revision/menu | サマリーを詳細へ拡張せず本人会計照合を変えない |
| `/api/bootstrap-core` | 空extras・revision/menu | 全データの読込フラグを更新しない |
| `/api/bootstrap` | full各集合 | no-store・アプリキャッシュなし。concert_record_videosを含むと仮定しない |

liteの団員詳細削減・coreの全件削減は既に済んでいる。追加効果だけ評価する。`applyBootstrapData`の欠落キーは既存値維持、明示空配列は空化という区別を保つ。

### 7.2 D0の判断資料

権限別に項目bytes・組立時間・初回必要画面・後続API・取得回数/待機増、圧縮転送量、表示可能時刻を記録。維持/移動候補、移動先・権限・表示、初回/再表示の総通信量を示す。候補なし・不利益超過ならD1を保留。具体項目未確定の現時点で本文を変えない。

### 7.3 D1の固定条件

- URLは`/api/v2/bootstrap-lite`と`/api/v2/bootstrap-core`。移動項目・表現バージョン値をD0追補で確定してから実装する。
- v1本文を維持し旧JSを空表示にしない。v2通常リリースから最低90日維持し、その後も利用状況確認・別レビューなしに削除しない。
- v2の404だけv1へ切替。401/403/5xx・通信例外で切り替えない。v1本文/ETagをv2キャッシュに保存しない。
- URL/表現版でキーを分離。保存後無効化・待機解除は両版。無関係なチューナー/メトロノーム/音声DBを消さない。
- パス判定のtimeout、認証、キャッシュ、no-store、middleware、計測マークを一覧化。lite12秒/core20秒を既定15秒へ落とさない。
- 団員詳細/紹介の権限・項目・順序を維持。既存読込表示を使い一瞬の空欄を加えない。
- DBバージョン・スナップショット置換は第3段階とする。

## 8. 第2段階E：監査主体の受渡しと再利用、応答キャッシュの整理

### 8.1 現行と計測

監査は`call_next()`後の`finally`で同期実行され、応答送信完了後とは限らない。`device_auth_record`はDBデバイス・団員を読み、取得不能時に代替認証を返す場合がある。INSERTは別の接続取得。

共通プール最大5に含まれ、回数は経路別実測とする。常に2回・必ず1回減としない。第3段階の本体接続1本とは別に監査を予算へ含めるが同じプールを二重計上しない。

主体取得・INSERT・監査全体・イベントループ停止を分離計測。スレッド化・キュー化・背景化・記録タイミング変更は含めない。

### 8.2 有効化条件

現時点で再利用を証明済みの経路はない。本人非更新のAPIでも、別要求の氏名/権限/団員/device変更で認証時と監査時の値が変わる。静的fixture一致だけで保証としない。

E0は実際の依存処理/middlewareで既存値と比較する。保証不能ならE1保留、PERF-R22削減は未達。ロック・DB方式・監査の意味を変える必要があれば別設計とする。

### 8.3 E1実施時の受渡し

設定は認証依存の薄いアダプター、受渡しは同一`request.state`、読取はmiddlewareの`finally`。直接認証呼出し・Depends別名の互換性を維持し、取得元を外部JSONに加えない。

内部情報は確認有無・認証成否・DB由来・device一致・必要主体項目のコピー・経路・同一性保証判定に限定。認証record全体/Secretを渡さずdevice/member ID・名前・permissionの既存値を保つ。

情報なしと確認済み空主体を明示区別。truthinessで決めない。method/ルートの許可、成功、DB由来、同一性保証が全成立時だけ再利用。許可一覧の既定は空。

失敗・依存未実行・`fallback_auth_device`・取得元不明・JSONモード・主体変更・長時間資産操作・独自認証・保証不能は既存取得へ戻す。失敗主体を空にせず、件数/status/target/request_id等と監査例外の扱いを保つ。

本番常時二重読取比較を導入しない。E0は架空データ試験と許可された計測で行う。E1保留時に未使用の本番受渡しコードだけ追加しない。

### 8.4 PERF-R17：ポータル応答キャッシュの整理（E2）

E0/E1と独立した単位とする。統合詳細設計v1.3の9章と、第2段階詳細設計v1.3の10章の条件を引き継ぐ。

- 整理対象は`OrchestraAppCache`の`bootstrap_cache`だけ。許可リストに追加しない限り、他のDB・ストアを開かず操作しない。
- 保留操作を保持するlocalStorage、通知設定等も対象外。
- 基準は最終使用から7日、最大200件、概算20MiB。期限切れを先に、上限超過時は最終使用の古い順に削除する。E2の修正前計測で実際の件数・容量を記録したうえで設定値として確定し、本書と運用文書に記録する。
- 7日判定と削除順は有効な`lastAccessAt`を優先し、欠けている旧記録では有効な`timestamp`を代用する。`validatedAt`を最終使用時刻へ読み替えない。両方とも欠落・不正なら期限切れと断定せず、件数・容量の上限超過時には時刻不明の記録を先に整理する。有効な時刻は有限の正のミリ秒値で判定時刻以前のものとする。
- `lastAccessAt`は読取ごとに書かない。前回の永続更新から1時間以上経過した場合だけ更新し、同一キーの更新を集約する。第2段階Bで追加した`validatedAt`（再検証成功時刻）と混同しない。旧記録への初回付与は1回だけ行い、以後は1時間の間引きを適用する。
- `approximateBytes`は保存時に本文の概算で記録する。旧記録で欠けている場合は整理時に概算する。
- 解釈できない旧形式キーと、認証世代が変わって使えなくなった旧利用者のキーは、破棄可能な応答キャッシュとして整理対象に含める。ただし#145（同じタブでのデータ残存）の修正を兼ねない。
- 起動の主要処理を待たせず、小分けに実行する。上限を超える単一応答は保存せず、取得結果は通常どおり返す。
- 整理対象の抽出は候補選定にとどめる。削除するreadwriteトランザクション内で現在の記録を読み直し、最新の使用時刻・内容・容量で整理条件を再判定する。抽出後の更新で条件を満たさなくなった記録は削除せず、上限超過時は必要な残りの候補を再評価する。別タブの通常書込も競合対象とする。
- 使用時刻の更新もreadwriteトランザクション内で現在の記録を読み、存在する有効な記録のメタデータだけを更新する。以前の読取結果の本文・ETagをそのままputして戻さない。削除済み・無効化済みなら更新を省略し、`invalidatedKeys`等の無効化状態を使用時刻更新や整理で解除しない。新しい本文・ETag・`validatedAt`を上書きしない。
- 削除・メタデータ更新の完了は個々のrequestの成功ではなくトランザクションの完了で判断する。abort時に整理件数や永続更新済み時刻を確定扱いにしない。
- 整理の失敗で表示・保存・ログインを失敗させない。全IndexedDBの削除やDB自体の削除を、整理処理にも戻し方にも含めない。

| 対象外DB | 対象外ストア |
|---|---|
| portalTunerAdvanced | ownerSettings、instruments、presets、sessions、seriesChunks、noteEvents、syncOutbox、localTombstones |
| portalMetronomeHistory | ownerState、sessions、dictionaries、timingEvents、syncOutbox、tombstones、budget |
| portalMetronomeCalibration | profiles |
| portalMetronomePresets | presets |
| portalAudioControl | claim |

## 9. 画面・挙動の維持

文言・項目・順序・配置を維持。PERF-R29以外の許容差を増やさず新しいスピナー・要素を作らない。

### 10.2 最終検証

対象試験の後、最終SHAで以下を実行。画像比較を全e2eの代替にしない。

```powershell
uv run python -m compileall -q src/backend tests
uv run ruff check .
uv run pytest
npm run check:frontend:syntax
npm run test:frontend
npm run test:e2e
```

同一固定WebKit画像/DOM比較と必須CI・release-safety等を維持。依存監査を無効化せず別PR更新後は統合SHAで確認。送信増加なし、描画削減、適用回数を評価。D1の後続取得増は追補で総量/表示時刻を判断する。実機iPhone・ホーム画面・BFCache未実施は未確認としWebKitで代用しない。

## 11. リリースとロールバック

単位別差分・記録でレビュー。範囲はコード内の対象集合指定で管理し、新運用フラグ基盤は作らない。下位共有処理変更時はB回帰も実行する。

| 単位 | 完了の証跡 | 戻し方 |
|---|---|---|
| C1 | 重複適用/競合・回数比較 | ローダー整理だけ戻しBの予算/待機/キャッシュ安全条件を残す |
