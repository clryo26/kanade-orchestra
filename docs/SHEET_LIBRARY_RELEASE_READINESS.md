## 5指摘への修正

1. **イベントループ停止:** 同期DB/GCSを使う楽譜の読取・ZIP処理を同期ハンドラーに変更し、FastAPIのワーカープールで実行する。非同期の本文読取を要する変更・削除・チケット・ZIP作成と、アップロードのDB/GCS確定処理もワーカーへ渡す。遅いZIP・アップロード中にも別のキャンセル要求が応答し、組織コンテキストを保持することを試験した。
2. **確認モードのDB更新:** 保持対象の再試行時刻更新は実行モードだけに限定。確認モードはPostgreSQLの読み取り専用トランザクションを使う。繰返し実行でDB行とファイルが変わらないことをSQLite・PostgreSQLで確認した。
3. **清掃範囲:** チケット・リース・操作記録の件数確認と削除を指定組織に限定。ZIP清掃の状態更新・リース削除にも組織条件を追加した。別組織の期限切れ記録を保持することを確認した。ファイル共有の参照確認は、誤削除防止のため全組織を確認する。
4. **CIのDB試験不足:** `SHEET_TEST_DB_URL` と楽譜PostgreSQL試験をCIに追加。新設サービスも計測するようカバレッジ対象試験に楽譜・清掃・ZIP・同時要求の回帰試験を加えた。50％の閾値は維持した。
5. **DockerへのローカルDB混入:** DB本体・SQLiteジャーナル類を `.dockerignore` に追加。`scripts/check_docker_context.py` は合成データだけのscratchイメージを作り、実際のDocker除外動作とソースの保持を確認する。CIにも追加した。既存のローカルDBは保持した。

## 最終確認で追加修正した競合

清掃が放置候補を選択した直後に別の要求がZIP処理を再開すると、古い選択結果だけをもとに稼働中ジョブを `failed/abandoned` にし、リース・部品を清掃する問題を、使い捨てPostgreSQLの2接続で再現した。

清掃のUPDATEでリース期限・最終更新時刻を再確認し、`RETURNING job_id` によって本当に放置状態へ遷移した場合だけリースを解放するよう修正した。再開済みジョブを失敗・削除対象にせず、リースと部品を保持する回帰試験を追加し、修正前の失敗・修正後の成功を確認した。DBスキーマ変更は不要。

## コミット対象の注意

今回の追加修正は `.dockerignore`、`.github/workflows/ci.yml`、`scores.py`、`sheet_library_service.py`、`sheet_cleanup_service.py`、Docker確認スクリプト、関連試験・文書。これらは先行する楽譜信頼性実装に依存するため、公開対象にはその新規サービス・repository・フロントモジュール・vendor・020/021も含める。作業ツリーには宣伝・通知などの先行変更も混在しており、共有ファイルは差分単位で確認する。`.pytest-promotion-*`、`.tmp`、ローカルDB・実データは含めない。

## 本番公開前に残る確認

1. 対象コミットのCI成功後、通常のDeploy Testで020・021を適用し、件数・URL・ログ・healthを確認する。
2. テスト環境の実GCSで登録・範囲読取・部品連結・保存版指定の削除・清掃・大容量ZIPの所要時間・キャンセルを確認する。
3. iPhone 12 Pro／iOS 26.6.2のSafariとホーム画面のポータルで、共有・ファイル保存・復帰・期限切れリンク・メモリー上限を [実機チェックリスト7-13](MANUAL_DEVICE_QA_CHECKLIST.md) で確認する。
4. ZIPの処理予算15秒は要求全体の20秒保証ではない。設定上の見積り205秒・リース240秒・クライアント待機270秒の実環境確認と、要求全体20秒という従来仕様との差異を解消してから、本番公開を判定する。
