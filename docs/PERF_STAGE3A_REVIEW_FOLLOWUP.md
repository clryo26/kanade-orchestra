## 2. 追加した試験と架空データ

試験の入口・接続先ガード・再実行方法は[初回資料](PERF_STAGE3A_BASELINE.md)と同じ。非空の子集合で再計測する場合は次の変数も設定する。接続先は専用の使い捨てDBに限る。

```powershell
$env:PORTAL_PERF_STAGE3_CHILDREN='1'
$env:PORTAL_PERF_STAGE3_REPORT='docs/perf_stage3a/CHILDREN_AND_CONCURRENCY_POSTGRES18.json'
.venv/Scripts/python.exe -m pytest tests/backend/test_perf_stage3a_postgres.py -q
```

出欠・イベント回答・写真等の基準量は初回と同じ。追加のperformance_pieces/payment_performance_feesは実親IDに関連付ける。既存schema生成と明示的に適用する002/016 migrationは隔離DBだけを対象にする。全migrationを再現した本番相当schemaとは扱わない。

### アプリの接続処理

最大1接続の共通プールを試験内で作り、同じbackend PIDが再貸出されることを確認する。READ ONLY/RR、lock_timeout、statement_timeout、同期GUCをSET LOCALし、正常終了と例外によるrollbackの後、設定が初期値へ戻ることを確認した。autocommit=TrueからFalseへの復元も確認する。通常保存のLOCK_TIMEOUTが既存5sであることを固定した。

### 読取と保存・監査の同時投入

1つのASGIイベントループへ、lite・演奏会・団員・団員紹介の4 GETを同時投入する。比較条件は読取だけの場合と、予定1/2への2 PUTも加える場合。標準/2倍量、初期メモリcold/warmを組み合わせ、各5回実行する。各版で40バースト、GET160件・PUT40件の200要求を記録する。初期状態は制御した実験条件で、TESTでのhit/miss頻度ではない。

本物のルーター・認証・RowStore保存・監査ミドルウェア・監査INSERTを使う。架空の団員1を管理者とし、専用DBの監査行が成功ステータス・同じ主体権限で記録されることを確認する。監査の貸出は主体の端末/団員取得2回、INSERT1回として分ける。Web Pushは試験環境で無効化し、外部送信は行わない。

ContextVarで各要求の計測を区分し、SQLや借用処理を差し替えず元の関数を呼ぶ。要求ごとのSQL数・貸出数・接続取得時間・本文長と、バースト単位のプール待ち統計を記録する。

audit_sync_msはイベントループ上で実行された同期監査関数の所要時間。audit_scheduled_callback_delay_msは監査開始直前に同じループへ予約したcallbackが動くまでの時間で、監査後の他処理・スケジューリングも含む。後者を監査だけの厳密な停止時間とは扱わない。読取の遅延差も、保存・無効化・認証・監査を含む混合負荷の差であり、監査だけが原因とは断定しない。

ASGI内での同時投入であり、実TCP・複数Cloud Runインスタンス・本番同時実行80の負荷試験ではない。本文構築などの同期処理が1ループ内で直列になる現行の性質も含める。

### 別の更新元と旧メモリ

MemoryCacheを2個用意し、Aで予定を取得→別接続の直接SQLで更新→Aの条件付き取得→新しいBで取得→Aを消去して取得、という現行挙動を記録する。Aの旧メモリでは304、新しいBと消去後のAでは更新済み本文の200となることを確認した。

これは新しい版の正しさの証明ではなく、3Dで解消する現状の不整合の基準。2個のキャッシュを順に使う同一プロセス・同一プールの模擬であり、2台へデプロイして試験したものではない。3Dの試験では更新を検知する側へ期待を変更して比較する。

## 3. 計測成果物と読み方

- [PostgreSQL 18](perf_stage3a/CHILDREN_AND_CONCURRENCY_POSTGRES18.json)

各版は非空子での8経路×2量×3状態×5回=240サンプルと、同時投入の200サンプルを持つ。初回の480サンプルを上書きしない。接続・SQL・本文長等の指標の定義は初回資料を引き継ぐ。追加のoperations/acquisitionsは監査主体取得・書込を分類した値で、SQLの本文・パラメーターや実データは保存しない。

非空の子があっても、標準量のlite warm304はSQL13・貸出11、演奏会warm304はSQL0・貸出0。子を含む本文が大きくなったことと、SQL数が増えたことを混同しない。保存PUTは貸出6回で、そのうち3回が監査。将来の読取枠や接続共有の実装前なので、追加SQLの上限や有効化後の速度を達成済みとは扱わない。

所要時間はこのローカル試験・投入数での値で、実環境の受入閾値ではない。追加の一覧SQLが見合うかという3DのAPI別判断を、本資料だけで完了しない。
